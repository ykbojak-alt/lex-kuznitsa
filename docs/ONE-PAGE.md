# ИИкузница — агент, который отвечает по регламентам и умеет сказать «не знаю»

**Заголовок:** ИИкузница — агент, который отвечает по корпоративным регламентам и умеет сказать «не знаю».

## Модель

Основной путь — **NexusLink** (внешний LLM-шлюз на нашем сервере), совместимый
с Anthropic/OpenAI API. Fallback — локально развёрнутая **Qwen3-8B-Instruct GGUF
Q4_K_M** (~5 GB, лицензия веса Apache-2.0), которая используется, если шлюз
недоступен или требуется изолированный контур. Embedding — **bge-m3**
(~2 GB, Apache-2.0), reranker — **bge-reranker-base** (~1 GB, Apache-2.0), оба
поднимаются локально независимо от профиля LLM. Наш код — MIT.

## Агентность (не менее 7 шагов)

Один вопрос проходит не менее 7 шагов: **normalize** → **decompose** (вопрос разбивается на 1..N подвопросов) → **retrieve** (гибридный поиск: BM25 + векторный, rerank top-K) → **resolve** (определение действующей редакции по §4 логике) → **conflict check** (разрешение противоречий или кандидат на отказ) → **compose** (ответ строго из цитат, каждая фраза ссылается на doc_id + редакция + фрагмент) → **verify** (все утверждения покрыты цитатами). Каждый шаг виден в интерфейсе (прогресс 1/7 … 7/7) и записан в журнал. Минимум три шага — архитектурное требование (один вызов LLM = 0 баллов по критерию агентности).

## Обоснованный отказ

При неразрешимом противоречии между двумя действующими документами одного уровня, либо когда ни один фрагмент не проходит порог релевантности, либо когда ответ требует документа, которого нет в корпусе, агент отказывается от однозначного ответа. Результат — **штатный**, не ошибка: перечисляются конфликтующие документы с редакциями и датами, объясняется причина, указывается, что нужно от пользователя. Это закрывает вопрос «действующего документа», который заказчик ждёт от команды.

## Логика действующего документа

Иерархию заказчик не задавал — мы её формализовали и обосновали. Уровни приоритета: **Приказ/распоряжение > Политика > Регламент/процесс > Инструкция/методичка > Описание продукта/правила лицензирования > FAQ**. Внутри уровня: больше effective_date, больше revision, явная отмена, явное указание «настоящий документ имеет приоритет над X». Формализация: вес = f(уровень, дата, редакция, отмены, область действия). Не «выбрать самый свежий», а «выбрать самый сильный действующий в области вопроса». Область действия критична для мульти-регламентных вопросов.

## Аналитика и журнал

Журнал (append-only JSONL) агрегируется в отчёт: **отказы** (сколько, причины, какие документы конфликтуют), **неудачные поиски** (нулевая выдача после rerank), **«чего нет в каталоге»** (темы, не покрытые ни одним документом), **топ вопросов** (частотные темы), **покрытие** (доля ответов с полной цитатной опорой). Ничего дополнительно не собираем — аналитика = агрегат по журналу.

## Экономика

Локальный инференс и векторный поиск — **нулевая стоимость запроса**. Кэш ответов и эмбеддингов: повторный вопрос стоит ~0. Стоимость = только амортизация железа (RTX 3050). Методика расчёта: час работы GPU / количество запросов за час, без платы за токены.

## Границы (честно)

- **Моки:** profile `mock` (детерминированная заглушка), векторный индекс на `dev` может быть ослаблен, интеграция с корп. системами имитируется.
- **Не проверено:** fallback-модель Qwen3-8B в изолированном контуре на 8 GB VRAM, Qwen3-8B на русском для декомпозиции, reranker на реальном корпусе, уложение в 3 мин видео, офлайн-бандл для изолированного контура, логика действующего документа на реальных документах задачи.
- **Не работает (из старого стенда, не переносится):** 502 на слот sonnet-5, зашитый адрес NexusLink, синтетические фикстуры, отсутствие LLM-агентов в терминалах. Прогон 32/32 PASS из прошлого отчёта — не относится к этой задаче.

**Запрещено:** production-ready, полная интеграция, любые метрики без указания набора данных. Контрольного набора от заказчика нет — метрики на собственном dev-наборе (N вопросов, ручная разметка + LLM-судья).
