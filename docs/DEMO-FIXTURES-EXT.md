# DEMO-FIXTURES-EXT — 10 фикстур для демо-видео LEX

**Статус:** pre-sprint материал. Продолжение `docs/DEMO-FIXTURES.md` (5 фикстур): здесь их
десять — по две на каждый класс из `docs/SAMPLE-QUESTIONS.md` (факт, расчёт, конфликт
редакций, отказ, аналитика журнала).

**Отличие от базовой версии:** в `DEMO-FIXTURES.md` часть фикстур была сформулирована как
схема («выручка при кросс-продаже», «[тема]», `<файл>`) — эти эталоны нельзя проверить.
Здесь у каждой фикстуры **конкретный вопрос, конкретный эталон и дословная цитата**, взятая
из `sample-corpus/` (seed `20261126`, опорная дата `2026-11-26`). Всё проверяемо: цитаты
можно найти поиском по корпусу.

**Как пользоваться:** фикстура — это не только «что ответить», но и **что должно быть на
экране**. Если в кадре агент показал не тот шаг или не сослался на `doc_id` — фикстура не
сдана, дубль переписывается (см. `docs/DEMO-SCRIPT.md` §4 «Стоп-условия»).

## F01 — факт: значение поля в конкретном документе

**Класс:** `fact` (соответствует Q02 из `SAMPLE-QUESTIONS.md`).

**Вопрос в кадре:**

> «Какой срок хранения установлен в ТЗ-ЭКЗ-0016?»

**Эталон:** `не менее одного года`

**Ожидаемый `doc_id`:** `ТЗ-ЭКЗ-0016`

**Обязательная цитата в ответе** (паспорт документа, поле «Срок хранения»):

```
| Срок хранения | не менее одного года |
```

**Что должно быть видно на экране:**

1. Ответ одной строкой: «не менее одного года».
2. Ссылка: `ТЗ-ЭКЗ-0016`, поле «Срок хранения».
3. Подсветка строки паспорта при нажатии на ссылку.

**Ловушка.** В корпусе 20 базовых документов с четырьмя разными значениями срока хранения
(2 / 7 / 3 / 8 документов соответственно). Система, которая отвечает «не менее трёх лет»
потому что это самое частое значение, — проваливает фикстуру. Ответ без `doc_id` не
засчитывается, даже если значение верное.

**Провал:** ответ верный, но без ссылки; ответ с другим значением; ответ склеен из двух
документов.

## F02 — факт: реквизит, которого нет ни в одном другом документе

**Класс:** `fact` (Q10).

**Вопрос в кадре:**

> «Какой ИНН контрагента указан в ТЗ-ЭКЗ-0006?»

**Эталон:** `77330473776`

**Ожидаемый `doc_id`:** `ТЗ-ЭКЗ-0006`

**Обязательная цитата:**

```
| ИНН контрагента (условный) | 77330473776 |
```

**Что должно быть видно:** ответ + `ТЗ-ЭКЗ-0006, паспорт, строка «ИНН контрагента
(условный)»` + подсветка.

**Зачем именно ИНН.** Это реквизит с жёстким форматом: 11 цифр, и любая правдоподобная
перестановка выглядит как настоящий ИНН. Ошибка здесь не «мелкая неточность», а выдумка.
В корпусе пять разных ИНН; ни один не выводится из другого.

**Провал:** ИНН из другого документа; ИНН, которого нет в корпусе (даже если формат
правильный); ответ «ИНН не указан», хотя поле есть.

## F03 — расчёт: подсчёт по паспортам с обязательным списком

**Класс:** `calc` (Q16).

**Вопрос в кадре:**

> «Сколько документов в корпусе имеют срок хранения «не менее двух лет»?»

**Эталон:** `3` — `ТЗ-ЭКЗ-0001`, `ТЗ-ЭКЗ-0009`, `ТЗ-ЭКЗ-0012`

**Что должно быть видно на экране:**

```
[3/7] retrieve    20 базовых документов (7 редакций правил исключены)
[4/7] aggregate   Срок хранения = «не менее двух лет» → 3 документа
                  ТЗ-ЭКЗ-0001 · ТЗ-ЭКЗ-0009 · ТЗ-ЭКЗ-0012
```

**Обязательная цитата** — по одной строке паспорта на каждый документ:

```
ТЗ-ЭКЗ-0001: | Срок хранения | не менее двух лет |
ТЗ-ЭКЗ-0009: | Срок хранения | не менее двух лет |
ТЗ-ЭКЗ-0012: | Срок хранения | не менее двух лет |
```

**Ловушка.** Ответ «3» без списка `doc_id` не проверяем — засчитывается только пара
«число + перечень». Ответ «10» (сложили «двух лет» с «трёх лет» — оба содержат слово «лет»)
— типичная ошибка грубого текстового поиска.

**Второй слой ловушки:** в корпусе 27 документов, но 7 из них — редакции правил, а не
документы подразделений. Если система считает по всем 27, она может получить завышенное
число. В кадре должно быть видно, что из выборки исключены редакции.

**Провал:** число без перечня; число с неверным перечнем; перечень длиннее или короче на
один документ.

## F04 — расчёт: группировка по подразделению

**Класс:** `calc` (Q23).

**Вопрос в кадре:**

> «Сколько документов у Отдела качества?»

**Эталон:** `4` — `ТЗ-ЭКЗ-0001`, `ТЗ-ЭКЗ-0004`, `ТЗ-ЭКЗ-0009`, `ТЗ-ЭКЗ-0012`

**Обязательные цитаты** — поле «Подразделение» четырёх паспортов:

```
ТЗ-ЭКЗ-0001: | Подразделение | Отдел качества |
ТЗ-ЭКЗ-0004: | Подразделение | Отдел качества |
ТЗ-ЭКЗ-0009: | Подразделение | Отдел качества |
ТЗ-ЭКЗ-0012: | Подразделение | Отдел качества |
```

**Ловушка.** «Отдел качества» — не единственное подразделение с похожим названием;
в корпусе есть «Отдел охраны труда», «Отдел продаж». Поиск по подстроке «Отдел» даст
завышенное число. Требуется точное совпадение значения поля.

**Вторая ловушка.** Значение поля в паспорте написано без предлога («Отдел качества»), а
в тексте документа — с предлогом («порядок работы Отдел качества компании…»). Система должна
брать поле паспорта, а не фразу из текста.

**Провал:** ответ 5+ (подмешаны другие отделы); перечень с документом из другого
подразделения.

## F05 — конфликт редакций: действующая редакция на опорную дату

**Класс:** `rule_asof` (Q27). **Главная фикстура видео.**

**Вопрос в кадре:**

> «Какой срок согласования заявки действует на 26 ноября 2026 года?»

**Эталон:** `пяти рабочих дней`

**Ожидаемый `doc_id`:** `ТЗ-ЭКЗ-СР01-Р2` (редакция 2, действует с 2026-06-01)

**Обязательная цитата:**

```
**Срок согласования заявки:** пяти рабочих дней.
```

и вторая строка, доказывающая, что применена именно Р2:

```
С 2026-06-01 применяется это значение; редакция от 2026-01-15 и ранее — не применяется.
```

**Что должно быть видно на экране (ядро видео):**

```
[4/7] resolve     найдено 3 редакции SR-01
      СР01-Р1 от 2026-01-15 → не действует на 2026-11-26 (заменена)
      СР01-Р2 от 2026-06-01 → ДЕЙСТВУЕТ
      СР01-Р3 от 2027-01-01 → не вступила в силу (будущая)
```

**Ловушка (`future-revision leakage`).** Редакция 3 вступает 2027-01-01 и уже лежит в
индексе — её значение «семи рабочих дней» является самым «свежим» в корпусе. Система,
которая ранжирует по дате документа вместо фильтра по `as_of`, ответит «семь» — и это
провал, хотя ответ выглядит правдоподобно. Именно этот кадр отличает «поиск документа» от
«определения действующей редакции».

**Провал:** «семи» (будущая редакция); «трёх» (устаревшая); оба значения через запятую
(«три или пять») — это не ответ; ответ без указания номера редакции.

## F06 — конфликт редакций: граничная дата

**Класс:** `rule_asof` (Q35).

**Вопрос в кадре:**

> «Какой порог автоматического одобрения действует на 1 августа 2026 года?»

**Эталон:** `150 000 рублей`

**Ожидаемый `doc_id`:** `ТЗ-ЭКЗ-СР03-Р2`

**Обязательная цитата:**

```
**Порог автоматического одобрения:** 150 000 рублей.
```

**Почему это отдельная фикстура.** 2026-08-01 — **день вступления** редакции 2 в силу.
Сравнение «дата вопроса > дата вступления» даёт «старая редакция» и ответ «50 000 рублей»;
правильное сравнение — «дата вопроса ≥ дата вступления». Это самая частая off-by-one
ошибка в логике дат, и на неё нет другого способа посмотреть, кроме границы.

**Что должно быть видно:**

```
[4/7] resolve     as_of 2026-08-01 ≥ 2026-08-01 → граница включительная
      СР03-Р1 от 2026-03-10 → заменена с 2026-08-01
      СР03-Р2 от 2026-08-01 → ДЕЙСТВУЕТ
```

**Провал:** «50 000 рублей»; ответ с оговоркой «возможно, действует с этого дня»; система
просит уточнить дату (дата в вопросе полная).

## F07 — отказ: правило ещё не введено

**Класс:** `refuse` (Q38). **Вторая по силе фикстура видео.**

**Вопрос в кадре:**

> «Какое значение действует для правила SR-01 на 1 декабря 2025 года?»

**Эталон:** отказ. Первая редакция SR-01 вступает 2026-01-15, до этой даты правило не
введено.

**Обязательная цитата** — доказательство, что значений до этой даты нет:

```
| Действует с | 2026-01-15 |        (ТЗ-ЭКЗ-СР01-Р1 — самая ранняя редакция)
```

**Что должно быть видно (структурированный отказ, а не текст ответа):**

```
Не могу ответить однозначно.
Причина: на 2025-12-01 ни одна редакция правила SR-01 не действует —
         самая ранняя вступает 2026-01-15.
Ближайшая действующая: СР01-Р1, вступает 2026-01-15.
Что нужно от вас: уточнить дату или правило.
```

**Главная ловушка.** Соблазн ответить «трёх рабочих дней» (значение ближайшей редакции)
велик, и такой ответ выглядит полезным. Но это подмена: на запрошенную дату правила не
существовало. Ответ с процитированным значением = провал фикстуры, даже если рядом написано
«но правило тогда не действовало».

**Провал:** любое числовое значение в ответе; отказ без причины; отказ без указания, какая
дата была бы верной.

## F08 — отказ: тема в корпусе есть, ответа нет

**Класс:** `refuse` (Q41).

**Вопрос в кадре:**

> «Каков порядок согласования заявки на закупку свыше 500 000 рублей?»

**Эталон:** отказ с объяснением, что порядок для сумм свыше 500 000 руб. в корпусе не
описан.

**Почему это сложнее F07.** Здесь нет спасительной даты. В корпусе есть три редакции
правила SR-01 («срок согласования заявки») и две редакции SR-03 («порог автоматического
одобрения» — 50 000 и 150 000 рублей). Тема «согласование заявки на закупку» покрыта
плотно. Но ни один документ не описывает **порядок** согласования для сумм свыше 500 000
рублей: SR-03 говорит про порог автоматического одобрения, а не про порядок.

**Что должно быть видно:**

```
Не могу ответить: в корпусе нет документа, описывающего этот порядок.
Что нашлось по теме: SR-01 (срок согласования заявки, 3 редакции),
                    SR-03 (порог автоматического одобрения, 2 редакции).
Почему не подходит: SR-03 задаёт порог авто-одобрения, а не порядок согласования
                    сумм свыше 500 000 руб.
Что нужно от вас: документ, описывающий порядок для крупных закупок.
```

**Ловушка.** Хорошая система обязана **показать, что искала** — иначе отказ неотличим от
«поиск не сработал». Отказ без перечня найденного по теме не засчитывается.

**Провал:** пересказ SR-03 как ответа; ответ «порог — 150 000 рублей» (это про другое);
молчаливый отказ без объяснения, почему найденные документы не подходят.

## F09 — аналитика: отказы прогона и причины

**Класс:** `journal` (Q43).

**Вопрос в кадре:**

> «Сколько отказов было в прогоне и по каким причинам?»

**Эталон:** число отказов + разбивка по причинам. В демо-прогоне отказов **как минимум
два** — F07 и F08; их причины разные:

| Причина | Фикстура | Формулировка |
|---|---|---|
| нет в корпусе | F08 | «в корпусе нет документа, описывающего этот порядок» |
| правило не введено на дату | F07 | «на 2025-12-01 ни одна редакция SR-01 не действует» |

**Что должно быть видно на экране:**

```
Отказы: 2
  · нет в корпусе ................................ 1  (F08)
  · правило не введено на запрошенную дату ....... 1  (F07)
Документы в отказах: ТЗ-ЭКЗ-СР01-Р1 (самая ранняя редакция SR-01)
```

**Обязательно:** числа совпадают с тем, что было в кадре ранее. Если в сцене 5 показан один
отказ, а аналитика говорит «3» — фикстура провалена: агрегат считается по журналу этого же
прогона, а не подставляется.

**Провал:** причина названа одна («нет в корпусе») при двух разных отказах; число не
совпадает с показанным ранее; список причин без чисел.

## F10 — аналитика: метрика, которая должна быть нулём

**Класс:** `journal` (Q48).

**Вопрос в кадре:**

> «Сколько в прогоне вопросов, где применена редакция с датой позже запрошенной?»

**Эталон:** `0`

**Почему это отдельная фикстура.** Ноль — самый информативный ответ в аналитике, потому что
он проверяемый. Система, которая «не считает» эту метрику, покажет пустое место или прочерк;
система, которая ошибается, покажет 1 (это была бы F05 с применённой редакцией 3).

**Что должно быть видно на экране:**

```
Покрытие:            ответов с полной цитатной опорой 2 из 2  (100%)
Future-revision leakage:  0  из 2 вопросов с учётом даты
Latency:             p50 1 180 мс · p95 2 340 мс
```

**Связка с кадром.** Ноль здесь — доказательство того, что сцена 3 была не постановкой:
в том же прогоне, из которого взят агрегат, будущая редакция ни разу не применилась.

**Провал:** прочерк вместо числа; «0» без знаменателя (0 из скольких?); 1 и больше;
метрика названа «конфликты» вместо «применение будущей редакции».

сцена 2 — одна из F03/F04, сцена 3 — F05 (F06 снимается как материал для жюри, если
спросят про границы), сцена 5 — F07, сцена 6 — F09 и F10. Остальные — резерв на вопросы
жюри после просмотра.

## Проверка фикстур перед съёмкой

Каждую фикстуру проверяют **на корпусе**, а не на памяти:

```bash
# цитата существует в указанном документе
grep -F "не менее одного года" "sample-corpus/ТЗ-ЭКЗ-0016-стандарт-приёмки-поступающей-партии.md"

# все 50 эталонов (включая фикстуры) сверяются машинно
python demo/gen-prep50.py --verify
```

`--verify` проверяет `fact` (значение есть в тексте документа), `calc` (число и список
пересчитаны по паспортам), `rule_asof` (редакция выбрана по `as_of` из `manifest.json`),
`refuse` (дата раньше первой редакции). Ожидаемый вывод: `проверено вопросов: 50; ошибок
нет`.

Если после брифинга корпус заказчика окажется другим (PDF/DOCX, без паспортов) — фикстуры
F01–F04 придётся переписать под реальные поля. F05–F10 опираются на логику, а не на формат,
и переносятся почти без изменений.

## Что эти фикстуры **не** доказывают (честно)

1. **Качество на реальных документах.** Все эталоны — из синтетического корпуса.
2. **Иерархию документов.** Ни одна фикстура не проверяет приоритет «приказ > политика >
   регламент»: в корпусе нет пары документов, где иерархия решает конфликт.
