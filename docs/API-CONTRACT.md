    journal.py         # журнал JSONL + агрегаты                   [ACE]

  api/                 # HTTP-слой                                    [SPARK]
    app.py             # FastAPI, роуты, SSE

  web/                 # фронтенд                                      [NEO]
    index.html
    app.js
    lex.css
    assets/

## 2. HTTP-эндпоинты

### `GET /api/health`
```json
{"status":"ok","version":"1.0.0",
 "llm":{"slot":"claude-sonnet-5","base":"…","reachable":true},
 "embed":{"model":"bge-m3","dim":1024,"reachable":true},
 "rerank":{"model":"bge-reranker-base","reachable":true},
 "corpus":{"documents":27,"chunks":412}}
```
`reachable` — результат живой проверки, не константа.

### `GET /api/roles`
```json
[{"id":"lawyer","title":"Юридический отдел","departments":["Юридический отдел"],"systems":[]},
 {"id":"quality","title":"Отдел качества","departments":["Отдел качества"],"systems":[]},
 {"id":"it","title":"ИТ-служба","departments":["ИТ-служба"],"systems":[]},
 {"id":"director","title":"Руководитель","departments":["*"],"systems":["*"]}]
```
`*` = все. Отделы берутся из `manifest.json → documents[].department`.

### `POST /api/ask` → `text/event-stream`
Запрос:
```json
{"question":"Какой срок согласования заявки на закупку?",
 "role_id":"lawyer",
 "as_of":"2026-03-01"}
```
- `as_of` — необязательная дата (YYYY-MM-DD). Если задана — действует редакция,
  вступившая в силу не позже неё. Если раньше первой редакции — обоснованный отказ.
- `role_id` — обязателен (права доступа обязательны по брифу).

### `GET /api/journal?limit=50&role_id=`
```json
[{"id":"q-001","ts":"2026-11-26T10:31:02Z","role_id":"lawyer",
  "question":"…","refused":false,"elapsed_ms":3410,"steps":[{"key":"retrieve","ms":210}],
  "doc_ids":["ТЗ-ЭКЗ-СР01-Р2"],"inference_path":"nexus-link"}]
```

### `GET /api/analytics`
```json
{"total":42,"refusals":7,"refusal_rate":0.167,"avg_latency_ms":3800,"p95_latency_ms":9100,
 "top_missing":[{"topic":"лицензирование продукта X","count":4}],
 "top_sources":[{"doc_id":"ТЗ-ЭКЗ-СР01-Р2","count":12}],
 "by_role":[{"role_id":"lawyer","count":20}],
 "unanswered":[{"question":"…","ts":"…"}]}
```
`top_missing` — из отказов и пустых выдач. Это критерий «Соответствие задаче партнёра».

### `POST /api/ingest`
```json
{"ok":true,"documents":28,"chunks":430,"added":["ТЗ-ЭКЗ-0031"]}
```
Перечитывает `sample-corpus/` и перестраивает индекс. Для живого показа
«положили документ — ответ изменился».

## 3. События SSE

Порядок фиксирован. Каждый `step` — отдельная запись; UI рисует строку в Console Lex.

| # | `key` | Заголовок в UI | Что в `detail` |
|---|---|---|---|
| 1 | `accept` | Запрос принят | роль, дата отсчёта |
| 2 | `decompose` | Разбор вопроса | «N подвопросов» и сами подвопросы |
| 3 | `retrieve` | Поиск | «BM25 N · вектор M → топ K» |
| 4 | `permissions` | Проверка прав | «доступно X из Y, отброшено Z» |
| 5 | `resolve` | Действующая редакция | «N редакций, действует Р2 от 2026-06-01» |
| 6 | `conflict` | Сопоставление | «конфликтов: N» / «приказ сильнее регламента» |
| 7 | `compose` | Сборка ответа | «из K цитат» |
| 8 | `verify` | Самопроверка | «покрыто N из N утверждений» |

```json
event: step
data: {"n":3,"total":8,"key":"retrieve","title":"Поиск",
       "detail":"BM25 12 · вектор 10 → топ 5","ms":210,"color":"cyan"}
```

Цвета (UI мапит сам): `accept`—`slate`, `decompose`—`violet`, `retrieve`—`cyan`,
`permissions`—`amber`, `resolve`—`blue`, `conflict`—`rose`, `compose`—`emerald`,
`verify`—`green`.

### Завершение — ровно одно из двух

```json
event: answer
data: {"text":"Пять рабочих дней (Правило SR-01).",
       "citations":[{"doc_id":"ТЗ-ЭКЗ-СР01-Р2","title":"…","revision":2,
                     "effective":"2026-06-01","quote":"Срок согласования заявки: пяти рабочих дней."}],
       "refused":false}
```
```json
event: refusal
data: {"reason":"На 2025-12-01 ни одна редакция правила SR-01 не действует",
       "sources":["ТЗ-ЭКЗ-СР01-Р1"],"kind":"no_edition_in_force"}
```
`kind`: `no_edition_in_force` | `no_access` | `not_in_corpus` | `conflict_unresolved`.

Затем всегда:
```json
event: done
data: {"elapsed_ms":3410,"inference_path":"nexus-link","journal_id":"q-001"}
```

Ошибка:
```json
event: error
data: {"message":"…","stage":"retrieve"}
```

## 4. Роли и права (обязательны по брифу)

`src/lex/access.py`:
- роль = список отделов + список систем; `*` — все;
- документ доступен, если `doc.department ∈ role.departments` **или** `role.departments` содержит `*`;
- если после фильтра по вопросу не осталось доступных документов, **но** они есть
  без фильтра — это `refusal.kind = "no_access"`, а не «не найдено». Разница
  видна в Console и в аналитике.
- `permissions` считает и отдаёт в `detail`: сколько отброшено.

## 5. Модель

NexusLink на sage-pl, слот `NEXUS_LINK_MODEL` (сейчас `claude-sonnet-5`).
Переменные — из `.env` (не в коде!): `NEXUSLINK_KEY`, `NEXUS_LINK_BASE_URL`,
`NEXUS_LINK_MODEL`. Эндпоинт `POST /v1/chat/completions`, `max_tokens ≥ 1024`
(иначе ответ приходит только блоком `thinking`).

Эмбеддинги — `POST http://127.0.0.1:8081/v1/embeddings` (bge-m3, dim 1024).
Реранк — `POST http://127.0.0.1:8082/rerank` (`{query, documents}`).

Оба локальны — это аргумент к критерию «Экономика эксплуатации».

## 8. Кейсы — пополняемая база реальных случаев (v1.1)

**Зачем (задача от владельца):** агент должен пополнять свою базу реальными
кейсами от ролей руководителей, чтобы в будущем они выводились. Основа —
регламенты по работе с заказчиками.

Кейс — это **не документ корпуса**. Документ нормативен и статичен. Кейс —
наблюдение из практики: что спросили, что ответили, что произошло. Кейсы живут
рядом с регламентами и **участвуют в поиске наравне**, но помечены источником
`kind: "case"` и имеют приоритет **ниже** любого нормативного документа при
конфликте.

### Модель кейса

```json
{"id":"case-0007","ts":"2026-11-26T10:44:00Z",
 "author_role":"director","author_name":"—",
 "question":"Клиент просит согласовать закупку за 2 дня вместо 5. Что делать?",
 "answer_in_practice":"Согласовали через директора, оформили отступление письмом.",
 "outcome":"resolved",
 "linked_docs":["ТЗ-ЭКЗ-СР01-Р2"],
 "tags":["срок","согласование","исключение"],
 "rule_key":"SR-01",
 "content_type":"text"}
```

`outcome`: `resolved` | `escalated` | `rejected` | `open`.
`content_type` — тот же набор, что у документов (§9).

### Эндпоинты

`POST /api/cases` — добавить кейс.
```json
{"question":"…","answer_in_practice":"…","outcome":"resolved",
 "author_role":"director","linked_docs":["ТЗ-ЭКЗ-СР01-Р2"],"tags":["срок"]}
```
Ответ: `{"id":"case-0007","ok":true,"in_index":true}` — кейс сразу попадает в
поиск, без переиндексации всего корпуса.

`GET /api/cases?limit=&role_id=&tag=&rule_key=` — список.

### Как кейсы влияют на ответ

1. Поиск идёт по документам **и** кейсам одновременно.
2. Кейсы не могут отменить регламент. Если кейс противоречит действующей
   редакции — в ответе это явно: «по регламенту 5 дней, в практике был случай
   согласования за 2 дня (кейс case-0007)».
3. Если регламент ответа не даёт, а кейс даёт — ответ строится на кейсе с
   пометкой «по практике, регламент не покрывает».
4. В шаг `retrieve` добавляется счётчик: «документов N, кейсов M».

### Новый шаг в SSE — `cases`

После `retrieve`, перед `permissions`:

| # | `key` | Заголовок | `detail` |
|---|---|---|---|
| 3a | `cases` | Поиск по кейсам | «найдено M кейсов, из них по теме K» |

Цвет: `teal`. Полный порядок становится:

```
accept → decompose → retrieve → cases → permissions → resolve → conflict → compose → verify
```

`total` в каждом событии = **9**.

## 9. Мультимодальный корпус (v1.1)

**Задача от владельца:** БД будет иметь разную форму — текст, картинки, сканы
документов. Агент должен уметь различать их.

### Тип содержимого

У каждого элемента корпуса (документ или кейс) есть `content_type`:

| `content_type` | Что это | Как обрабатываем | Что в ответе |
|---|---|---|---|
| `text` | Готовый текст (md/txt/docx с текстовым слоем) | чанкинг → BM25 + эмбеддинги | обычная цитата |
| `image` | Картинка со смыслом (схема, скриншот, таблица-картинка) | OCR → текст + описание; сама картинка доступна по URL | цитата + превью |
| `scan` | Скан документа без текстового слоя | OCR; если OCR дал < 100 символов — помечаем `ocr_degraded` | цитата + предупреждение |
| `mixed` | PDF/документ со страницами разного типа | постранично: текст + OCR страниц-картинок | цитата с номером страницы |

### Различение — обязательный шаг

Агент **обязан** определить тип и сказать это в консоли. Новый шаг перед
`retrieve`:

| # | `key` | Заголовок | `detail` |
|---|---|---|---|
| 2a | `inspect` | Разбор источников | «текст N · картинки M · сканы K · смешанные J» |

Цвет: `indigo`.

Если в корпусе есть сканы с плохим OCR — в шаге `inspect` это видно:
«сканы 3 (1 с плохим распознаванием)».

### Ответ по нетекстовому источнику

`citations[]` расширяется:
```json
{"doc_id":"ТЗ-ЭКЗ-0042","title":"Схема процесса согласования",
 "content_type":"image","page":1,
 "quote":"…распознанный текст…",
 "preview_url":"/api/doc/ТЗ-ЭКЗ-0042/preview?page=1",
 "ocr_confidence":0.82}
```

При `ocr_confidence < 0.6` в ответе обязательна пометка: «источник распознан
неуверенно, сверьте с оригиналом» — и это же уходит в `refusal`-логику, если
утверждение держится только на таком фрагменте.

### Эндпоинт

`GET /api/doc/{doc_id}/preview?page=N` — отдаёт изображение страницы или саму
картинку. Нужен, чтобы в UI цитата была кликабельной: «показать источник».

### Честное ограничение

OCR на старте — **уже готовый движок, не обучаемый нами**. Если его нет в
окружении, сканы помечаются `ocr_unavailable` и в `inspect` пишется честно:
«сканы не обрабатываются». Не выдавать за поддержку того, чего нет.

## 10. Диалог с уточнением параметров (v1.2)

**Задача от владельца:** агент должен уметь вести диалог с сотрудником, уточнять
у него необходимые параметры задачи.

Сейчас `/api/ask` отвечает на один вопрос и забывает его. Так нельзя: половина
реальных вопросов неполна — «какой срок согласования?» без указания даты,
подразделения и предмета закупки. Агент обязан **спросить, а не догадываться**.

### Свойства, которые нельзя терять

1. **Уточнение — это не отказ.** Вопрос осмысленный, просто неполный. Ответ
   `clarification`, а не `refusal`.
2. **Не больше 3 вопросов за раз.** Сотрудник не проходит допрос.
3. **Каждый уточняющий вопрос — обоснован.** Агент говорит, *почему* спрашивает:
   «не могу определить действующую редакцию без даты».
4. **Уточнение можно пропустить.** Если сотрудник отвечает «не знаю» — агент идёт
   по разумному умолчанию и **явно говорит**, какое умолчание применил.
5. **Диалог имеет состояние.** `session_id` в запросе и ответе.

### Запрос

`POST /api/ask` дополняется полем `session_id` (необязательным):

```json
{"question":"Какой срок согласования заявки?",
 "role_id":"lawyer","session_id":"s-7f3a1c"}
```

Первый запрос — без `session_id`, сервер создаёт сессию.

### Новое событие — `clarify`

Вместо `answer`/`refusal` может прийти:

```json
event: clarify
data: {"session_id":"s-7f3a1c",
       "questions":[{"key":"as_of","text":"На какую дату определить действующую редакцию?","reason":"в корпусе три редакции правила SR-01, без даты нельзя выбрать","kind":"date"},
                    {"key":"amount","text":"Сумма заявки больше 500 000 рублей?","reason":"от суммы зависит порядок согласования","kind":"choice","options":["до 500 000","свыше 500 000","не знаю"]}],
       "partial":{"retrieved":12,"accessible":5},
       "can_skip":true}
```

`kind`: `date` | `choice` | `text` | `doc_id`.
`can_skip` — если `true`, UI показывает «Пропустить, выбери сам».

После `clarify` поток **закрывается** (не приходит `done`). Следующий запрос
несёт `session_id` и `answers`:

```json
{"question":"Какой срок согласования заявки?","role_id":"lawyer",
 "session_id":"s-7f3a1c",
 "answers":{"as_of":"2026-07-01","amount":"свыше 500 000"}}
```

Значение `"не знаю"` или отсутствие ключа = «пропустить».

### Ограничения

- Максимум **2 уточняющих круга** на сессию. Третий — либо ответ с явными
  умолчаниями, либо отказ. Защита от бесконечного диалога.
- Сессия живёт 30 минут без активности.
- Каждый пропущенный параметр и умолчание пишутся в `answer.assumptions`.

### В ответе — что предположили

```json
event: answer
data: {…, "assumptions":[{"key":"as_of","value":"2026-11-26","note":"дата не указана — считаю сегодняшней"}]}
```

### В SSE-потоке это отдельный шаг

Шаг `clarify` идёт **вместо** `decompose`, когда нужны уточнения. Console Lex
показывает его тем же механизмом, но с цветом `sky` и иконкой вопроса:

```
[2/9] Уточнение   Нужна дата: в корпусе три редакции SR-01
```

### Что показывает UI

Левая колонка (чат): вопрос агента с полем ввода/выбора прямо в ленте.
Правая колонка (консоль): видно, какие параметры уже известны, какие
запрошены, какие пропущены с умолчанием.

**Почему это важно для оценки:** критерий «Агентность» — 0 баллов за один
запрос, 3 за автономного агента. Уточняющий диалог — прямое доказательство,
что это не «вопрос → ответ», а цикл. Плюс это то, чего не будет у большинства
конкурентов.

## 11. Бизнес-направления (v1.3)

**Задача от владельца:** регламенты для разных бизнес-направлений разные. Агент
должен уметь различить бизнес-направление сотрудника и его задачи.

### Зачем это отдельно от `department`

`department` (отдел) — организационная единица. Бизнес-направление — предметная
область работы: у одного отдела может быть несколько направлений, одно
направление может затрагивать несколько отделов. Регламенты привязаны к
**направлению**, не только к отделу.

### Модель

Документ и кейс получают поле `business_line` (обязательное для новых данных):

```json
{"doc_id":"ТЗ-ЭКЗ-СР01-Р2","business_line":"закупки","department":"Юридический отдел"}
```

Список направлений — из данных, не из кода:
`GET /api/business-lines` → `[{"id":"закупки","title":"Закупки","docs":12},
{"id":"лицензирование","title":"Лицензирование","docs":5}, …]`

### Как агент различает

1. **От роли.** Роль сотрудника несёт `default_lines[]` — направления, в которых
   он обычно работает. Это фильтр по умолчанию, не жёсткий.
2. **От вопроса.** Вопрос упоминает предмет: «лицензия на продукт X» → направление
   `лицензирование`. Определяется на шаге `decompose` по синонимам
   (`docs/db/ARTICLES-DRAFT.md` — статьи как раз для этого).
3. **От уточнения.** Если ни роль, ни вопрос не дают однозначности — спросить
   (связка с §10): `{"key":"business_line","kind":"choice","text":"О каком направлении речь?","options":["Закупки","Лицензирование","…"]}`.
4. **На пересечении.** Вопрос может затрагивать два направления — тогда поиск
   идёт по обоим, а в ответе явно: «ответ по направлению X; по Y — другой
   документ».

### Права: И роли, И направления

Документ доступен, если **оба** условия:
- `doc.department ∈ role.departments` (или `*`);
- `doc.business_line ∈ role.business_lines` (или `*`).

Иначе — `refusal.kind = "no_access"` с указанием, по какому признаку закрыт.

### В SSE

Шаг `decompose` теперь сообщает определённое направление:

```
[2/9] Разбор вопроса   направление: закупки · 2 подвопроса
```

Если направление не определено — шаг `clarify` (см. §10), а не догадка.
`inspect` показывает срез: «текст N · картинки M · сканы K · направлений L».

### В аналитике (`GET /api/analytics`)

```json
"by_business_line":[{"line":"закупки","count":18,"refusals":2},
                    {"line":"лицензирование","count":7,"refusals":5}],
"missing_by_line":[{"line":"лицензирование","count":5,"note":"чаще всего нет документа"}]
```

Это прямо бьёт в критерий «Соответствие задаче партнёра»: видно, где регламентов
не хватает — по направлениям, а не «вообще».

### Что делать с нашим корпусом

В `sample-corpus/manifest.json` поля `business_line` сейчас **нет**. Добавить:
- у ARCH в `schema/source-schema.md` — обязательное поле в целевой модели;
- в генератор `demo/gen-sample-corpus.py` — вывести направление из `system`
  и типа документа (закупки / лицензирование / качество / хранение / персонал);
- до появления поля — считать `business_line = "общее"` и не блокировать.

## 12. Только из базы знаний (v1.4) — ГЛАВНОЕ ПРАВИЛО

**Задача от владельца (дословно):** «Нельзя чтобы ИИ-агент брал знания вне базы
данных. Агент должен заботиться о конфиденциальности данных заказчика. Агент не
должен придумывать ответы, полученные вне базы знаний организации.»

Это не рекомендация. Это **ограничение верхнего уровня**, которое важнее
красоты ответа и важнее полноты.

### 12.1. Правило

Каждое утверждение в ответе обязано иметь **цитату из элемента базы знаний**
(документ или кейс). Нет цитаты — нет утверждения. Модель не имеет права
дополнять ответ общими знаниями, даже если они верны.

**Пример нарушения:** «Срок согласования обычно составляет 5 рабочих дней, как
принято в практике закупок» — «как принято в практике» источником не является.

**Правильный ответ:** «Срок согласования — пять рабочих дней (ТЗ-ЭКЗ-СР01-Р2,
редакция 2 от 2026-06-01, раздел «Порядок выполнения процедуры»).»

### 12.2. Как это обеспечивается технически (три барьера)

**Барьер 1 — промпт.** Модели явно запрещено использовать знания вне
переданного контекста. Контекст — только фрагменты из базы. Формулировка
в системном сообщении (`src/lex/llm.py`):

> Ты отвечаешь ТОЛЬКО на основе фрагментов, переданных ниже. Если фрагменты не
> содержат ответа — верни отказ, а не общие знания. Не используй сведения, которых
> нет во фрагментах, даже если ты их знаешь. Каждое утверждение сопровождай
> номером фрагмента в квадратных скобках.

**Барьер 2 — проверка покрытия (шаг `verify`).** После генерации каждое
утверждение сверяется с цитатами:
- утверждение без опоры на фрагмент → **ответ не выдаётся**;
- проверка программная, не «на глаз модели»: ответ разбивается на предложения,
  каждое должно нести ссылку `[n]` на существующий фрагмент, и `n` должен
  действительно содержать смысл утверждения (эмбеддинг-близость предложения к
  цитируемому фрагменту, порог в конфиге).

**Барьер 3 — финальный фильтр.** Если после барьера 2 остаётся хоть одно
непокрытое утверждение — ответ **усекается** до покрытых частей; если покрытых
нет — `refusal.kind = "not_in_corpus"`.

### 12.3. Отказ — это правильный ответ

Если в базе знаний ответа нет, агент **обязан** отказаться. Это не сбой, а
выполнение требования:

```json
event: refusal
data: {"reason":"В базе знаний нет документа, регулирующего этот вопрос",
       "kind":"not_in_corpus",
       "searched":{"documents":27,"cases":4,"business_lines":["закупки"]},
       "hint":"Уточните направление или обратитесь к владельцу регламента"}
```

Отказ **всегда** говорит, что искали: сколько документов, кейсов, по каким
направлениям. Пустое «не знаю» — плохой отказ.

### 12.4. Конфиденциальность

1. **В промпт уходит только необходимое.** Не весь документ, а найденные
   фрагменты (топ-K после реранка). Не «на всякий случай весь корпус».
2. **Журнал не хранит содержимое документов.** Только идентификаторы, шаги,
   время. Цитаты — в ответе пользователю, но не в `journal.jsonl` (там `doc_ids`,
   не `quotes`).
3. **Права проверяются ДО генерации.** Недопустимый для роли документ не попадает
   в промпт вообще — не «попадает, но не показывается». Иначе конфиденциальные
   данные уходят в модель.
4. **Никаких «полезных» дополнений.** На вопрос «а как обычно делают в других
   компаниях?» агент отвечает: «База знаний организации этот вопрос не покрывает».

### 12.5. Что меняется в событиях

Шаг `verify` несёт результат проверки покрытия:

```json
event: step
data: {"n":9,"total":9,"key":"verify","title":"Самопроверка",
       "detail":"утверждений 4 · покрыто цитатами 4 · внешних знаний 0","ms":120,"color":"green"}
```

Если барьер сработал и ответ усечён:
`"detail":"утверждений 5 · покрыто 3 · 2 отброшено (нет цитаты)"` — цвет `amber`.

### 12.6. Демонстрационный кейс для жюри (обязателен)

Нужен вопрос, на который модель **знает** ответ из общих знаний, но в базе его
**нет**. Агент обязан отказаться. Пример: «Какая ставка НДС в России?» — модель
это знает, в корпусе этого нет, правильное поведение — отказ.

Этот кейс показывается в демо и в видео. Он доказывает главное: агент не
галлюцинирует, а работает по базе.

### 12.7. Честное ограничение

Барьер 2 — эвристика на эмбеддинг-близости, а не формальное доказательство. Она
ловит большинство случаев «придумал», но не все. Записывается в `docs/LIMITS.md`;
не выдавать за гарантию.

## 13. Формат ответа и работа с документами (v1.5)

**Задача от владельца (дословно):** «Формат ответа агента: точная и краткая
выжимка информации — далее в диалоге он может узнать подробности уже развёрнуто,
ссылки на документы, по которому он может перейти и прочитать, скачать
необходимую форму документа, агент должен помочь ему с запоминанием форм тех или
иных документов и проверить, чтобы все данные совпадали.»

Четыре отдельные возможности. Все четыре обязательны.

### 13.1. Кратко по умолчанию, развёрнуто по запросу

**Первый ответ — выжимка. Не пересказ документа.** Правило: 2–4 предложения,
не больше 400 знаков. Сотрудник за 5 секунд понимает ответ и решает, нужны ли
подробности.

```json
event: answer
data: {"short":"Пять рабочих дней (ТЗ-ЭКЗ-СР01-Р2, ред. 2).",
       "has_details":true,
       "detail_id":"d-q0001",
       "citations":[…]}
```

**Развёрнутая версия — по отдельному запросу**, не сразу:

`POST /api/expand` → `{"detail_id":"d-q0001","section":"all"}`

```json
{"short":"…",
 "detailed":"Согласно редакции 2 регламента согласования заявок, вступившей
             в силу 1 июня 2026 года, срок согласования заявки на закупку
             составляет пять рабочих дней. Срок отсчитывается с момента
             регистрации заявки. Редакция 1 (2026-01-15) устанавливала три
             рабочих дня, редакция 3 (вступает 2027-01-01) — семь. …",
 "sections":[{"title":"Порядок выполнения","quote":"…"},
             {"title":"Исключения","quote":"…"}],
 "tables":[{"caption":"Сроки по редакциям","rows":[["Ред.","Дата","Срок"],["Р1","2026-01-15","3"],…]}],
 "citations":[…]}
```

`section` — можно запросить конкретный раздел: `"exceptions"`, `"procedure"`,
`"roles"`. В диалоге это естественный следующий шаг: «А какие исключения?»

**Правило:** развёрнутая версия строится из **тех же** фрагментов, что и краткая.
Она не добавляет новых знаний — только раскрывает цитаты полнее. Барьер §12
действует на обе.

### 13.2. Ссылки на документы — перейти и прочитать

Каждая цитата несёт ссылку на документ целиком:

```json
"citations":[{"doc_id":"ТЗ-ЭКЗ-СР01-Р2","title":"Регламент согласования заявки на закупку",
  "revision":2,"effective":"2026-06-01","business_line":"закупки",
  "quote":"Срок согласования заявки: пяти рабочих дней.",
  "view_url":"/api/doc/ТЗ-ЭКЗ-СР01-Р2",
  "download_url":"/api/doc/ТЗ-ЭКЗ-СР01-Р2/download",
  "anchor":"#razdel-poryadok"}]
```

Новые эндпоинты:

| Метод | Путь | Что отдаёт |
|---|---|---|
| `GET` | `/api/doc/{doc_id}` | документ целиком, HTML с оглавлением |
| `GET` | `/api/doc/{doc_id}/download` | исходный файл (md/docx/pdf) с `Content-Disposition: attachment` |
| `GET` | `/api/doc/{doc_id}/preview?page=N` | страница как изображение (для сканов) |

**Права проверяются и здесь.** Документ вне области роли — 403 с причиной,
не 404: сотрудник должен знать, что документ существует, но ему не положен.

### 13.3. Скачивание формы документа

Отдельно от скачивания документа — **скачивание формы**, то есть бланка для
заполнения. У части документов есть приложение-форма (заявка, акт, чек-лист).

`GET /api/forms` → список доступных форм:
```json
[{"form_id":"form-zayavka","title":"Заявка на закупку","doc_id":"ТЗ-ЭКЗ-СР01-Р2",
  "fields":7,"format":"docx","business_line":"закупки"}]
```

`GET /api/forms/{form_id}/download` → файл бланка.

`GET /api/forms/{form_id}` → описание полей:
```json
{"form_id":"form-zayavka","title":"Заявка на закупку",
 "fields":[
  {"key":"number","label":"Номер заявки","type":"text","required":true,
   "pattern":"^ЗК-\\d{4}-\\d{4}$","example":"ЗК-2026-0042",
   "hint":"формат ЗК-ГГГГ-НННН"},
  {"key":"amount","label":"Сумма","type":"money","required":true,"min":0},
  {"key":"deadline","label":"Требуемый срок","type":"date","required":true},
  {"key":"department","label":"Подразделение","type":"choice","required":true,
   "options":["Отдел качества","Юридический отдел",…]}
 ]}
```

### 13.4. Помощь с заполнением и проверка данных

**Агент запоминает форму** и ведёт сотрудника по полям. Состояние — в сессии
(связка с §10).

`POST /api/forms/{form_id}/fill`
```json
{"session_id":"s-7f3a1c",
 "values":{"number":"ЗК-2026-42","amount":"450 000","department":"Отдел качества"}}
```
```json
{"ok":false,
 "errors":[{"field":"number","value":"ЗК-2026-42","message":"номер не соответствует формату ЗК-ГГГГ-НННН","expected":"ЗК-2026-0042"},
           {"field":"deadline","message":"поле обязательное","expected":"дата в формате ГГГГ-ММ-ДД"}],
 "warnings":[{"field":"amount","message":"сумма близка к порогу 500 000 — согласование пойдёт по другому порядку","doc_id":"ТЗ-ЭКЗ-СР01-Р3"}],
 "filled":{"number":"ЗК-2026-42","amount":450000,"department":"Отдел качества","deadline":null},
 "missing":["deadline"],
 "progress":"3 из 4 полей"}
```

Типы проверок (все обязательны):

1. **Обязательность** — пустое обязательное поле.
2. **Формат** — по `pattern`/типу: номер, дата, сумма, ИНН.
3. **Значения из справочника** — подразделение должно быть из списка.
4. **Согласованность с регламентом** — это самое ценное: если сумма выше порога
   из другого документа, агент предупреждает и **ссылается на документ**.
   Не блокирует, а предупреждает с обоснованием.
5. **Полнота** — чего не хватает, чтобы форма считалась заполненной.

**Правило §12 здесь работает жёстко:** если агент не может обосновать
требование формата цитатой из базы — он **не выдумывает** формат. В таком поле
`"hint":"формат не описан в регламенте — уточните у владельца формы"`.

### 13.5. Что видит сотрудник (UI)

**Левая колонка:**

1. Вопрос → **краткая выжимка** (крупно, 2–4 строки).
2. Под ней две кнопки: «Подробнее» и «Открыть документ».
3. «Подробнее» раскрывает развёрнутый ответ с разделами, цитатами и таблицами —
   прямо в ленте, без перехода.
4. У каждой цитаты: номер `[1]`, документ, редакция, дата, бейдж типа
   (текст/картинка/скан), ссылки «Читать» и «Скачать».
5. Если в ответе есть форма — карточка: «Есть форма: Заявка на закупку» с
   кнопками «Скачать бланк» и «Заполнить здесь».

**Правая колонка (консоль)** — новые шаги для формы:
```
[8/9] Сборка ответа      краткая выжимка · 3 цитаты · есть форма
[9/9] Самопроверка       утверждений 3 · покрыто 3 · внешних знаний 0
```

При заполнении формы консоль показывает проверки построчно — это красиво и
доказывает, что агент реально сверяет, а не «говорит, что сверяет».

### 13.6. Чего не делать

- Не выдавать краткую выжимку за полный ответ. Если это выжимка — так и названо.
- Не давать «Подробнее» для отказа: отказ уже полный, раскрывать нечего.
- Не проверять форму «на глаз модели» — только по правилам из §13.4, с цитатами.
- Не подставлять значения, которых сотрудник не вводил. Пустое поле остаётся
  пустым, а не «разумным умолчанием» (умолчания допустимы только в ответах на
  вопросы, не в формах).

## 14. Telegram-бот (v1.6) — задел, не реализация

**Задача от владельца:** «Агент должен будет связан с ботом в телеграм (это
сделаем позже) пока просто зафиксируй в документах.»

**Статус: НЕ реализуется в спринте.** Этот раздел фиксирует архитектурное
требование, чтобы сегодняшние решения его не заблокировали.

### 14.1. Почему это дёшево сделать позже

Ядро (`src/lex`) не знает про HTTP. Это правило из §1 не случайно: оно же
делает возможным второй транспорт. Бот — это ещё один потребитель того же
оркестратора, как HTTP-слой.

```
        ┌──────────────┐
        │   src/lex    │  ядро: 9 шагов, никакого HTTP
        └──────┬───────┘
      ┌────────┴────────┐
      │                 │
┌─────▼─────┐    ┌──────▼──────┐
│  src/api  │    │  src/bot    │   ← появится позже
│  (сейчас) │    │ (Telegram)  │
└───────────┘    └─────────────┘
```

**Что это требует уже сегодня:** ничего дополнительно, кроме соблюдения
правила «ядро не знает про транспорт». Если код ядра начнёт возвращать
`JSONResponse` или SSE-строки — бот станет дорогим.

### 14.2. Что нужно будет при подключении

| Что | Откуда |
|---|---|
| Токен бота | `BOT_TOKEN` в `.env`, не в коде |
| Привязка пользователя Telegram к роли | `telegram_user_id → role_id`, таблица в конфиге |
| Транспорт | long polling (проще) или webhook (быстрее) |
| Что переиспользуется | `session_id` из §10 — диалог живёт в тех же сессиях |

### 14.3. Что нельзя сломать сейчас

1. **Сессии — по `session_id`, а не по HTTP-соединению.** Иначе в Telegram
   каждый запрос будет новой сессией, и диалог с уточнением не заработает.
2. **Права — по `role_id`, а не по чему-то, что живёт в запросе.** В боте роль
   придёт из привязки Telegram-пользователя, и `access.py` должен её принять
   как обычный параметр.
3. **Короткий ответ отдельно от развёрнутого** (§13.1) — в Telegram длинные
   сообщения режутся, и краткость там не опция, а необходимость. Архитектура
   уже правильная.
4. **Формы, которые не влезают в мессенджер**, — в боте будет ссылка на
   веб-форму, а не попытка отрисовать поля в чате.

### 14.4. Чего в боте не будет

- Полноценного UI-консоли (9 шагов) — только компактная сводка шагов под ответом.
- Просмотра документов — только ссылки.
- Заполнения форм — только ссылка на веб-форму.

**В документации фиксируется как «второй транспорт, планируется».**
В `docs/LIMITS.md` — в раздел «не реализовано». Не упоминать в питче как
готовое.
