## 2. HTTP-эндпоинты

### `GET /api/health`
```json
{"status":"ok","version":"1.0.0",
 "llm":{"slot":"claude-sonnet-5","base":"…","reachable":true},
 "embed":{"model":"bge-m3","dim":1024,"reachable":true},
 "rerank":{"model":"bge-reranker-base","reachable":true},
 "corpus":{"documents":27,"chunks":412}}
```
`reachable` — результат живой проверки, не константа.

### `GET /api/roles`
```json
[{"id":"lawyer","title":"Юридический отдел","departments":["Юридический отдел"],"systems":[]},
 {"id":"quality","title":"Отдел качества","departments":["Отдел качества"],"systems":[]},
 {"id":"it","title":"ИТ-служба","departments":["ИТ-служба"],"systems":[]},
 {"id":"director","title":"Руководитель","departments":["*"],"systems":["*"]}]
```
`*` = все. Отделы берутся из `manifest.json → documents[].department`.

### `POST /api/ask` → `text/event-stream`
Запрос:
```json
{"question":"Какой срок согласования заявки на закупку?",
 "role_id":"lawyer",
 "as_of":"2026-03-01"}
```
- `as_of` — необязательная дата (YYYY-MM-DD). Если задана — действует редакция,
  вступившая в силу не позже неё. Если раньше первой редакции — обоснованный отказ.
- `role_id` — обязателен (права доступа обязательны по брифу).

### `GET /api/journal?limit=50&role_id=`
```json
[{"id":"q-001","ts":"2026-11-26T10:31:02Z","role_id":"lawyer",
  "question":"…","refused":false,"elapsed_ms":3410,"steps":[{"key":"retrieve","ms":210}],
  "doc_ids":["ТЗ-ЭКЗ-СР01-Р2"],"inference_path":"nexus-link"}]
```

### `GET /api/analytics`
```json
{"total":42,"refusals":7,"refusal_rate":0.167,"avg_latency_ms":3800,"p95_latency_ms":9100,
 "top_missing":[{"topic":"лицензирование продукта X","count":4}],
 "top_sources":[{"doc_id":"ТЗ-ЭКЗ-СР01-Р2","count":12}],
 "by_role":[{"role_id":"lawyer","count":20}],
 "unanswered":[{"question":"…","ts":"…"}]}
```
`top_missing` — из отказов и пустых выдач. Это критерий «Соответствие задаче партнёра».

### `POST /api/ingest`
```json
{"ok":true,"documents":28,"chunks":430,"added":["ТЗ-ЭКЗ-0031"]}
```
Перечитывает `sample-corpus/` и перестраивает индекс. Для живого показа
«положили документ — ответ изменился».

## 3. События SSE

Порядок фиксирован. Каждый `step` — отдельная запись; UI рисует строку в Console Lex.

| # | `key` | Заголовок в UI | Что в `detail` |
|---|---|---|---|
| 1 | `accept` | Запрос принят | роль, дата отсчёта |
| 2 | `decompose` | Разбор вопроса | «N подвопросов» и сами подвопросы |
| 3 | `retrieve` | Поиск | «BM25 N · вектор M → топ K» |
| 4 | `permissions` | Проверка прав | «доступно X из Y, отброшено Z» |
| 5 | `resolve` | Действующая редакция | «N редакций, действует Р2 от 2026-06-01» |
| 6 | `conflict` | Сопоставление | «конфликтов: N» / «приказ сильнее регламента» |
| 7 | `compose` | Сборка ответа | «из K цитат» |
| 8 | `verify` | Самопроверка | «покрыто N из N утверждений» |

```json
event: step
data: {"n":3,"total":8,"key":"retrieve","title":"Поиск",
       "detail":"BM25 12 · вектор 10 → топ 5","ms":210,"color":"cyan"}
```

Цвета (UI мапит сам): `accept`—`slate`, `decompose`—`violet`, `retrieve`—`cyan`,
`permissions`—`amber`, `resolve`—`blue`, `conflict`—`rose`, `compose`—`emerald`,
`verify`—`green`.

### Завершение — ровно одно из двух

```json
event: answer
data: {"text":"Пять рабочих дней (Правило SR-01).",
       "citations":[{"doc_id":"ТЗ-ЭКЗ-СР01-Р2","title":"…","revision":2,
                     "effective":"2026-06-01","quote":"Срок согласования заявки: пяти рабочих дней."}],
       "refused":false}
```
```json
event: refusal
data: {"reason":"На 2025-12-01 ни одна редакция правила SR-01 не действует",
       "sources":["ТЗ-ЭКЗ-СР01-Р1"],"kind":"no_edition_in_force"}
```
`kind`: `out_of_scope` | `no_edition_in_force` | `not_in_corpus` | `conflict_unresolved` | `ocr_unavailable`.

(В v1.15 `no_access` удалён: чтение единое, документ существует — виден всем. См. §23.)

Затем всегда:
```json
event: done
data: {"elapsed_ms":3410,"inference_path":"nexus-link","journal_id":"q-001"}
```

Ошибка:
```json
event: error
data: {"message":"…","stage":"retrieve"}
```

## 4. Роли и права (обязательны по брифу)

**Актуальная модель — §23 (v1.15): чтение единое, запись — только `quality` и
`director`.** Ниже — историческая модель v1, оставленная для чтения диффа
контракта; она больше не действует.

`src/lex/access.py` (v1, отменено §23):
- роль = список отделов + список систем; `*` — все;
- документ доступен, если `doc.department ∈ role.departments` **или** `role.departments` содержит `*`;
- если после фильтра по вопросу не осталось доступных документов, **но** они есть
  без фильтра — это `refusal.kind = "no_access"`, а не «не найдено».
- `permissions` считает и отдаёт в `detail`: сколько отброшено.

**Действует (v1.15):**
- чтение — весь корпус для всех ролей (`filter_docs` → `mode: "unified_read"`,
  `dropped: 0`); `role.departments`/`business_lines` остаются только для
  аналитики, на выдачу не влияют;
- запись (`POST /api/cases`, `/api/tickets/*`, `/api/ingest`,
  `/api/change-requests/*/status`) — `quality`/`director`, иначе `403`;
  решения по предложениям изменений — только `director`;
- отказ `no_access` из чтения удалён. Действующие `kind`: `out_of_scope`,
  `not_in_corpus`, `no_edition_in_force`, `conflict_unresolved`,
  `ocr_unavailable`.

NexusLink на sage-pl, слот `NEXUS_LINK_MODEL` (сейчас `claude-sonnet-5`).

Оба локальны — это аргумент к критерию «Экономика эксплуатации».

## 8. Кейсы — пополняемая база реальных случаев (v1.1)

**Зачем (задача от владельца):** агент должен пополнять свою базу реальными
кейсами от ролей руководителей, чтобы в будущем они выводились. Основа —
регламенты по работе с заказчиками.

Кейс — это **не документ корпуса**. Документ нормативен и статичен. Кейс —
наблюдение из практики: что спросили, что ответили, что произошло. Кейсы живут
рядом с регламентами и **участвуют в поиске наравне**, но помечены источником
`kind: "case"` и имеют приоритет **ниже** любого нормативного документа при
конфликте.

### Модель кейса

```json
{"id":"case-0007","ts":"2026-11-26T10:44:00Z",
 "author_role":"director","author_name":"—",
 "question":"Клиент просит согласовать закупку за 2 дня вместо 5. Что делать?",
 "answer_in_practice":"Согласовали через директора, оформили отступление письмом.",
 "outcome":"resolved",
 "linked_docs":["ТЗ-ЭКЗ-СР01-Р2"],
 "tags":["срок","согласование","исключение"],
 "rule_key":"SR-01",
 "content_type":"text"}
```

`outcome`: `resolved` | `escalated` | `rejected` | `open`.
`content_type` — тот же набор, что у документов (§9).

### Эндпоинты

`POST /api/cases` — добавить кейс.
```json
{"question":"…","answer_in_practice":"…","outcome":"resolved",
 "author_role":"director","linked_docs":["ТЗ-ЭКЗ-СР01-Р2"],"tags":["срок"]}
```
Ответ: `{"id":"case-0007","ok":true,"in_index":true}` — кейс сразу попадает в
поиск, без переиндексации всего корпуса.

`GET /api/cases?limit=&role_id=&tag=&rule_key=` — список.

### Как кейсы влияют на ответ

1. Поиск идёт по документам **и** кейсам одновременно.
2. Кейсы не могут отменить регламент. Если кейс противоречит действующей
   редакции — в ответе это явно: «по регламенту 5 дней, в практике был случай
   согласования за 2 дня (кейс case-0007)».
3. Если регламент ответа не даёт, а кейс даёт — ответ строится на кейсе с
   пометкой «по практике, регламент не покрывает».
4. В шаг `retrieve` добавляется счётчик: «документов N, кейсов M».

### Новый шаг в SSE — `cases`

После `retrieve`, перед `permissions`:

| # | `key` | Заголовок | `detail` |
|---|---|---|---|
| 3a | `cases` | Поиск по кейсам | «найдено M кейсов, из них по теме K» |

Цвет: `teal`. Полный порядок становится:

```
accept → decompose → retrieve → cases → permissions → resolve → conflict → compose → verify
```

`total` в каждом событии = **9**.

## 9. Мультимодальный корпус (v1.1)

**Задача от владельца:** БД будет иметь разную форму — текст, картинки, сканы
документов. Агент должен уметь различать их.

### Тип содержимого

У каждого элемента корпуса (документ или кейс) есть `content_type`:

| `content_type` | Что это | Как обрабатываем | Что в ответе |
|---|---|---|---|
| `text` | Готовый текст (md/txt/docx с текстовым слоем) | чанкинг → BM25 + эмбеддинги | обычная цитата |
| `image` | Картинка со смыслом (схема, скриншот, таблица-картинка) | OCR → текст + описание; сама картинка доступна по URL | цитата + превью |
| `scan` | Скан документа без текстового слоя | OCR; если OCR дал < 100 символов — помечаем `ocr_degraded` | цитата + предупреждение |
| `mixed` | PDF/документ со страницами разного типа | постранично: текст + OCR страниц-картинок | цитата с номером страницы |

### Различение — обязательный шаг

Агент **обязан** определить тип и сказать это в консоли. Новый шаг перед
`retrieve`:

| # | `key` | Заголовок | `detail` |
|---|---|---|---|
| 2a | `inspect` | Разбор источников | «текст N · картинки M · сканы K · смешанные J» |

Цвет: `indigo`.

Если в корпусе есть сканы с плохим OCR — в шаге `inspect` это видно:
«сканы 3 (1 с плохим распознаванием)».

### Ответ по нетекстовому источнику

`citations[]` расширяется:
```json
{"doc_id":"ТЗ-ЭКЗ-0042","title":"Схема процесса согласования",
 "content_type":"image","page":1,
 "quote":"…распознанный текст…",
 "preview_url":"/api/doc/ТЗ-ЭКЗ-0042/preview?page=1",
 "ocr_confidence":0.82}
```

При `ocr_confidence < 0.6` в ответе обязательна пометка: «источник распознан
неуверенно, сверьте с оригиналом» — и это же уходит в `refusal`-логику, если
утверждение держится только на таком фрагменте.

### Эндпоинт

`GET /api/doc/{doc_id}/preview?page=N` — отдаёт изображение страницы или саму
картинку. Нужен, чтобы в UI цитата была кликабельной: «показать источник».

### Честное ограничение

OCR на старте — **уже готовый движок, не обучаемый нами**. Если его нет в
окружении, сканы помечаются `ocr_unavailable` и в `inspect` пишется честно:
«сканы не обрабатываются». Не выдавать за поддержку того, чего нет.

## 10. Диалог с уточнением параметров (v1.2)

**Задача от владельца:** агент должен уметь вести диалог с сотрудником, уточнять
у него необходимые параметры задачи.

Сейчас `/api/ask` отвечает на один вопрос и забывает его. Так нельзя: половина
реальных вопросов неполна — «какой срок согласования?» без указания даты,
подразделения и предмета закупки. Агент обязан **спросить, а не догадываться**.

### Свойства, которые нельзя терять

1. **Уточнение — это не отказ.** Вопрос осмысленный, просто неполный. Ответ
   `clarification`, а не `refusal`.
2. **Не больше 3 вопросов за раз.** Сотрудник не проходит допрос.
3. **Каждый уточняющий вопрос — обоснован.** Агент говорит, *почему* спрашивает:
   «не могу определить действующую редакцию без даты».
4. **Уточнение можно пропустить.** Если сотрудник отвечает «не знаю» — агент идёт
   по разумному умолчанию и **явно говорит**, какое умолчание применил.
5. **Диалог имеет состояние.** `session_id` в запросе и ответе.

### Запрос

`POST /api/ask` дополняется полем `session_id` (необязательным):

```json
{"question":"Какой срок согласования заявки?",
 "role_id":"lawyer","session_id":"s-7f3a1c"}
```

Первый запрос — без `session_id`, сервер создаёт сессию.

### Новое событие — `clarify`

Вместо `answer`/`refusal` может прийти:

```json
event: clarify
data: {"session_id":"s-7f3a1c",
       "questions":[{"key":"as_of","text":"На какую дату определить действующую редакцию?","reason":"в корпусе три редакции правила SR-01, без даты нельзя выбрать","kind":"date"},
                    {"key":"amount","text":"Сумма заявки больше 500 000 рублей?","reason":"от суммы зависит порядок согласования","kind":"choice","options":["до 500 000","свыше 500 000","не знаю"]}],
       "partial":{"retrieved":12,"accessible":5},
       "can_skip":true}
```

`kind`: `date` | `choice` | `text` | `doc_id`.
`can_skip` — если `true`, UI показывает «Пропустить, выбери сам».

После `clarify` поток **закрывается** (не приходит `done`). Следующий запрос
несёт `session_id` и `answers`:

```json
{"question":"Какой срок согласования заявки?","role_id":"lawyer",
 "session_id":"s-7f3a1c",
 "answers":{"as_of":"2026-07-01","amount":"свыше 500 000"}}
```

Значение `"не знаю"` или отсутствие ключа = «пропустить».

### Ограничения

- Максимум **2 уточняющих круга** на сессию. Третий — либо ответ с явными
  умолчаниями, либо отказ. Защита от бесконечного диалога.
- Сессия живёт 30 минут без активности.
- Каждый пропущенный параметр и умолчание пишутся в `answer.assumptions`.

### В ответе — что предположили

```json
event: answer
data: {…, "assumptions":[{"key":"as_of","value":"2026-11-26","note":"дата не указана — считаю сегодняшней"}]}
```

### В SSE-потоке это отдельный шаг

Шаг `clarify` идёт **вместо** `decompose`, когда нужны уточнения. Console Lex
показывает его тем же механизмом, но с цветом `sky` и иконкой вопроса:

```
[2/9] Уточнение   Нужна дата: в корпусе три редакции SR-01
```

### Что показывает UI

Левая колонка (чат): вопрос агента с полем ввода/выбора прямо в ленте.
Правая колонка (консоль): видно, какие параметры уже известны, какие
запрошены, какие пропущены с умолчанием.

**Почему это важно для оценки:** критерий «Агентность» — 0 баллов за один
запрос, 3 за автономного агента. Уточняющий диалог — прямое доказательство,
что это не «вопрос → ответ», а цикл. Плюс это то, чего не будет у большинства
конкурентов.

## 11. Бизнес-направления (v1.3)

**Задача от владельца:** регламенты для разных бизнес-направлений разные. Агент
должен уметь различить бизнес-направление сотрудника и его задачи.

### Зачем это отдельно от `department`

`department` (отдел) — организационная единица. Бизнес-направление — предметная
область работы: у одного отдела может быть несколько направлений, одно
направление может затрагивать несколько отделов. Регламенты привязаны к
**направлению**, не только к отделу.

### Модель

Документ и кейс получают поле `business_line` (обязательное для новых данных):

```json
{"doc_id":"ТЗ-ЭКЗ-СР01-Р2","business_line":"закупки","department":"Юридический отдел"}
```

Список направлений — из данных, не из кода:
`GET /api/business-lines` → `[{"id":"закупки","title":"Закупки","docs":12},
{"id":"лицензирование","title":"Лицензирование","docs":5}, …]`

### Как агент различает

1. **От роли.** Роль сотрудника несёт `default_lines[]` — направления, в которых
   он обычно работает. Это фильтр по умолчанию, не жёсткий.
2. **От вопроса.** Вопрос упоминает предмет: «лицензия на продукт X» → направление
   `лицензирование`. Определяется на шаге `decompose` по синонимам
   (`docs/db/ARTICLES-DRAFT.md` — статьи как раз для этого).
3. **От уточнения.** Если ни роль, ни вопрос не дают однозначности — спросить
   (связка с §10): `{"key":"business_line","kind":"choice","text":"О каком направлении речь?","options":["Закупки","Лицензирование","…"]}`.
4. **На пересечении.** Вопрос может затрагивать два направления — тогда поиск
   идёт по обоим, а в ответе явно: «ответ по направлению X; по Y — другой
   документ».

### Права: И роли, И направления

Документ доступен, если **оба** условия:
- `doc.department ∈ role.departments` (или `*`);
- `doc.business_line ∈ role.business_lines` (или `*`).

Иначе — `refusal.kind = "no_access"` с указанием, по какому признаку закрыт.

### В SSE

Шаг `decompose` теперь сообщает определённое направление:

```
[2/9] Разбор вопроса   направление: закупки · 2 подвопроса
```

Если направление не определено — шаг `clarify` (см. §10), а не догадка.
`inspect` показывает срез: «текст N · картинки M · сканы K · направлений L».

### В аналитике (`GET /api/analytics`)

```json
"by_business_line":[{"line":"закупки","count":18,"refusals":2},
                    {"line":"лицензирование","count":7,"refusals":5}],
"missing_by_line":[{"line":"лицензирование","count":5,"note":"чаще всего нет документа"}]
```

Это прямо бьёт в критерий «Соответствие задаче партнёра»: видно, где регламентов
не хватает — по направлениям, а не «вообще».

### Что делать с нашим корпусом

В `sample-corpus/manifest.json` поля `business_line` сейчас **нет**. Добавить:
- у ARCH в `schema/source-schema.md` — обязательное поле в целевой модели;
- в генератор `demo/gen-sample-corpus.py` — вывести направление из `system`
  и типа документа (закупки / лицензирование / качество / хранение / персонал);
- до появления поля — считать `business_line = "общее"` и не блокировать.

## 12. Только из базы знаний (v1.4) — ГЛАВНОЕ ПРАВИЛО

**Задача от владельца (дословно):** «Нельзя чтобы ИИ-агент брал знания вне базы
данных. Агент должен заботиться о конфиденциальности данных заказчика. Агент не
должен придумывать ответы, полученные вне базы знаний организации.»

Это не рекомендация. Это **ограничение верхнего уровня**, которое важнее
красоты ответа и важнее полноты.

### 12.1. Правило

Каждое утверждение в ответе обязано иметь **цитату из элемента базы знаний**
(документ или кейс). Нет цитаты — нет утверждения. Модель не имеет права
дополнять ответ общими знаниями, даже если они верны.

**Пример нарушения:** «Срок согласования обычно составляет 5 рабочих дней, как
принято в практике закупок» — «как принято в практике» источником не является.

**Правильный ответ:** «Срок согласования — пять рабочих дней (ТЗ-ЭКЗ-СР01-Р2,
редакция 2 от 2026-06-01, раздел «Порядок выполнения процедуры»).»

### 12.2. Как это обеспечивается технически (три барьера)

**Барьер 1 — промпт.** Модели явно запрещено использовать знания вне
переданного контекста. Контекст — только фрагменты из базы. Формулировка
в системном сообщении (`src/lex/llm.py`):

> Ты отвечаешь ТОЛЬКО на основе фрагментов, переданных ниже. Если фрагменты не
> содержат ответа — верни отказ, а не общие знания. Не используй сведения, которых
> нет во фрагментах, даже если ты их знаешь. Каждое утверждение сопровождай
> номером фрагмента в квадратных скобках.

**Барьер 2 — проверка покрытия (шаг `verify`).** После генерации каждое
утверждение сверяется с цитатами:
- утверждение без опоры на фрагмент → **ответ не выдаётся**;
- проверка программная, не «на глаз модели»: ответ разбивается на предложения,
  каждое должно нести ссылку `[n]` на существующий фрагмент, и `n` должен
  действительно содержать смысл утверждения (эмбеддинг-близость предложения к
  цитируемому фрагменту, порог в конфиге).

**Барьер 3 — финальный фильтр.** Если после барьера 2 остаётся хоть одно
непокрытое утверждение — ответ **усекается** до покрытых частей; если покрытых
нет — `refusal.kind = "not_in_corpus"`.

### 12.3. Отказ — это правильный ответ

Если в базе знаний ответа нет, агент **обязан** отказаться. Это не сбой, а
выполнение требования:

```json
event: refusal
data: {"reason":"В базе знаний нет документа, регулирующего этот вопрос",
       "kind":"not_in_corpus",
       "searched":{"documents":27,"cases":4,"business_lines":["закупки"]},
       "hint":"Уточните направление или обратитесь к владельцу регламента"}
```

Отказ **всегда** говорит, что искали: сколько документов, кейсов, по каким
направлениям. Пустое «не знаю» — плохой отказ.

### 12.4. Конфиденциальность

1. **В промпт уходит только необходимое.** Не весь документ, а найденные
   фрагменты (топ-K после реранка). Не «на всякий случай весь корпус».
2. **Журнал не хранит содержимое документов.** Только идентификаторы, шаги,
   время. Цитаты — в ответе пользователю, но не в `journal.jsonl` (там `doc_ids`,
   не `quotes`).
3. **Права проверяются ДО генерации.** Недопустимый для роли документ не попадает
   в промпт вообще — не «попадает, но не показывается». Иначе конфиденциальные
   данные уходят в модель.
4. **Никаких «полезных» дополнений.** На вопрос «а как обычно делают в других
   компаниях?» агент отвечает: «База знаний организации этот вопрос не покрывает».

### 12.5. Что меняется в событиях

Шаг `verify` несёт результат проверки покрытия:

```json
event: step
data: {"n":9,"total":9,"key":"verify","title":"Самопроверка",
       "detail":"утверждений 4 · покрыто цитатами 4 · внешних знаний 0","ms":120,"color":"green"}
```

Если барьер сработал и ответ усечён:
`"detail":"утверждений 5 · покрыто 3 · 2 отброшено (нет цитаты)"` — цвет `amber`.

### 12.6. Демонстрационный кейс для жюри (обязателен)

Нужен вопрос, на который модель **знает** ответ из общих знаний, но в базе его
**нет**. Агент обязан отказаться. Пример: «Какая ставка НДС в России?» — модель
это знает, в корпусе этого нет, правильное поведение — отказ.

Этот кейс показывается в демо и в видео. Он доказывает главное: агент не
галлюцинирует, а работает по базе.

### 12.7. Честное ограничение

Барьер 2 — эвристика на эмбеддинг-близости, а не формальное доказательство. Она
ловит большинство случаев «придумал», но не все. Записывается в `docs/LIMITS.md`;
не выдавать за гарантию.

## 13. Формат ответа и работа с документами (v1.5)

**Задача от владельца (дословно):** «Формат ответа агента: точная и краткая
выжимка информации — далее в диалоге он может узнать подробности уже развёрнуто,
ссылки на документы, по которому он может перейти и прочитать, скачать
необходимую форму документа, агент должен помочь ему с запоминанием форм тех или
иных документов и проверить, чтобы все данные совпадали.»

Четыре отдельные возможности. Все четыре обязательны.

### 13.1. Кратко по умолчанию, развёрнуто по запросу

**Первый ответ — выжимка. Не пересказ документа.** Правило: 2–4 предложения,
не больше 400 знаков. Сотрудник за 5 секунд понимает ответ и решает, нужны ли
подробности.

```json
event: answer
data: {"short":"Пять рабочих дней (ТЗ-ЭКЗ-СР01-Р2, ред. 2).",
       "has_details":true,
       "detail_id":"d-q0001",
       "citations":[…]}
```

**Развёрнутая версия — по отдельному запросу**, не сразу:

`POST /api/expand` → `{"detail_id":"d-q0001","section":"all"}`

```json
{"short":"…",
 "detailed":"Согласно редакции 2 регламента согласования заявок, вступившей
             в силу 1 июня 2026 года, срок согласования заявки на закупку
             составляет пять рабочих дней. Срок отсчитывается с момента
             регистрации заявки. Редакция 1 (2026-01-15) устанавливала три
             рабочих дня, редакция 3 (вступает 2027-01-01) — семь. …",
 "sections":[{"title":"Порядок выполнения","quote":"…"},
             {"title":"Исключения","quote":"…"}],
 "tables":[{"caption":"Сроки по редакциям","rows":[["Ред.","Дата","Срок"],["Р1","2026-01-15","3"],…]}],
 "citations":[…]}
```

`section` — можно запросить конкретный раздел: `"exceptions"`, `"procedure"`,
`"roles"`. В диалоге это естественный следующий шаг: «А какие исключения?»

**Правило:** развёрнутая версия строится из **тех же** фрагментов, что и краткая.
Она не добавляет новых знаний — только раскрывает цитаты полнее. Барьер §12
действует на обе.

### 13.2. Ссылки на документы — перейти и прочитать

Каждая цитата несёт ссылку на документ целиком:

```json
"citations":[{"doc_id":"ТЗ-ЭКЗ-СР01-Р2","title":"Регламент согласования заявки на закупку",
  "revision":2,"effective":"2026-06-01","business_line":"закупки",
  "quote":"Срок согласования заявки: пяти рабочих дней.",
  "view_url":"/api/doc/ТЗ-ЭКЗ-СР01-Р2",
  "download_url":"/api/doc/ТЗ-ЭКЗ-СР01-Р2/download",
  "anchor":"#razdel-poryadok"}]
```

Новые эндпоинты:

| Метод | Путь | Что отдаёт |
|---|---|---|
| `GET` | `/api/doc/{doc_id}` | документ целиком, HTML с оглавлением |
| `GET` | `/api/doc/{doc_id}/download` | исходный файл (md/docx/pdf) с `Content-Disposition: attachment` |
| `GET` | `/api/doc/{doc_id}/preview?page=N` | страница как изображение (для сканов) |

**Права проверяются и здесь.** Документ вне области роли — 403 с причиной,
не 404: сотрудник должен знать, что документ существует, но ему не положен.

### 13.3. Скачивание формы документа

Отдельно от скачивания документа — **скачивание формы**, то есть бланка для
заполнения. У части документов есть приложение-форма (заявка, акт, чек-лист).

`GET /api/forms` → список доступных форм:
```json
[{"form_id":"form-zayavka","title":"Заявка на закупку","doc_id":"ТЗ-ЭКЗ-СР01-Р2",
  "fields":7,"format":"docx","business_line":"закупки"}]
```

`GET /api/forms/{form_id}/download` → файл бланка.

`GET /api/forms/{form_id}` → описание полей:
```json
{"form_id":"form-zayavka","title":"Заявка на закупку",
 "fields":[
  {"key":"number","label":"Номер заявки","type":"text","required":true,
   "pattern":"^ЗК-\\d{4}-\\d{4}$","example":"ЗК-2026-0042",
   "hint":"формат ЗК-ГГГГ-НННН"},
  {"key":"amount","label":"Сумма","type":"money","required":true,"min":0},
  {"key":"deadline","label":"Требуемый срок","type":"date","required":true},
  {"key":"department","label":"Подразделение","type":"choice","required":true,
   "options":["Отдел качества","Юридический отдел",…]}
 ]}
```

### 13.4. Помощь с заполнением и проверка данных

**Агент запоминает форму** и ведёт сотрудника по полям. Состояние — в сессии
(связка с §10).

`POST /api/forms/{form_id}/fill`
```json
{"session_id":"s-7f3a1c",
 "values":{"number":"ЗК-2026-42","amount":"450 000","department":"Отдел качества"}}
```
```json
{"ok":false,
 "errors":[{"field":"number","value":"ЗК-2026-42","message":"номер не соответствует формату ЗК-ГГГГ-НННН","expected":"ЗК-2026-0042"},
           {"field":"deadline","message":"поле обязательное","expected":"дата в формате ГГГГ-ММ-ДД"}],
 "warnings":[{"field":"amount","message":"сумма близка к порогу 500 000 — согласование пойдёт по другому порядку","doc_id":"ТЗ-ЭКЗ-СР01-Р3"}],
 "filled":{"number":"ЗК-2026-42","amount":450000,"department":"Отдел качества","deadline":null},
 "missing":["deadline"],
 "progress":"3 из 4 полей"}
```

Типы проверок (все обязательны):

1. **Обязательность** — пустое обязательное поле.
2. **Формат** — по `pattern`/типу: номер, дата, сумма, ИНН.
3. **Значения из справочника** — подразделение должно быть из списка.
4. **Согласованность с регламентом** — это самое ценное: если сумма выше порога
   из другого документа, агент предупреждает и **ссылается на документ**.
   Не блокирует, а предупреждает с обоснованием.
5. **Полнота** — чего не хватает, чтобы форма считалась заполненной.

**Правило §12 здесь работает жёстко:** если агент не может обосновать
требование формата цитатой из базы — он **не выдумывает** формат. В таком поле
`"hint":"формат не описан в регламенте — уточните у владельца формы"`.

### 13.5. Что видит сотрудник (UI)

**Левая колонка:**

1. Вопрос → **краткая выжимка** (крупно, 2–4 строки).
2. Под ней две кнопки: «Подробнее» и «Открыть документ».
3. «Подробнее» раскрывает развёрнутый ответ с разделами, цитатами и таблицами —
   прямо в ленте, без перехода.
4. У каждой цитаты: номер `[1]`, документ, редакция, дата, бейдж типа
   (текст/картинка/скан), ссылки «Читать» и «Скачать».
5. Если в ответе есть форма — карточка: «Есть форма: Заявка на закупку» с
   кнопками «Скачать бланк» и «Заполнить здесь».

**Правая колонка (консоль)** — новые шаги для формы:
```
[8/9] Сборка ответа      краткая выжимка · 3 цитаты · есть форма
[9/9] Самопроверка       утверждений 3 · покрыто 3 · внешних знаний 0
```

При заполнении формы консоль показывает проверки построчно — это красиво и
доказывает, что агент реально сверяет, а не «говорит, что сверяет».

### 13.6. Чего не делать

- Не выдавать краткую выжимку за полный ответ. Если это выжимка — так и названо.
- Не давать «Подробнее» для отказа: отказ уже полный, раскрывать нечего.
- Не проверять форму «на глаз модели» — только по правилам из §13.4, с цитатами.
- Не подставлять значения, которых сотрудник не вводил. Пустое поле остаётся
  пустым, а не «разумным умолчанием» (умолчания допустимы только в ответах на
  вопросы, не в формах).

## 14. Telegram-бот (v1.6) — задел, не реализация

**Задача от владельца:** «Агент должен будет связан с ботом в телеграм (это
сделаем позже) пока просто зафиксируй в документах.»

**Статус: НЕ реализуется в спринте.** Этот раздел фиксирует архитектурное
требование, чтобы сегодняшние решения его не заблокировали.

### 14.1. Почему это дёшево сделать позже

Ядро (`src/lex`) не знает про HTTP. Это правило из §1 не случайно: оно же
делает возможным второй транспорт. Бот — это ещё один потребитель того же
оркестратора, как HTTP-слой.

```
        ┌──────────────┐
        │   src/lex    │  ядро: 9 шагов, никакого HTTP
        └──────┬───────┘
      ┌────────┴────────┐
      │                 │
┌─────▼─────┐    ┌──────▼──────┐
│  src/api  │    │  src/bot    │   ← появится позже
│  (сейчас) │    │ (Telegram)  │
└───────────┘    └─────────────┘
```

**Что это требует уже сегодня:** ничего дополнительно, кроме соблюдения
правила «ядро не знает про транспорт». Если код ядра начнёт возвращать
`JSONResponse` или SSE-строки — бот станет дорогим.

### 14.2. Что нужно будет при подключении

| Что | Откуда |
|---|---|
| Токен бота | `BOT_TOKEN` в `.env`, не в коде |
| Привязка пользователя Telegram к роли | `telegram_user_id → role_id`, таблица в конфиге |
| Транспорт | long polling (проще) или webhook (быстрее) |
| Что переиспользуется | `session_id` из §10 — диалог живёт в тех же сессиях |

### 14.3. Что нельзя сломать сейчас

1. **Сессии — по `session_id`, а не по HTTP-соединению.** Иначе в Telegram
   каждый запрос будет новой сессией, и диалог с уточнением не заработает.
2. **Права — по `role_id`, а не по чему-то, что живёт в запросе.** В боте роль
   придёт из привязки Telegram-пользователя, и `access.py` должен её принять
   как обычный параметр.
3. **Короткий ответ отдельно от развёрнутого** (§13.1) — в Telegram длинные
   сообщения режутся, и краткость там не опция, а необходимость. Архитектура
   уже правильная.
4. **Формы, которые не влезают в мессенджер**, — в боте будет ссылка на
   веб-форму, а не попытка отрисовать поля в чате.

### 14.4. Чего в боте не будет

- Полноценного UI-консоли (9 шагов) — только компактная сводка шагов под ответом.
- Просмотра документов — только ссылки.
- Заполнения форм — только ссылка на веб-форму.

**В документации фиксируется как «второй транспорт, планируется».**
В `docs/LIMITS.md` — в раздел «не реализовано». Не упоминать в питче как
готовое.

## 15. Эскалация в службу качества (v1.7)

**Задача от владельца (дословно):** «Агент, если не знает или не может найти
ответ, должен 2-3 уточняющих итерации сделать, после этого отправить в службу
качества.»

Уточняет §10: делаем уточнения **до** того, как сдаться, и сдаёмся не в пустоту.

### 15.1. Точная последовательность

```
вопрос
  ↓
поиск → не нашёл / неоднозначно
  ↓
уточнение 1  (до 3 вопросов в одной итерации)
  ↓
поиск → не нашёл
  ↓
уточнение 2  (до 3 вопросов)
  ↓
поиск → не нашёл
  ↓
уточнение 3  (последнее)
  ↓
поиск → не нашёл
  ↓
ЭСКАЛАЦИЯ В СЛУЖБУ КАЧЕСТВА
```

**Минимум 2, максимум 3 уточняющих итерации.** Не 1 (мало — сотрудник не
успевает уточнить), не 5 (допрос). Если после первой итерации стало ясно, что
вопрос вне базы (не «неполный», а именно «такого документа нет») — можно
эскалировать раньше: уточнять нечего.

Разница, которую агент обязан различать:
- **неполный вопрос** (нет даты, направления, суммы) → уточнять;
- **вопрос вне базы** (спросили про НДС) → эскалировать, уточнения бессмысленны.

### 15.2. Что такое «передать в службу качества»

Это не письмо в пустоту. Создаётся **заявка** в очередь разбора:

`POST /api/escalate` (внутренний, вызывается оркестратором автоматически)

```json
{"id":"esc-0003","ts":"2026-11-26T11:20:00Z",
 "session_id":"s-7f3a1c","role_id":"lawyer","business_line":"закупки",
 "question":"Как согласовать закупку, если поставщик единственный?",
 "clarifications":[{"iteration":1,"asked":["На какую дату?"],"answers":["2026-07-01"]},
                   {"iteration":2,"asked":["Сумма?"],"answers":["не знаю"]},
                   {"iteration":3,"asked":["Направление?"],"answers":["закупки"]}],
 "searched":{"documents":27,"cases":4,"accessible":5,"top":["ТЗ-ЭКЗ-СР01-Р2"]},
 "why_unresolved":"в корпусе нет порядка для единственного поставщика",
 "kind":"not_in_corpus",
 "status":"open"}
```

**Обязательные поля:** что спрашивали, что ответили, что искали, **почему не
решилось**. Заявка без «почему» бесполезна службе качества.

### 15.3. Событие в потоке

После последнего уточнения и неудачного поиска:

```json
event: escalate
data: {"ticket":"esc-0003","iterations":3,
       "reason":"В базе знаний нет порядка согласования с единственным поставщиком",
       "searched":{"documents":27,"cases":4},
       "next":"Заявка передана в службу качества. Ответ появится в базе как кейс.",
       "eta":"до 2 рабочих дней"}
```

Цвет шага: `orange`. Номер шага — вместо `verify`, то есть последним идёт
`escalate`, а не `answer`.

**Сотрудник видит не «ошибку», а действие:** «ваш вопрос передан, вот номер
заявки, вот что мы уже проверили».

### 15.4. Обратная связь: заявка превращается в кейс

Это замыкает цикл с §8. Когда служба качества отвечает на заявку, ответ
становится **кейсом** в базе, и следующий сотрудник с тем же вопросом получает
ответ, а не эскалацию.

`POST /api/escalate/{id}/resolve`
```json
{"answer":"Для единственного поставщика — обоснование по 44-ФЗ п.4 ч.1 ст.93, форма ОС-2.",
 "resolved_by":"quality","doc_id":null,"make_case":true}
```
Ответ: `{"ok":true,"case_id":"case-0012","status":"resolved"}`.

**Это и есть «агент пополняет свою базу реальными кейсами»** — но с
человеческим контролем: не агент придумал, а служба качества подтвердила.

### 15.5. Журнал и аналитика

- каждая эскалация — запись в `var/journal.jsonl` с `escalated: true`;
- `GET /api/analytics` дополняется:
  ```json
  "escalations":{"total":6,"open":4,"resolved":2,
                 "by_business_line":[{"line":"закупки","count":4}],
                 "top_unresolved":[{"question":"…","count":3}]}
  ```
- **«горячие темы без регламента»** — эскалации с частотой ≥ 2 автоматически
  попадают в раздел «чего нет в каталоге». Это ровно то, что просит критерий
  «Соответствие задаче партнёра».

### 15.6. Чего не делать

- Не эскалировать на первом же промахе — сначала уточнить.
- Не эскалировать без «почему»: заявка без анализа бесполезна.
- Не отправлять эскалацию молча — сотрудник должен видеть номер заявки.
- Не подменять эскалацию отказом. Отказ — «нет в базе, иди спроси другого».
  Эскалация — «нет в базе, я передал, тебе ответят».

## 16. Форма пополнения базы из ответа службы качества (v1.8)

**Задача от владельца (дословно):** «После ответа от Службы качества агент
должен пополнить свою базу через специальную форму.»

Развивает §15.4: там было «заявка превращается в кейс» — технически, вызовом
API. Здесь — **через форму**, то есть с человеческим контролем и явным
подтверждением.

### 16.1. Кто и что делает

```
служба качества отвечает на заявку
        ↓
агент ПРЕДЛАГАЕТ пополнение (черновик, не запись)
        ↓
человек проверяет и правит в форме
        ↓
подтверждение → кейс в базе → сотрудники получают ответ вместо эскалации
```

**Ключевое:** агент **не пишет в базу сам**. Он готовит черновик, человек
подтверждает. Иначе база загрязнится догадками — прямое противоречие §12.

### 16.2. Черновик кейса — что предлагает агент

`GET /api/escalate/{id}/draft`

```json
{"ticket":"esc-0003","status":"answered",
 "quality_answer":"Для единственного поставщика — обоснование по 44-ФЗ п.4 ч.1 ст.93, форма ОС-2.",
 "resolved_by":"quality","answered_at":"2026-11-26T13:40:00Z",
 "draft":{
  "question":"Как согласовать закупку, если поставщик единственный?",
  "answer_in_practice":"Обоснование по 44-ФЗ п.4 ч.1 ст.93, форма ОС-2.",
  "outcome":"resolved",
  "business_line":"закупки",
  "linked_docs":[],
  "tags":["единственный поставщик","закупки","44-ФЗ"],
  "rule_key":null,
  "author_role":"quality",
  "author_name":"служба качества",
  "content_type":"text",
  "source":"escalation",
  "escalation_id":"esc-0003"
 },
 "suggestions":{
  "missing":[
   {"field":"linked_docs","why":"в ответе упомянут 44-ФЗ, но такого документа нет в корпусе",
    "note":"можно оставить пустым — кейс будет без ссылки на регламент"},
   {"field":"rule_key","why":"ответ не относится ни к SR-01/02/03"}
  ],
  "conflicts":[
   {"with":"ТЗ-ЭКЗ-СР01-Р2","why":"ответ предлагает обход процедуры; в регламенте такого исключения нет",
    "severity":"warning"}
  ]
 }}
```

**`suggestions` — обязательная часть.** Агент не просто отдаёт черновик, а
говорит, чего в нём не хватает и с чем он расходится. Это то же правило §12:
не выдумывать, а показывать пробелы.

### 16.3. Форма подтверждения

`POST /api/escalate/{id}/confirm`

```json
{"case":{…тот же объект, что draft, возможно исправленный человеком…},
 "acknowledge_warnings":true,
 "editor_role":"quality"}
```

Ответ:
```json
{"ok":true,"case_id":"case-0012","in_index":true,
 "ticket_status":"resolved",
 "affected":"кейсов в базе: 13 · вопрос теперь покрыт"}
```

Правила:
- `links` на несуществующие `doc_id` → ошибка 400, не молчаливое игнорирование;
- если есть `conflicts` с `severity: "error"` → блокирует; `warning` → требует
  `acknowledge_warnings: true`;
- `editor_role` обязателен и пишется в кейс: видно, кто подтвердил.

### 16.4. Форма в UI (для службы качества)

Страница «Заявки» — доступна роли `quality` (и `director`):

1. Список заявок: номер, вопрос, дата, статус, сколько итераций уточнения было.
2. Открыть заявку → что спрашивали, что искали, почему не решилось (§15.2).
3. Поле «Ответ службы качества» — свободный текст.
4. После ввода ответа — **карточка черновика кейса**, поля редактируемые:
   вопрос, ответ, направление, теги, ссылки на документы, outcome.
5. Под полями — блок `suggestions`: чего не хватает (жёлтым), с чем расходится
   (красным), с кнопкой-ссылкой на документ.
6. Кнопка «Добавить в базу» — активна только когда обязательные поля заполнены.
7. После добавления: «Кейс case-0012 в базе. На этот вопрос теперь отвечают.»

**Это отдельный экран, не часть чата.** Служба качества — другой пользователь с
другими задачами.

### 16.5. Что видит обычный сотрудник

Когда по его заявке появился кейс:
```json
event: escalate
data: {"ticket":"esc-0003","status":"resolved",
       "case_id":"case-0012",
       "next":"По вашему вопросу добавлено решение в базу. Спросите снова — ответ будет."}
```

В ленте чата — карточка «Ваш вопрос решён» с кнопкой «Получить ответ», которая
переотправляет исходный вопрос: теперь он покрыт кейсом.

### 16.6. Аналитика цикла

`GET /api/analytics` дополняется:

```json
"knowledge_loop":{
  "escalations_total":6,"answered":4,"converted_to_cases":3,
  "avg_hours_to_answer":18.5,
  "questions_now_covered":3,
  "not_converted":[{"ticket":"esc-0005","why":"ответ дублирует существующий регламент"}]
}
```

**Что это доказывает жюри:** база знаний **растёт от использования**. Не
статичный корпус, а живой контур: сотрудник спросил → не нашлось → служба
качества ответила → кейс в базе → следующий получает ответ. Это и «агент
пополняет свою базу реальными кейсами» из §8, и «аналитика» из критерия
«Соответствие задаче партнёра».

### 16.7. Чего не делать

- Не давать агенту права писать в базу без подтверждения человеком.
- Не терять исходный вопрос при конвертации — он в `question` кейса.
- Не конвертировать заявку, если ответ дублирует существующий документ —
  предупредить об этом (`not_converted`).
- Не скрывать от сотрудника, что его вопрос стал кейсом.

## 17. Policy на входе (v1.9)

**Задача от владельца (дословно):** «Policy на входе должен проверять: касается
ли вообще вопрос его компетенции и роли спрашивающего.»

Это **не** фильтр результатов (§11) — это проверка **до всякого поиска**.
Разница принципиальная: не «нашли, но не покажем», а «не ищем вообще».

### 17.1. Новый первый содержательный шаг

Порядок меняется. Было:

```
accept → decompose → retrieve → cases → permissions → resolve → conflict → compose → verify
```

Стало:

```
accept → policy → decompose → retrieve → cases → permissions → resolve → conflict → compose → verify
```

Всего **10 шагов**, `total: 10`.

| # | `key` | Заголовок | `detail` |
|---|---|---|---|
| 1 | `accept` | Запрос принят | роль, направление |
| 2 | `policy` | Проверка компетенции | «в компетенции роли: да · направление: закупки» |
| 3 | `decompose` | Разбор вопроса | направление · N подвопросов |
| 4 | `retrieve` | Поиск | BM25 N · вектор M → топ K |
| 5 | `cases` | Поиск по кейсам | найдено M кейсов |
| 6 | `permissions` | Проверка прав | доступно X из Y, отброшено Z |
| 7 | `resolve` | Действующая редакция | N редакций, действует Р2 |
| 8 | `conflict` | Сопоставление | конфликтов N |
| 9 | `compose` | Сборка ответа | из K цитат |
| 10 | `verify` | Самопроверка | утверждений N · покрыто M |

Цвет `policy`: `pink`.

### 17.2. Что именно проверяется

Три независимых вопроса, все должны пройти:

| Проверка | Что значит | Что если нет |
|---|---|---|
| **Тема в компетенции** | Вопрос относится к предметной области базы знаний (регламенты, лицензирование, процессы организации) | `refusal.kind = "out_of_scope"` |
| **Роль имеет доступ** | У роли есть хотя бы один доступный документ по этому направлению | `refusal.kind = "no_access"` |
| **Направление определимо** | Из вопроса и роли можно понять направление | `clarify` (спросить направление, §10) |

**Порядок важен:** сначала «вообще наша ли это тема», потом «можно ли этой роли».
Иначе получим «нет доступа» на вопрос про НДС — это дезинформирует.

### 17.3. Как определяется «в компетенции»

Не моделью на глаз — по данным. Метод:

1. **По направлению.** Вопрос сопоставляется с направлениями базы
   (`GET /api/business-lines`) через статьи (§ в `docs/db/ARTICLES-DRAFT.md`) —
   синонимы и ключевые слова. Если ни одно направление не набирает порог
   близости — вопрос вне компетенции.
2. **По покрытию корпуса.** Быстрый поиск (BM25, без эмбеддингов — он на входе
   должен быть дешёвым) по названиям и первым абзацам документов. Если лучший
   результат ниже порога — тема не покрыта.
3. **По роли.** Роль с `business_lines: ["закупки"]` на вопрос про лицензирование
   получает `no_access` от policy, а не пустой поиск.

**Пороги в конфиге**, не в коде: `POLICY_MIN_SCORE`, `POLICY_MIN_LINES`.

### 17.4. Ответ при провале policy

```json
event: refusal
data: {"kind":"out_of_scope",
       "reason":"Вопрос не относится к базе знаний организации",
       "detail":"База покрывает: закупки, лицензирование, качество, хранение, персонал",
       "searched":null,
       "hint":"Переформулируйте или обратитесь в службу качества"}
```

**Ключевое отличие от `not_in_corpus`:** здесь мы **не искали**, потому что
вопрос не наш. Это честнее и быстрее — и объясняет сотруднику, почему.

При `no_access` — как в §11: документы существуют, но не для этой роли.

### 17.5. Что видит сотрудник

В консоли:
```
[1/10] Запрос принят        роль: юрист · направление: закупки
[2/10] Проверка компетенции в компетенции: да · 5 доступных документов
```
или
```
[2/10] Проверка компетенции ВНЕ КОМПЕТЕНЦИИ: база не покрывает «бухгалтерия»
       (база покрывает: закупки, лицензирование, качество, хранение, персонал)
```

Отказ `out_of_scope` оформляется в UI так же, как `not_in_corpus` (§12.3) —
спокойный блок, не ошибка. Разница в тексте: «вопрос вне базы знаний
организации» против «в базе нет ответа».

### 17.6. Связь с §15 (эскалация)

`out_of_scope` **не эскалируется** — службе качества нечего разбирать в вопросе
про НДС. Эскалация — только для `not_in_corpus` (тема наша, ответа нет).

**Уточнение v1.13 (после спора с MIMIC):** отказ `out_of_scope` содержит
кнопку «Всё равно передать в службу качества». Это **не автоматическая**
эскалация, а осознанный выбор сотрудника. Если он нажимает — тикет создаётся с
пометкой `kind: "out_of_scope_requested"` и `priority: "low"`. Разница
принципиальная: очередь не засоряется вопросами не по адресу, но сотрудник не
остаётся в тупике, если считает, что вопрос всё-таки относится к организации.

Правило простое: **агент не решает за человека, что его вопрос неважен.**

Это важное различие. Оно экономит время службы качества и показывает жюри, что
агент понимает границы своей компетенции.

### 17.7. Чего не делать

- Не проверять компетенцию моделью «на глаз» — нужны пороги и данные.
- Не путать `out_of_scope` с `not_in_corpus` — это разные ситуации и разные
  следующие действия.
- Не блокировать пограничные вопросы: если сомнительно — пропускать к поиску,
  поиск сам покажет, есть ли ответ.

## 18. Тикет создаёт агент, качество подключается (v1.10)

**Задача от владельца (дословно):** «Если агент не может ответить на вопрос
пользователя — он сам создаёт тикет в службу качества, к этому вопросу
подключаются сотрудники службы качества.»

Уточняет §15: там было «эскалация», здесь — **агент делает это сам**, без
участия человека, и тикет **попадает в работу** службы качества.

### 18.1. Автоматика

Сотрудник ничего не нажимает. Агент, исчерпав уточнения (§15.1) и не найдя
ответа, **сам** создаёт тикет. Сотрудник видит только результат: «передано,
номер такой-то».

Триггеры (любой из):
- `not_in_corpus` после 2–3 уточнений;
- `conflict_unresolved` — документы противоречат, и иерархия не разрешает;
- `ocr_degraded` — единственный источник распознан неуверенно (< 0.6).

`out_of_scope` (§17) **не** создаёт тикет — это не наша тема.

### 18.2. Тикет попадает в очередь, а не в пустоту

`POST /api/tickets` (создаёт оркестратор, не пользователь)

```json
{"id":"LEX-2026-0042","created_at":"2026-11-26T11:20:00Z",
 "created_by":"agent","session_id":"s-7f3a1c",
 "question":"Как согласовать закупку, если поставщик единственный?",
 "asker":{"role_id":"lawyer","business_line":"закупки"},
 "clarifications":[...3 итерации...],
 "searched":{"documents":27,"cases":4,"accessible":5,"top":["ТЗ-ЭКЗ-СР01-Р2"]},
 "why_unresolved":"в корпусе нет порядка для единственного поставщика",
 "kind":"not_in_corpus",
 "priority":"normal",
 "assignee":null,
 "status":"open",
 "sla_due":"2026-11-28T11:20:00Z"}
```

Отличия от §15.2:
- **`created_by: "agent"`** — явно видно, что тикет создан автоматически;
- **номер человекочитаемый** — `LEX-2026-0042`, чтобы его можно было назвать
  сотруднику и вписать в письмо;
- **`assignee`** — кто из службы качества взял в работу;
- **`sla_due`** — срок из конфига (по умолчанию 48 ч, для `high` — 8 ч).

### 18.3. Подключение сотрудников службы качества

Тикет не «висит» — он назначается:

| Действие | Кто | Эндпоинт |
|---|---|---|
| Взять в работу | сотрудник качества | `POST /api/tickets/{id}/assign` → `{"assignee":"И. Петрова"}` |
| Передать другому | сотрудник качества | тот же, с новым `assignee` |
| Ответить | сотрудник качества | `POST /api/tickets/{id}/answer` |
| Закрыть без ответа | сотрудник качества | `POST /api/tickets/{id}/close` → `{"reason":"..."}` |

**Правило распределения:** тикет с `business_line` попадает в очередь того
направления; если направление не определено — в общую очередь. Сотрудники
видят только тикеты своих направлений (та же логика прав, что у документов).

Одновременно над тикетом работает **один** человек — `assignee` блокирует
двойной ответ. Взять чужой можно, но с явным предупреждением.

### 18.4. Что видит сотрудник, задавший вопрос

В ленте чата — карточка, которая меняет состояние:

```
[ открыт ]   Вопрос передан в службу качества · LEX-2026-0042
             Что мы проверили: 27 документов, 4 кейса, направление «закупки»
             Срок ответа: до 28 ноября
[ в работе ] Взял в работу: И. Петрова, служба качества
[ решён ]    Ваш вопрос решён · добавлено в базу как кейс case-0012
             [ Получить ответ ]
```

Сотрудник может проверить статус: `GET /api/tickets/LEX-2026-0042` — но только
свой (по `session_id` или `role_id`).

### 18.5. Связь с §16 (форма пополнения)

Закрывается цикл целиком:

```
агент создал тикет (сам)
   → сотрудник качества взял в работу
   → ответил
   → агент предложил ЧЕРНОВИК кейса с пометками о пробелах (§16.2)
   → сотрудник качества подтвердил через форму (§16.3)
   → кейс в базе
   → следующий вопрос покрыт (§8)
```

Ни на одном шаге агент не пишет в базу без подтверждения человеком.

### 18.6. Аналитика очереди

`GET /api/analytics` → `tickets`:

```json
{"total":6,"open":2,"assigned":1,"answered":2,"closed":1,
 "by_business_line":[{"line":"закупки","count":4}],
 "avg_hours_to_assign":1.5,"avg_hours_to_answer":18.5,
 "sla_breached":0,
 "top_topics":[{"topic":"единственный поставщик","count":3}]}
```

`top_topics` — прямо в «чего нет в каталоге»: три тикета про единственного
поставщика означают, что регламента не хватает, и это видно без чтения тикетов.

### 18.7. Чего не делать

- Не создавать тикет на `out_of_scope` и на ошибки системы (это не задача качества).
- Не создавать дубликат: если по этой сессии тикет уже есть — вернуть его номер.
- Не показывать сотруднику внутренние поля (`assignee` видно, `why_unresolved`
  — да, но не служебные заметки качества).
- Не закрывать тикет автоматически по таймауту — только человеком.

## 19. Кейс, регламент и предложение об изменении (v1.11)

**Вопрос владельца:** «Может ли разъяснение эксперта, которого нет в
регламентах, стать самостоятельным источником? Или его сначала нужно включить в
утверждённый регламент? И так и так, но информацию в регламент вносят люди.
Агент только собирает полезную информацию для Службы качества.»

**Ответ и правило, которое из него следует.**

### 19.1. Два разных типа знания — не смешивать

| | Регламент | Кейс |
|---|---|---|
| Природа | норматив: «как должно быть» | практика: «как было однажды» |
| Кто утверждает | владелец регламента | служба качества |
| Может ли противоречить | нет, он и есть норма | **да**, и это его ценность |
| Что значит для ответа | обязателен | справочный, с оговоркой |
| Можно ли изменить агентом | **никогда** | да, с подтверждением человеком |

**Правило:** кейс **становится источником сразу**, но **источником второго
сорта**. Он отвечает на «а как у нас бывало», а не «а как нам положено».

Это и отвечает на вопрос владельца: **и так, и так**. Разъяснение эксперта —
самостоятельный источник (кейс), и **одновременно** повод изменить регламент.
Первое — для сотрудника прямо сейчас, второе — для организации на будущее.

### 19.2. Флаг не-нормативности — обязателен

Каждый кейс несёт:

```json
{"id":"case-0012","kind":"case","normative":false,
 "source":"escalation","escalation_id":"LEX-2026-0042",
 "deviates_from":["ТЗ-ЭКЗ-СР01-Р2"],
 "deviation":"регламент требует 5 рабочих дней; в практике согласовали за 2 через директора",
 "confirmed_by":"И. Петрова, служба качества","confirmed_at":"2026-11-26T15:00:00Z"}
```

`deviates_from` заполняется **автоматически**: при создании кейса агент
проверяет, противоречит ли ответ действующему документу по тому же `rule_key`
или теме. Противоречит — пишет документ в `deviates_from` и формулирует
`deviation`. Не противоречит — пусто.

### 19.3. Как кейс участвует в ответе

| Ситуация | Что отвечает агент |
|---|---|
| Регламент есть, кейс **согласуется** | Ответ по регламенту, кейс как подтверждение: «по регламенту 5 дней (ТЗ-…-Р2); был случай за 2 дня, но это было отступление (case-0007)» — **только если кейс отклоняется** |
| Регламент есть, кейс **противоречит** | Ответ по регламенту **с явным упоминанием** отклонения. Никогда не наоборот |
| Регламента нет, кейс есть | Ответ по кейсу с пометкой: «по практике, регламент этот вопрос не покрывает» |
| Ни регламента, ни кейса | Тикет в службу качества (§18) |

**Жёсткое правило:** кейс **не может отменить регламент**. Если сотрудник
действует по кейсу, противоречащему регламенту, — агент обязан об этом сказать.
Иначе кейс станет лазейкой, а это для юридического продукта недопустимо.

### 19.4. Предложение об изменении регламента

Когда кейс противоречит действующему документу — это сигнал, что регламент
устарел. Агент **формирует предложение**, но не вносит его.

`POST /api/change-requests` (создаёт агент автоматически при подтверждении кейса с `deviates_from`)

```json
{"id":"CR-2026-0007","created_at":"2026-11-26T15:01:00Z",
 "created_by":"agent",
 "target_doc":"ТЗ-ЭКЗ-СР01-Р2",
 "rule_key":"SR-01",
 "observed":"в практике согласовали за 2 рабочих дня (кейс case-0012)",
 "current_norm":"5 рабочих дней",
 "evidence":[{"case_id":"case-0012","count":3},
             {"tickets":["LEX-2026-0042"],"note":"ещё 2 схожих вопроса"}],
 "proposal":"добавить в раздел «Исключения» порядок для особых случаев",
 "status":"proposed","assignee":null}
```

**Важно, что здесь делает агент и чего не делает:**

| Делает | Не делает |
|---|---|
| собирает кейсы, противоречащие документу | не правит регламент |
| считает частоту (3 кейса — это уже система) | не решает, верно ли исключение |
| формулирует, что именно расходится | не утверждает изменение |
| показывает доказательства | не закрывает предложение сам |

**Люди решают.** Служба качества берёт предложение, владелец регламента
принимает решение, новая редакция появляется обычным путём — и **тогда** агент
начнёт отвечать по ней. Не раньше.

`POST /api/change-requests/{id}/status` → `{"status":"accepted"|"rejected"|"merged","by":"..."}`
При `merged` → новый документ/редакция попадает в корпус, кейсы с этим
`rule_key` перепроверяются: если больше не противоречат — флаг снимается.

### 19.5. Что видно в UI

**Сотруднику** — короткая пометка у кейса:
```
[кейс] согласовали за 2 рабочих дня (не регламент — отступление)
       По регламенту: 5 рабочих дней (ТЗ-ЭКЗ-СР01-Р2) — обязательно
```

**Службе качества** — раздел «Предложения»:
```
CR-2026-0007  ТЗ-ЭКЗ-СР01-Р2 · расхождение: 5 дней против 2 на практике
              3 кейса · принято 0 · [Открыть]
```

**В аналитике** — `change_requests`: сколько предложено, принято, отклонено;
какие документы чаще всего расходятся с практикой. Это прямое доказательство
для жюри, что контур **совершенствует саму нормативную базу**, а не только
отвечает на вопросы.

### 19.6. Чего не делать

- Не давать кейсу перевес над регламентом ни в каком случае.
- Не прятать расхождение: сотрудник должен видеть и норму, и практику.
- Не править регламент автоматически — даже «очевидно верным» исправлением.
- Не считать предложением единичный случай: 1 кейс — наблюдение, 3 — сигнал.
  Порог в конфиге (`CR_MIN_CASES`, по умолчанию 3).
- Не терять связь: `case → change_request → новый документ` должна быть
  прослеживаемой в обе стороны.

## 20. Ответ с оговоркой (v1.12)

**Задача от владельца (дословно):** «Если агент не уверен в корректности своих
ответов — он должен дать ответ "с оговоркой".»

До сих пор было два исхода: `answer` и `refusal`. Появляется третий —
**`answer` с полем `caveat`**. Это не отказ и не полноценный ответ: агент
отвечает, но честно говорит, где он не уверен.

### 20.1. Когда ответ идёт с оговоркой

Триггеры — любой из (все измеримые, не «на глаз модели»):

| Триггер | Условие | Что писать в оговорке |
|---|---|---|
| **Низкая уверенность покрытия** | проверка покрытия (§12.2) прошла, но средняя близость утверждений к цитатам ниже `CAVEAT_MIN_COVERAGE` (по умолчанию 0.72) | «формулировка выведена из фрагментов, но прямой цитаты нет» |
| **Конфликт редакций не разрешён однозначно** | две редакции близки по дате вступления, или приоритет неявный | «на дату X действует ред. Y; ред. Z вступает {дата}» |
| **Источник распознан неуверенно** | `ocr_confidence < 0.6` (§9) | «источник — скан, распознан неуверенно, сверьте с оригиналом» |
| **Ответ частичный** | покрыто часть утверждений, остальные отброшены (§12.2 барьер 3) | «отвечено на N из M частей; остальное в базе не найдено» |
| **Источник — только кейс** | регламента нет, ответ по практике (§19.3) | «по практике, регламент вопрос не покрывает» |
| **Единственный источник** | ответ держится на одном фрагменте, подтверждения нет | «единственный источник, подтверждения в других документах нет» |

**Пороги в конфиге**, не в коде: `CAVEAT_MIN_COVERAGE`, `CAVEAT_MIN_SOURCES`.

### 20.2. Формат

```json
event: answer
data: {"short":"Пять рабочих дней (ТЗ-ЭКЗ-СР01-Р2, ред. 2).",
       "caveat":{"level":"low",
                 "reasons":[{"code":"edition_conflict",
                             "text":"Ред. 3 вступает 2027-01-01 — на дату после неё срок изменится"},
                            {"code":"single_source","text":"подтверждения в других документах нет"}],
                 "advice":"Сверьтесь с владельцем регламента перед принятием решения"},
       "has_details":true, "citations":[…]}
```

`level`: `low` — отвечаю уверенно, оговорка информационная; `medium` — стоит
проверить; `high` — лучше не действовать без человека.

**Правило:** оговорка **не отменяет ответ**. Сотрудник получает и ответ, и
предупреждение. Это важно: продукт не должен уходить в отказ при малейшем
сомнении — он должен быть честным.

### 20.3. Оговорка ≠ отказ

| | `answer` + `caveat` | `refusal` |
|---|---|---|
| Есть ответ на вопрос | да | нет |
| Что делает сотрудник | читает и решает | идёт к другому источнику |
| Когда | ответ есть, но уверенность ниже порога | ответа в базе нет |
| Порядок | сначала пытаемся ответить с оговоркой | только когда ответить нечем |

**Важно:** если можно ответить с оговоркой — **не отказываем**. Отказ дороже:
он отправляет человека искать самому. Сначала оговорка, отказ — последнее
средство.

### 20.4. Что видит сотрудник

В ленте чата под кратким ответом — блок оговорки, спокойный, не красный:

```
⚠ Не полная уверенность
   Ред. 3 вступает 2027-01-01 — на дату после неё срок изменится
   Подтверждения в других документах нет
   Сверьтесь с владельцем регламента перед принятием решения
```

Цвет по `level`: `low` — серый, `medium` — янтарный, `high` — оранжевый.
Никогда красный: это не ошибка.

В **Console Lex** — в шаге `verify`:
```
[10/10] Самопроверка   утверждений 3 · покрыто 3 · уверенность 0.68 · ОГОВОРКА (medium)
```

### 20.5. В журнале и аналитике

Запись журнала получает: `caveat_level`, `caveat_reasons[]`.
В аналитике:

```json
"caveats":{"total":9,"by_level":{"low":4,"medium":4,"high":1},
           "by_reason":[{"code":"edition_conflict","count":5},
                        {"code":"single_source","count":4}],
           "answer_rate":{"plain":31,"caveated":9,"refused":6}}
```

`answer_rate` — самая честная метрика продукта: сколько вопросов получили
ответ (полный или с оговоркой) против отказов. Это то, что жюри спросит
первым: «на сколько процентов вопросов вы вообще отвечаете».

### 20.6. Чего не делать

- Не ставить оговорку на каждый ответ «на всякий случай» — обесценит её.
  Только по триггерам из §20.1, с конкретной причиной.
- Не подменять оговоркой нормальный ответ: если уверенность высокая — оговорки нет.
- Не писать в оговорке общие слова («возможны неточности») — только конкретика:
  какой документ, какая дата, чего не хватает.
- Не превращать оговорку в отказ.

## 21. Язык ответа (v1.13)

**Задача от владельца (дословно):** «Агент может ответить сотруднику менее
формальным языком, НО БЕЗ ИЗМЕНЕНИЯ СМЫСЛА.»

### 21.1. Что можно и чего нельзя

| Можно | Нельзя |
|---|---|
| Проще формулировать | Менять формулировку нормы |
| Убирать канцелярит | Убирать условия и исключения |
| Объяснять своими словами | Добавлять варианты («обычно так»), которых нет |
| Разбивать длинное на короткое | Округлять числа, сроки, суммы |
| Начинать с сути | Смягчать оговорку до «наверное» |

**Граница:** переформулировка допустима, если при обратном переводе в
формальный язык получается **тот же** смысл. Не «примерно тот же».

### 21.2. Реквизиты нормы не переформулируются вообще

Числа, сроки, названия, суммы, коды, номера пунктов — **дословно**:

| В документе | В ответе — так | А так — нельзя |
|---|---|---|
| «пяти рабочих дней» | «пять рабочих дней» | «около недели» |
| «не менее трёх лет» | «не меньше трёх лет» | «несколько лет» |
| п. 4 ч.1 ст.93 44-ФЗ | п. 4 ч.1 ст.93 44-ФЗ | «по 44-ФЗ» |
| «АО «Пример-Маш»» | АО «Пример-Маш» | «компания» |

**Правило:** если в предложении есть реквизит — он вставляется как есть, из
цитаты, а не пересказывается.

### 21.3. Два уровня тона

```json
{"short":"Пять рабочих дней — по редакции 2, она с 1 июня.",
 "tone":"plain"}
```

`tone`: `plain` (по умолчанию, разговорно-простой) | `formal` (канцелярский,
как в документе). Переключатель в UI. `formal` — для случая, когда ответ
пойдёт в документ или письмо.

Разница:
- `plain`: «Пять рабочих дней — по редакции 2, она с 1 июня.»
- `formal`: «Согласно редакции 2 (вступила в силу 01.06.2026) срок
  согласования составляет пять рабочих дней.»

Смысл одинаковый, объём разный.

### 21.4. Контроль смысла — программный, не «на глаз»

Барьер §12 (проверка покрытия) **уже** сверяет утверждения с цитатами. Для
`plain` добавляется вторая проверка:

1. **Извлечение якорей.** Из каждого утверждения извлекаются реквизиты:
   числа, даты, суммы, коды, названия документов.
2. **Сверка с цитатой.** Каждый якорь обязан присутствовать в цитируемом
   фрагменте. Отсутствует → утверждение отбрасывается (§12.2 барьер 3).
3. **Запрет усилителей.** Слова «обычно», «как правило», «в большинстве
   случаев» — запрещены, если их нет в цитате. Они меняют модальность нормы
   («обязательно» → «принято»), а это уже изменение смысла.

**Проверка №3 — самая частая утечка.** Модель любит смягчать: «срок согласования
составляет пять дней» → «обычно пять дней». Формально похоже, юридически — ложь.
Регулярка по списку усилителей в `lex/grounding.py`, нарушение — отбрасывание
утверждения.

### 21.5. В оговорке и отказе — наоборот, строже

В блоке `caveat` (§20) и в `refusal` (§12.3) тон **всегда** `formal`.
Смягчать предупреждение нельзя: «возможно, стоит уточнить» вместо «сверьтесь с
владельцем регламента» — это вред.

### 21.6. Чего не делать

- Не менять тон, если это меняет модальность («обязан» → «следует»).
- Не сокращать ответ за счёт исключений: «5 дней» без «кроме случаев закупки
  у единственного поставщика» — неполный ответ.
- Не добавлять эмодзи, шуток, разговорных вставок — «менее формальный» означает
  **понятный**, а не **небрежный**.
- Не позволять модели самой решать, что можно упростить: реквизиты извлекаются
  программно (§21.4).

## 22. Обращение в службу качества — имитация почты (v1.14)

**Задача от владельца (дословно):** «В демо-стенде обращение в службу качества —
имитация обращения на почту.»

Тикет (§18) в демо **выглядит как отправка письма**. Реальной почты нет, но
сотрудник должен увидеть привычный сценарий: письмо ушло, есть номер, есть срок.

### 22.1. Что происходит в демо

```
сотрудник задаёт вопрос
   → агент не нашёл (после 2-3 уточнений)
   → в ленте появляется карточка отправленного письма
   → (демонстрация) переключение на роль «Служба качества»
   → там это же письмо лежит во входящих
```

**Это имитация, и это честно.** В `LIMITS.md` записано: реальной отправки нет,
интеграция с почтовым сервером не реализована.

### 22.2. Карточка «письмо отправлено»

```json
{"ticket":"LEX-2026-0042","channel":"email",
 "email":{"to":"quality@example.invalid",
          "from":"lawyer@example.invalid",
          "subject":"[LEX] Вопрос без ответа в базе: согласование с единственным поставщиком",
          "sent_at":"2026-11-26T11:20:00Z",
          "delivery":"simulated"}}
```

`delivery: "simulated"` — обязательное поле. Оно есть в каждом ответе и в
журнале. Врать «отправлено по SMTP», если SMTP не было, нельзя.

В UI:
```
✉ Письмо отправлено в службу качества
   Кому: quality@example.invalid
   Тема: [LEX] Вопрос без ответа в базе: …
   Номер: LEX-2026-0042 · ответ до 28 ноября
   (демонстрационный режим — реальная отправка не выполнялась)
```

**Приписка про демо-режим обязательна** и видна всегда, не мелким шрифтом.

### 22.3. Входящие службы качества

Экран «Заявки» (§18) в демо дополнительно имеет вид **почтового ящика**:

- список писем: тема, от кого, дата, статус (новое / в работе / отвечено)
- открытие письма — тело: вопрос сотрудника, что агент уже проверил, почему
  не нашлось
- поле «Ответ» — как в почтовом клиенте, кнопка «Отправить»
- после ответа — письмо уходит в «Отвечено», а агент готовит черновик кейса (§16)

Формулировки — почтовые, не тикетные: «Входящие», «Ответить», «Отправлено».
Это ближе к тому, как реально работает служба качества.

### 22.4. Что настраивается

| Параметр | Где | По умолчанию |
|---|---|---|
| Адрес службы качества | `QUALITY_EMAIL` в `.env` | `quality@example.invalid` |
| Адрес отправителя | из роли | `<role_id>@example.invalid` |
| Режим | `EMAIL_MODE` | `simulated` |

**Домен `example.invalid`** — из RFC 2606, зарезервирован под примеры. Никогда
не подставлять реальный адрес: демо публичное.

### 22.5. Если позже подключат настоящую почту

Контракт не меняется — меняется только `EMAIL_MODE: "smtp"` и параметры
соединения. Письмо уже сформировано с темой и телом, интеграция — это транспорт.

**Чего не делать:** не подключать SMTP в спринте. Риск: улетят письма на
настоящие адреса, а демо публичное.

### 22.6. Чего не делать

- Не показывать письмо как «отправлено», если `delivery != "simulated"` и отправки
  не было.
- Не убирать пометку про демо-режим — это защита от обвинения в обмане.
- Не использовать реальные домены в адресах.
- Не имитировать входящие письма от сотрудника, которых он не отправлял.

## 23. Модель прав: чтение единое, запись — только качество и руководство (v1.15)

**Задача от владельца (дословно):** «Права доступа к базе на чтение у
пользователей единые. На редактирование — служба качества и руководство.»

### 23.1. Это ОТМЕНЯЕТ прежнюю модель

До этого в контракте (§4, §11, §12.4) было: документ доступен, если
`department ∈ role.departments` **и** `business_line ∈ role.business_lines`.
Это делало чтение разным для разных ролей.

**Теперь иначе:**

| Действие | Кто | Правило |
|---|---|---|
| **Чтение** (поиск, ответ, цитаты, документы) | **все роли одинаково** | весь корпус, без фильтров |
| **Запись** (кейсы, документы, формы) | `quality`, `director` | только эти две роли |

**Почему это лучше для продукта:** сотрудник не упирается в «нет доступа» на
вопрос, который ему нужен по работе. А целостность базы защищена — править
может не всякий.

### 23.2. Что меняется в коде

**`access.py` — упрощается:**
- `filter_docs()` больше не отбрасывает документы по роли при чтении;
- остаются только две функции: `can_read(role) -> True` (для всех) и
  `can_write(role) -> role in {"quality", "director"}`;
- прежние `role.departments` и `role.business_lines` **не удалять** — они нужны
  для аналитики (кто о чём спрашивает) и для предупреждений в UI, но на выдачу
  не влияют.

**`policy.py` — упрощается:**
- проверка «тема в компетенции базы» остаётся (вопрос про НДС по-прежнему
  `out_of_scope`);
- проверка «роль имеет доступ к документам направления» **убирается** — она
  больше не имеет смысла при едином чтении;
- итог policy: `in_scope` (да/нет) + `business_line` (определено/нет).

**`orchestrator` — шаг `permissions`:**
Он больше не «отбрасывает N документов». Теперь он показывает:
```
[6/10] Права доступа   чтение: полный корпус (27 документов) · запись: недоступна
```
Для роли `quality`/`director`:
```
[6/10] Права доступа   чтение: полный корпус (27 документов) · запись: разрешена
```

**Шаг не исчезает** — он становится информационным. Это важно для жюри: видно,
что права продуманы, а не забыты.

**Отказ `no_access` исчезает из чтения.** Остаются: `out_of_scope`,
`not_in_corpus`, `no_edition_in_force`, `conflict_unresolved`, `ocr_unavailable`.
Если документ существует — его видно всем.

### 23.3. Запись — где именно проверяется

| Действие | Эндпоинт | Требуемая роль |
|---|---|---|
| Добавить кейс | `POST /api/cases` | `quality`, `director` |
| Подтвердить кейс из тикета | `POST /api/tickets/{id}/confirm` | `quality`, `director` |
| Ответить на тикет | `POST /api/tickets/{id}/answer` | `quality`, `director` |
| Взять тикет в работу | `POST /api/tickets/{id}/assign` | `quality`, `director` |
| Предложение об изменении | `POST /api/change-requests/{id}/status` | `director` (только руководство решает) |
| Переиндексация корпуса | `POST /api/ingest` | `quality`, `director` |

Нарушение → `403` с телом `{"error":"write_forbidden","role":"lawyer","need":["quality","director"]}`.

**Читать кейсы, тикеты, предложения могут все.** Писать — только двое.

### 23.4. Что это даёт в демо

**Главный кадр:** один и тот же вопрос от «менеджера» и от «юриста» даёт
**одинаковый** ответ. Раньше бы дал разный — и это выглядело как искусственное
ограничение.

**Второй кадр:** менеджер пробует добавить кейс — кнопка неактивна, подсказка
«Добавление доступно службе качества и руководству». Переключились на
`quality` — кнопка активна. Это нагляднее, чем «нет доступа к документу».

### 23.5. Аналитика сохраняет разрез по ролям

Даже при едином чтении полезно знать, кто о чём спрашивает:
```json
"by_role":[{"role_id":"lawyer","count":20},{"role_id":"manager","count":12}],
"by_business_line":[…]
```
Это остаётся — для «чего не хватает в каталоге» и для приоритизации
обновления регламентов.

### 23.6. Чего не делать

- Не оставлять фильтр по отделам на чтении «на всякий случай» — он противоречит
  требованию и ломает демо.
- Не убирать шаг `permissions` — его информативность полезна.
- Не давать роль `quality` редактировать регламенты — только кейсы, ответы,
  предложения. Регламент правит владелец документа в своей системе, не LEX.
- Не путать «руководство» и «служба качества»: руководство утверждает
  изменения регламентов, качество отвечает на вопросы.
