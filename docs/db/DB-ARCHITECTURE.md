# DB-ARCHITECTURE: как устроена база знаний LEX

Документ описывает **схему** базы: какие сущности в ней есть, какие у них поля и
типы, где они лежат и как по ним искать. Это не перечисление конкретных файлов: состав
корпуса вынесен в приложение и служит примером.

Главное правило базы: **статья — навигационная карта, ответ — из документа**. Ни статья,
ни справочник, ни список не являются источником нормы.

## 1. Слои базы

| Слой | Сущность | Где лежит | Ключ доступа |
|---|---|---|---|
| Реестр | манифест корпуса | каталог корпуса, manifest.json | корень корпуса |
| Тексты | файлы документов | каталог корпуса, файлы по doc_id | doc_id + file |
| Правила | правила с редакциями | раздел conflict_rules манифеста | rule_key + revision |
| Практика | кейсы | var/cases.jsonl | case id |
| Формы | карточки форм | forms/forms.json рядом с корпусом | form_id |
| Навигация | статьи базы знаний | docs/db/articles/*.md | файл статьи |
| Журнал | запросы и ответы | var/journal.jsonl | journal id |
| Заявки | эскалации и тикеты | var/escalations.jsonl, var/tickets.jsonl | esc-NNNN, ticket id |
| Сессии | уточняющие диалоги | var/sessions.jsonl | session_id |

Пути переопределяются переменными окружения: LEX_MANIFEST_PATH, LEX_CASES_PATH,
LEX_JOURNAL_PATH, LEX_ESCALATIONS_PATH, LEX_SESSIONS_PATH, LEX_VAR_DIR. Это позволяет
подставить реальную базу заказчика, не меняя код.

**Правило публичности:** каталоги с документами заказчика (dataset/, corpus-real/,
sample-corpus-real/) перечислены в .gitignore и в публичный репозиторий не попадают.
В git лежат только схема, код и статьи-карты, в которых нет нормативных значений.

## 2. Документ

Запись документа (манифест и модель DocumentMeta):

| Поле | Тип | Смысл |
|---|---|---|
| doc_id | string | идентификатор документа, первичный ключ цитаты |
| title | string | название документа, обычно «Домен (дирекция)» |
| kind | string | вид: регламент, инструкция, порядок, стандарт, чек-лист |
| subtype | string | подвид: регламент, редакция правила, инструкция, … |
| department | string | дирекция-владелец процесса |
| system | string | учётный контур (проектная деятельность, пресейл) |
| owner | string | ответственный за документ |
| version | string | версия документа |
| issued | date | дата выдачи (в реальном корпусе может быть пустой) |
| file | string | файл текста в каталоге корпуса |
| sha256 | string | контрольная сумма текста документа |
| words | int | объём текста |
| sections | list[string] | названия разделов документа |
| content_type | enum | text \| image \| scan \| mixed |
| source | string | происхождение документа (для реального корпуса — заказчик) |

### Чего в схеме реального корпуса нет

Это важно для навигации, и это надо называть прямо:

- **нет поля rule_key** — у документов нет ключа правила;
- **нет поля business_line** — направление не выводится из карточки, его определяет
  политика по словарю терминов;
- **раздел conflict_rules пуст** — редакций правил в корпусе нет. Значит, механизм
  «выбрать действующую редакцию по дате отсчёта» к этому корпусу неприменим: спрашивать
  надо не «какая редакция действует», а «какой раздел регламента применим». Дата
  отсчёта корпуса (as_of) по-прежнему нужна как точка отсчёта, но выбора редакции не
  происходит;
- **нет форм и кейсов** в самом корпусе: заявки, расчёты, ТКП и протоколы ведутся в
  системах (CRM, спецификатор, СЭД, система управления проектами), а кейсы накапливаются
  в var/cases.jsonl в рантайме.

## 3. Редакции правил (механизм есть, данных нет)

Правило хранится как набор редакций: key, field, short, topic, revisions, first_effective;
редакция — revision, doc_id, effective, value, file, sha256.

Правила выбора редакции (работают, когда conflict_rules непуст):

1. дата отсчёта (as_of) обязательна для вопросов о правилах;
2. действует последняя редакция, у которой effective не позже as_of;
3. редакция с датой вступления в будущем не действует;
4. если ни одна редакция не вступила в силу — честный отказ no_edition_in_force;
5. при расхождении редакций приоритет по иерархии видов документов, при равном виде — более
   поздняя дата.

Иерархия видов (сильнее → слабее): приказ и распоряжение, политика, регламент и процесс,
инструкция, методичка и методические указания, описание продукта, правила лицензирования,
стандарт, FAQ и разъяснение.

В реальном корпусе этот слой пуст — см. раздел 2.

## 4. Тип носителя (content_type)

| Значение | Что это | Как цитировать |
|---|---|---|
| text | текстовый документ | цитата из раздела, уверенность высокая |
| image | изображение | цитата невозможна без распознавания |
| scan | скан | цитата только после OCR |
| mixed | часть страниц текстовая, часть — картинки | постранично: текстовая страница цитируется, картинка помечается |

Правила:

- тип определяется по содержимому и наличию текстового слоя, а не по расширению файла;
- распознавание — внешний движок; если его нет, источник помечается «сканы не
  обрабатываются», и честный отказ ocr_unavailable лучше выдуманного текста;
- уверенность распознавания ниже порога помечает цитату как «распознано неуверенно»
  (оговорка, а не отказ);
- в цитате для нетекстового источника доступны: тип, номер страницы, ссылка на превью,
  уверенность распознавания.

В реальном корпусе все документы текстовые.

## 5. Кейсы (практика)

Хранилище: var/cases.jsonl, одна строка — один кейс, дозапись атомарная.

| Поле | Тип | Смысл |
|---|---|---|
| id | string | идентификатор кейса |
| ts | datetime | время наблюдения |
| author_role | string | роль автора |
| author_name | string | автор |
| question | string | как спросили |
| answer_in_practice | string | как было на практике |
| outcome | enum | resolved \| escalated \| rejected \| open |
| linked_docs | list[string] | документы, к которым кейс относится |
| tags | list[string] | метки |
| rule_key | string | правило, к которому кейс относится |
| content_type | enum | тип носителя наблюдения |
| normative | bool | всегда False: кейс не нормативен |
| deviation | string | в чём практика разошлась с документом |
| deviates_from | list[string] | документы, от которых практика отступила |
| confirmed_by | string | кто подтвердил практику |
| escalation_id | string | заявка, если кейс эскалирован |

Правила: кейс участвует в поиске наравне с документами, но помечается как кейс и имеет
приоритет ниже любого нормативного документа; кейс не может отменить регламент; если
регламент тему не покрывает, а кейс отвечает — ответ строится на кейсе с пометкой «по
практике, регламент не покрывает».

В корпусе заказчика кейсов нет: они накапливаются в рантайме.

## 6. Формы

Хранилище: forms/forms.json рядом с корпусом (каталог <corpus_root>/forms/). Файл может
отсутствовать — корпус приходит и без форм.

Запись формы: form_id, title, doc_id (документ-основание), format, business_line, fields.

Поле формы: key, label, type (text | date | money | choice | number), required, pattern,
example, hint, options, min, max, source_doc, source_quote.

Правила: поле появляется только если требование описано в корпусе, иначе в hint
записывается, что формат не описан; каждое поле помнит документ-источник и цитату; при
проверке заполнения проверяются обязательность, формат, значение из справочника,
согласованность с регламентом и полнота.

В реальном корпусе форм нет: заявка на пресейл, расчёт, спецификация, ТКП и протоколы
живут в системах, а не как бланки в базе.

## 7. Статьи базы знаний

Формат: docs/db/ARTICLE-TEMPLATE.md. Рабочий набор: docs/db/articles/*.md, указатель:
docs/db/ARTICLES.md.

Каждая статья — навигационная карта по одному классу документа и обязана содержать:

- тему и суть (3–7 строк);
- «Синонимы / как спрашивают» — включая разговорные и ошибочные формулировки;
- «Что искать в базе» — термины, роли, артефакты и поля для retrieval;
- «Где искать» — класс документа и его реквизиты;
- «Чего в базе НЕТ» — честный пробел;
- «Типичные ловушки»;
- «Пример вопроса»;
- «Примеры в локальном корпусе» — пример с пометкой, что корпус заказчика локальный и в
  публичный репозиторий не попадает;
- обязательные строки: «Ответ берётся из документа-источника, не из этой статьи» и «Если
  источника с таким классом в базе нет — агент обязан сказать, что ответа нет, а не
  собирать из статьи».

В статье не должно быть нормативных значений (сроков, сумм, порогов): статья не
источник ответа.

Термины статей обязаны попадать в словарь направлений (policy.BUSINESS_LINES), иначе
политика не определит направление.

## 8. Контракт ответа

Ответ собирается из найденных источников и сопровождается цитатой: идентификатор
документа, название, редакция, дата вступления, цитата, тип носителя, страница,
уверенность распознавания, признак кейса.

Отказ — не пустое «не знаю»: он называет причину (вне темы базы, класса нет, редакция не
вступила в силу, конфликт не разрешён, распознавание недоступно) и перечисляет, что
искали. Оговорка снижает уверенность, но не превращается в отказ.

## 9. Сокращения и глоссарий

Регламенты заказчика насыщены сокращениями ролей и артефактов (АМ, SS, BDM, TSS, ПА, РП, РСП,
ГИП, АП, ЦК, ТМЦ, ЗИП, ЗП, ЗНИ, РТЗ, ТКП, КП, ТЗ, ПГ, КСУП, УПД, КС-2, КС-3, КИ, ОПЭ, ДС, SLA,
NDA, RFI, HW, ПО, ФОТ, СРО и другие). Правила схемы:

- **файла-глоссария в корпусе нет.** Расшифровки приходят внешним справочником (глоссарий
  владельца передан 26.11.2026), а контекст и ответственность — из текста регламентов. Статьи
  базы знаний ведут по схеме: сокращение → полное название → раздел, где роль или артефакт
  закреплён.
- **словарь направлений знает часть аббревиатур.** У направления «пресейл» есть отдельный
  список сокращений (abbrev), и он ловится только целым словом: короткая подстрока «па»
  поймала бы «паспорт», «компания», «программа».
- **в текстах регламентов встречаются не все сокращения глоссария.** Те, что не встречаются,
  перечислены прямо в статьях-глоссариях: искать по ним в базе нечего, и это надо говорить, а
  не додумывать.
- **одно сокращение в текстах есть, а в глоссарии отсутствует** (ТЗТ) — его надо искать в
  разделе о расчёте, а не расшифровывать по догадке.
- **похожие сокращения не взаимозаменяемы:** технико-коммерческое предложение и коммерческое
  предложение, договор и дополнительное соглашение, акт (общий термин) и формы КС-2 и КС-3.

## 10. Пример: состав локального корпуса

Пример заменяется реальной базой заказчика и целиком лежит вне публичного репозитория
(каталоги dataset/ и corpus-real/ в .gitignore). В примере 4 документа, все текстовые,
дата отсчёта корпуса — 2026-11-26, раздел правил-редакций пуст.

| Идентификатор | Вид | Дирекция | Название | Направление |
|---|---|---|---|---|
| КД-ПД-01 | Регламент | Техническая дирекция | Организация проектной деятельности (Техническая дирекция) | проектная деятельность |
| КД-ПС-02 | Регламент | Дирекция ИБ | Пресейловая деятельность (Дирекция ИБ) | пресейл |
| КД-ПД-03 | Регламент | ДБРЦТ | Проектная деятельность (ДБРЦТ) | проектная деятельность |
| КД-ПД-04 | Регламент | Дирекция ИБ | Проектная деятельность (Дирекция ИБ) | проектная деятельность |

Один домен — три дирекции, поэтому класс документа в статьях задаётся словами
(«пресейл», «проектная деятельность», «внутренняя приёмка»), а не идентификатором:
идентификатор привязан к локальной выгрузке и станет другим в другой базе.
