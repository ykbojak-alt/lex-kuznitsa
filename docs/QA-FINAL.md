# QA-FINAL.md — финальный чек-лист перед сдачей жюри

**Статус:** pre-sprint шаблон (2026-11-25). Заполняется **по факту прогона** перед отправкой
продукта. До старта спринта все пункты — `[ ]`.

**Что это.** Финальный гейт сдачи. Двадцать пунктов по шести критериям Положения
(Приложение 1), плюс отдельные гейты по видео и по репозиторию.

**Как не дублирует соседей:**

| Документ | Уровень | Вопрос |
|---|---|---|
| `docs/ACCEPTANCE-CRITERIA.md` | продуктовый | работает ли каждая функция (P/R/V) |
| `docs/SELF-REVIEW.md` | командный | SR-01…SR-20 по критериям, для себя |
| `docs/VIDEO-CHECKLIST.md` | видео | готов ли файл технически |
| **`docs/QA-FINAL.md`** (этот) | **сдача** | всё ли вместе годится к отправке жюри |

Разница: `SELF-REVIEW` — что мы думаем о себе; `QA-FINAL` — что мы предъявим жюри, с
явным evidence и правом «стоп».

**Основание:** Положение «ИИкузницы», §4.4–4.8, §5.2, Приложение 1 — шесть критериев,
равный вес 0–3, максимум 18; порог рассмотрения в «Путь к витрине» — 12/18 и отсутствие
нуля по технической корректности. Структура критериев — `IIKUZNITZA-sprint-materials.md`
sec 2.

## 0. Правило прохода

- **P0 (блокер):** любой непройденный пункт = сдача не идёт. Ноль по критерию
  «Корректность технической реализации» автоматически исключает из рассмотрения —
  QF-05 не может быть `[ ]`.
- Каждый пункт закрывается **только evidence**, а не намерением: путь к файлу, команда
  и её вывод, таймкод видео, SHA. «Да, работает» без ссылки не принимается.
- Пункт, который проверить не удалось, помечается `N/A` **с причиной**; молчаливое
  `[x]` запрещено.
- Формат отметки: `[x]` — подтверждено; `[ ]` — не подтверждено; `N/A: <причина>`.

> Правило про видео и цифры: любое число в evidence должно быть получено **в этом
> прогоне**. Числа из прошлых отчётов и чужих стендов не переносятся
> (`docs/LIMITS.md` §3).

## 1. Соответствие задаче партнёра (4 пункта)

Партнёр ожидает: поиск ответов по корпоративным документам, цитаты, действующая
редакция, обоснованный отказ, аналитика неудачных поисков и «чего нет в каталоге».

| ID | Пункт | Evidence, который принимается | Отметка |
|---|---|---|---|
| QF-01 | Продукт решает **задачу партнёра**, а не общий чат: принимает вопрос по корпусу и отвечает по документам | Точная формулировка задачи (после брифинга) + кадр/лог ответа именно по корпусу | [ ] |
| QF-02 | Каждый ответ **опирается на источник**: цитата + идентификатор документа + редакция + дата | Скрин ответа с подсветкой источника; запись в журнале с `doc_id`/`revision`/`date` | [ ] |
| QF-03 | **Обоснованный отказ** как штатный результат (не ошибка) | ≥ 3 кейса «нет в корпусе» → структурированный отказ с причиной и «что нужно от пользователя» | [ ] |
| QF-04 | **Действующий документ**: при конфликте редакций выбран действующий, отменённый отброшен | Прогон на конфликтной тройке редакций; в логе видно, какая отброшена и почему | [ ] |
