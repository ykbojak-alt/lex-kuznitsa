## 1. Что должно быть в репозитории

| Блок | Содержимое | Зачем |
|---|---|---|
| `README.md` | название, одно предложение, быстрый старт в 5 команд, скриншот, лицензия | первое, что откроет жюри |
| `ARCHITECTURE.md` | схема слоёв, поток вопроса, логика «действующего документа», границы | критерий «Корректность реализации» |
| `MODEL.md` | **название локальной модели**, размер, лицензия, как поднять, требования к железу | Q9 — модель обязана быть названа |

| `METRICS.md` | своя методика, мини-датасет, результаты, признание что контрольного набора нет | критерий «Соответствие задаче» + честность |
| `LIMITS.md` | что не работает, что mock, что не проверено | критерий «Степень готовности» — честный список повышает доверие |
| код | ingest, индекс, оркестратор, отказ, журнал, UI | собственно продукт |
| `demo/` | скрипт прогона + конфиг `local` | воспроизводимость |
| `sample-corpus/` | **только** обезличенные/синтетические документы | Q13 разрешает хранение; но чужие данные в публичный репозиторий не кладём никогда |

### Чего в репозитории быть не должно

- реальные корпоративные документы заказчика (даже «обезличенные» — до подтверждения, что публикация допустима);
- ключи, токены, `.env`, конфиги с секретами;
- веса моделей (только инструкция по скачиванию + имя);
- внутренние имена компонентов NEXUS, не вошедшие в публичное описание.

## 2. Решение по данным в репозитории

Три варианта, по убыванию риска:

| Вариант | Что кладём | Риск | Рекомендация |
|---|---|---|---|
| A | реальный корпус заказчика | высокий: даже «обезличенные» материалы могут быть не для публикации | **нет** |
| B | синтетический корпус в нашей структуре + генератор | низкий, воспроизводимо | **да, основной** |
| C | только схема + скрипт загрузки, корпус отдельно | нулевой, но жюри не запустит из коробки | как дополнение к B |

**Вывод:** в репозиторий — синтетический корпус с теми же полями и форматами, что ТЗ 26.11. Демо и видео — на данных задачи локально, без публикации.

## 3. Одностраничное описание продукта

Структура уже есть в `IIKUZNITZA-sprint-materials.md` §2 (шесть критериев Приложения 1) — она верна, менять не нужно. Отличия для RAG-продукта:

**Заголовок:** `[Название] — агент, который отвечает по регламентам и умеет сказать «не знаю»`

**Ключевые абзацы, которые обязаны быть:**

1. **Модель.** «Работает на локально развёрнутой модели [название], [размер], [лицензия], без обращений к внешним LLM API.» — закрывает Q9 и Q11 одной фразой.
2. **Агентность.** «Один вопрос проходит не менее N шагов: разбор, поиск, определение действующей редакции, разрешение конфликта, сборка с цитатами, самопроверка. Каждый шаг виден в интерфейсе и записан в журнал.» — прямо в критерий «Агентность решения».
3. **Обоснованный отказ.** «При неразрешимом противоречии агент отказывается от однозначного ответа, перечисляет конфликтующие документы с редакциями и объясняет причину. Это штатный результат, а не ошибка.» — Q6.
4. **Логика действующего документа.** Таблица приоритетов из §4 архитектуры, коротко. «Иерархию заказчик не задавал — мы её формализовали и обосновали.»
5. **Аналитика.** «Журнал агрегируется в отчёт: отказы и их причины, вопросы без выдачи, темы, которых нет в каталоге.» — дословно из ожидаемого результата заказчика.
6. **Экономика.** «Локальный инференс и векторный поиск — нулевая стоимость запроса; кэш повторных обращений. Методика расчёта: …» — Q12.
7. **Границы.** Честный список: что mock, что не проверено, чего нет.

**Запрещено в описании:** слово «production-ready», «полная интеграция», любые метрики без указания, на каком наборе они получены.
