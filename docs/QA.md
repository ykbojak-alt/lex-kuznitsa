# QA — чек-лист приёмки финалистов «ИИкузницы»

**Статус документа:** шаблон приёмки. Заполняется **после спринта** по фактическому
snapshot. Не публикуется как доказательство реализованного продукта до заполнения.

**Основа критериев:** Положение ИИкузницы §4.4–4.8, §5.2 и Приложение 1. Структура
разделов повторяет skeleton одностраничного описания из материалов спринт-подготовки (§2).
Проверяемый продукт в этом экземпляре — **LEX** (см. `docs/ONE-PAGE.md`).

**Как пользоваться**
1. Один экземпляр на финалиста (команду). Заполняет **ответственный за приёмку**, не авторы команды.
2. Проверка идёт по **зафиксированному состоянию**: указывается commit SHA и точные команды.
3. Каждый пункт имеет вердикт: `PASS` / `FAIL` / `НЕ ИЗМЕРЕНО` + ссылка на evidence.
4. Любое числовое утверждение сопровождается источником. **Если измерения не было — пишем «не измерено»,
   а не подставляем условные суммы и оценки «на глаз».**
5. Итоговый вердикт по разделу выводится из пунктов: есть `FAIL` → `FAIL`; нет `FAIL`, но есть
   `НЕ ИЗМЕРЕНО` → `PASS С ОГОВОРКАМИ`; иначе `PASS`.

> Правило честности: пункт, который нельзя проверить на зафиксированной версии, нельзя отмечать `PASS`.
> Отметка `PASS` означает «проверено и подтверждено evidence», а не «заявлено в описании».

## 1. Соответствие задаче партнёра

*Цель: убедиться, что прототип решает задачу партнёра, а не смежную задачу.*

- [ ] Задача партнёра процитирована **дословно**, с указанием целевого пользователя.
- [ ] Требования задачи разложены на проверяемые пункты (ID/формулировка → flow → evidence).
- [ ] Каждое требование имеет явную связь: «требование → шаг демо → артефакт/лог → результат».
- [ ] Показан **пользовательский сценарий целиком**, а не отдельные кирпичики.
- [ ] Проверено, что ответы строятся **по данным задачи**, а не по заготовленным строкам.
- [ ] Отмечено, что из задачи **не покрыто** (осознанные пробелы, а не случайные).
- [ ] Нет обещаний функций, которых нет в snapshot.

## 2. Корректность технической реализации

*Цель: показать, что реализация работает, и честно описать её пределы.*

- [ ] Описана схема потока данных: от входа вопроса до результата (индекс, поиск, генерация).
- [ ] Проверки выполнены на **зафиксированной версии**: указан commit SHA и точные команды.
- [ ] Приведён **фактический** итог прогона (PASS/FAIL по шагам), а не ожидаемый.
- [ ] Проверено поведение при отказе: нет доступа, пустой результат, ответ не найден.
- [ ] Проверено, что в ответе **нет выдуманных фактов** (цитаты, источники, ссылки на документы).
- [ ] Проверена защита данных: чужие/чувствительные документы не попадают в выдачу и в логи.
- [ ] Зафиксировано поведение при таймауте/обрыве/отсутствии сети.
- [ ] Логи и трейсы не содержат секретов (ключи, токены, содержимое приватных документов).

## 4. Степень готовности продукта

*Цель: отделить показанное от заявленного.*

- [ ] Есть раздел «реализовано и показано» — только то, что подтверждено на текущем snapshot.

- [ ] Есть явный список «не реализовано» — без смягчений.

- [ ] Зафиксирована версия: commit SHA + образ/окружение (Python, зависимости).

## Стоп-условия

Приёмка **не завершается**, если выполнено хотя бы одно:

- [ ] В evidence видны секреты или содержимое документов, к которым у проверяющего нет доступа.
- [ ] Описание продукта обещает функциональность, отсутствующую в snapshot.
- [ ] Числа в разделе экономики не имеют источника (вместо них должно стоять «не измерено»).
- [ ] Видео/демо собрано из разных прогонов, а не из одного непрерывного.
- [ ] Зафиксированная версия не собирается/не запускается с чистого состояния.
- [ ] В продукте не раскрыты заранее созданные компоненты и их лицензии.
