## 1. Что оценивают

Шесть критериев Приложения 1, **равный вес** — нельзя «выиграть» на одном.

| Критерий | Что даёт балл | Где в архитектуре |
|---|---|---|
| Соответствие задаче партнёра | анализ неудачных поисков, «чего нет в каталоге», лог действий, аналитика по поиску | §7 |
| Корректность реализации | поток данных, воспроизводимость, обработка отказов | §3, §6 |
| Потенциал внедрения | путь к пилоту, зависимости, интеграции | §10 |

| **Агентность решения** | 0 баллов за один запрос к модели, **3 балла за автономного многошагового агента** | §5 |

**Главный вывод:** «Агентность» — самый дешёвый рычаг. Один вызов LLM = 0. Значит в демо обязателен **видимый многошаговый цикл с логом шагов** (§5).

## 2. Продукт в одном абзаце

Агент отвечает на вопросы сотрудников по корпусу регламентов и правилам лицензирования, включая вопросы, затрагивающие несколько документов. Он не «делает один запрос к модели», а ведёт цикл: разбирает вопрос на подвопросы → ищет по нескольким каналам → определяет, какая редакция действует → при конфликте дочитывает и сопоставляет → собирает ответ с цитатами и номерами редакций → при неразрешимом конфликте отказывается с указанием источников и причины. Каждый шаг пишется в журнал; журнал агрегируется в аналитику «чего не нашли».

**Что НЕ делаем:** действий по итогам вопроса (не требуется, Q14), отправки писем/тикетов, полной интеграции с корп. системами (имитация допустима).

## 3.2. Поток одного вопроса

1. **normalize** — вопрос → структура: сущности, тип (право/лицензия/процедура), признаки мульти-регламентности.
2. **decompose** — LLM разбивает вопрос на 1..N подвопросов (это первый видимый шаг «агентности»).
3. **retrieve per subquestion** — гибридный поиск: BM25 (точные термины, номера приказов) + векторный (смысл) + фильтр по метаданным. Rerank top-K.
4. **resolve** — для каждого найденного фрагмента определить **действующую редакцию** по логике §4.
5. **conflict check** — если два действующих фрагмента противоречат: дочитывать соседние чанки, искать документ-основание, пробовать иерархию. Если не разрешилось — кандидат на отказ.
6. **compose** — ответ строго из собранных цитат; каждая фраза ссылается на `doc_id + редакция + фрагмент`.
7. **refuse** (если нужно) — «не могу ответить однозначно» + список конфликтующих источников + причина.
8. **log** — весь цикл: шаги, инструменты, что нашлось/не нашлось, время, токены.

Каждый шаг — отдельная запись журнала. Это же и есть evidence для критерия «Агентность».

## 4. Логика «действующего документа» — наше предложение

Заказчик иерархию не задаёт (Q2, Q5) → предлагаем и обосновываем. Иерархия должна быть **объявлена в UI**, чтобы жюри видело правило, а не магию.

**Уровни приоритета (от сильного к слабому):**

| Ур. | Тип документа | Обоснование |
|---|---|---|
| 1 | Приказ / распоряжение | Акт прямого действия, отменяет и изменяет нижестоящие |
| 2 | Политика (верхнеуровневая) | Задаёт рамку, на неё ссылаются регламенты |
| 3 | Регламент / процесс | Описывает порядок, подчинён политике |
| 4 | Инструкция / методичка | Детализирует регламент |
| 5 | Описание продукта / правила лицензирования | Прикладной документ, действует в своей области |
| 6 | FAQ / разъяснение | Не нормативный, только вспомогательный |

**Внутри уровня:**
1. Больше `effective_date` (вступил в силу позже) — сильнее.
2. Больше `revision` — сильнее.
3. Есть явная отмена («признать утратившим силу») — предыдущий выводится из действия.
4. Явное указание «настоящий документ имеет приоритет над X» — перебивает уровень.

**Формализация:** вес документа = `f(уровень, дата, редакция, явные отмены, область действия)`. Не «выбрать самый свежий», а «выбрать самый сильный действующий в области вопроса».

**Область действия** — критично для мульти-регламентных вопросов: если вопрос про лицензирование продукта X, то общий регламент и описание продукта X оба действуют, а «действующий» определяется по предмету, а не по дате. Отсюда — не один ответ, а **ответ по каждому предмету** + сводка.

**Обоснование для жюри (одна фраза):** «Мы не угадываем, какой документ главнее — мы формализуем правовую иерархию актов и показываем правило в интерфейсе, чтобы специалист мог его проверить».

**Риск:** ТЗ 26.11 может дать реальные поля и признаки; тогда таблицу приоритетов правим по факту, но каркас `f(уровень, дата, редакция, отмены, область)` остаётся.

## 5. Агентный цикл — как получить 3 балла, а не 0

Критерий: 0 = один запрос к модели, 3 = автономный многошаговый агент.

**Что должно быть видно на экране** (это же — сценарий видео):

```
[1/7] decompose      вопрос → 2 подвопроса                    0.4 c
[2/7] retrieve       q1: BM25 12 · vector 10 → rerank 5       0.9 c
[3/7] retrieve       q2: BM25  7 · vector  9 → rerank 4       0.8 c
[4/7] resolve        5 фрагментов → 4 действующих, 1 отменён  0.1 c
[5/7] conflict       регламент vs приказ → приказ сильнее     0.3 c
[6/7] compose        ответ из 3 цитат                         2.1 c
[7/7] verify         все утверждения покрыты цитаты         ок
```

**Правила, чтобы цикл был настоящим, а не декоративным:**
- Модель **сама** выбирает следующий шаг через tool calls (поиск / дочитывание / отказ), а не жёсткий скрипт.
- Есть **бюджет шагов** (например, 8) и **условие остановки** — иначе «автономный агент» превращается в бесконечный цикл.
- Каждый шаг — реальный вызов инструмента; в журнале видно аргументы.
- Если модель может ответить сразу — она всё равно проходит minimum path (decompose + retrieve + verify). Один запрос = 0 баллов, поэтому минимум три шага — архитектурное требование, не украшение.

**Human gate:** отказ от ответа и «низкая уверенность» — точка, где агент передаёт человеку. Это и есть контролируемая автономность.

## 6. Обоснованный отказ как фича

Заказчик прямо разрешил (Q6): «Обоснованный отказ с указанием источников и причины ничему не противоречит».

**Триггеры отказа:**
- два действующих документа одного уровня противоречат, и правило приоритета не разрешает;
- ни один фрагмент не проходит порог релевантности;
- ответ требует документа, которого нет в корпусе;
- цитаты не покрывают ключевое утверждение ответа.

**Формат отказа (не «ошибка», а результат):**

```
Не могу ответить однозначно.

Причина: противоречие между действующими документами.
· Регламент «Лицензирование», ред. 3 (12.03.2026): срок 30 дней
· Описание продукта X, ред. 5 (04.06.2026): срок 45 дней
Оба действующие, уровень 5 и 3, приоритет не разрешает.

Что нужно от вас: указать, какая редакция применяется к продукту X.
```

Это делает отказ **полезным**, а не пустым. И закрывает вопрос «действующего документа», который заказчик ждёт от команды.

## 7. Аналитика поиска (критерий «Соответствие задаче партнёра»)

Заказчик в ожидаемом результате прямо перечислил: «агент анализирует неудачные поиски, что ищут клиенты и чего нет в каталоге, логирует действия и показывает аналитику по поиску».

**Экран аналитики (обязателен, иначе теряем баллы):**

| Блок | Содержимое |
|---|---|
| Отказы | сколько, по каким причинам, какие документы конфликтуют |
| Неудачные поиски | вопросы с нулевой выдачей после rerank |
| «Чего нет в каталоге» | темы вопросов, которые не покрывает ни один документ |

Данные — из журнала (§3.2, шаг 8). Ничего дополнительно не собираем: аналитика = агрегат по журналу.

## 8. Модельный слой: локальная модель как целевая поставка

**Требование правил:** решение и демонстрация жюри — в изолированном контуре, локально развёрнутая модель, названная в описании продукта (Q9, Q11).

### 8.1. Три профиля, одна конфигурация

Всё общение с моделями — через **один** интерфейс (Anthropic/OpenAI-совместимый `/v1/messages` или `/v1/chat/completions`). Профиль выбирается конфигом, код не меняется:

```json
{
  "profile": "local",
  "llm":       { "base_url": "http://127.0.0.1:8080/v1", "model": "<локальный кандидат>" },
  "embedding": { "base_url": "http://127.0.0.1:8081/v1", "model": "<локальная embedding>" },
  "reranker":  { "base_url": "http://127.0.0.1:8082", "model": "<локальный reranker>" }
}
```

| Профиль | Назначение | Честность |
|---|---|---|
| `local` | **целевая поставка**, съёмка видео, демо жюри | то, что заявлено в описании продукта |
| `dev` | разработка в спринте (быстрее итерации) | раскрывается в описании как этап разработки |
| `mock` | тесты, CI, детерминированный прогон | без сети |

**Правило:** **видео снимается на `local`**. Иначе придётся переснимать после вопроса жюри «а модель-то локальная?».

### 8.2. Кандидаты под наше железо

Железо (наше, не организаторов): RTX 3050 **8 GiB VRAM**, 31.9 GiB RAM, i7-3770.

| Роль | Кандидат | Размер | Почему |
|---|---|---|---|
| LLM | Qwen3-8B-Instruct, GGUF Q4_K_M | ~5 GB | влезает в 8 GB, сильный русский, Apache-2.0 |
| LLM (fallback) | Qwen3-4B-Instruct Q5 | ~3 GB | если 8B не хватает по скорости/VRAM |
| Embedding | bge-m3 (или multilingual-e5-base) | ~2 GB / ~0.5 GB | мультиязычный, работает и на CPU |
| Reranker | bge-reranker-base | ~1 GB | заметно поднимает точность top-K |

**Важно:** выбор фиксируется в описании продукта **одним** названием (Q9). Fallback держим в резерве, но не заявляем как второй.

### 8.3. Экономика (критерий 6)

Локальный инференс = **нет платы за токены**. Аргумент в питче:
- LLM, embeddings, rerank — локально, нулевая стоимость запроса;
- кэш ответов и кэш эмбеддингов → повторный вопрос стоит ~0;
- стоимость = только амортизация железа; считаем честно и пишем «метод расчёта», а не выдуманную сумму.

Это сильный аргумент против облачных конкурентов — заказчик сам поставил экономичность критерием (Q12).

## 9. Метрики и методика оценки

Контрольного набора нет (Q4), методика не задана (Q15). Значит:

1. **Свой мини-датасет** — 25–40 вопросов по корпусу, с ручными эталонами: `{вопрос, ожидаемые doc_id+редакция, ожидаемый ответ (кратко), тип: простой / мульти-регламентный / конфликтный / непокрытый}`. Обязательно включаем «непокрытые» — на них проверяется отказ.
2. **Три оси оценки**, каждая вручную по шкале 0–2:
   - **полнота** — покрыт ли ответ эталоном;
   - **корректность источника** — верные ли документы и редакции;
   - **обоснованность** — есть ли цитаты; для отказов — корректна ли причина.
3. **LLM-судья** — второй проход тем же локальным LLM с фиксированным промптом и temperature=0. Даёт воспроизводимость, но **не заменяет** ручную разметку: в описании пишем «судья + ручная проверка выборки».
4. **Автоматические метрики** (без человека): доля ответов с полной цитатной опорой, доля корректных отказов, p50/p95 времени, число шагов агента, стоимость.

**Честность:** в описании пишем «контрольного набора от заказчика нет, метрики на собственном dev-наборе из N вопросов» — это сильнее, чем выдуманная цифра.

## 11. Риски

| Риск | Удар | Мера |
|---|---|---|
| Локальная модель на 8 GB VRAM медленная → видео не влезает в 3 мин | высокий | Qwen3-4B fallback; ответы короткие, шаги кэшируются на предзаписи? **нет** — видео одним дублем, поэтому сначала замер времени |
| ТЗ 26.11 даст неожиданные форматы (сканы без OCR) | высокий | закладываем OCR-слой в ingest как опцию; если сканов нет — не разворачиваем |
| Корпус большой → индексация не успевает | средний | чанкинг + инкрементальный индекс; при >N документов — префильтр по метаданным |
| Жюри просит живое демо в изолированном контуре | **высокий** | профиль `local` + офлайн-бандл (бинарь инференса + веса + wheels) собран заранее |
