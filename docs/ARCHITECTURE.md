# LEX: архитектура

Описание соответствует коду v1.16 (стенд `1.14.0`). Документ отвечает на три
вопроса: из чего состоит система, что происходит с вопросом от ввода до ответа,
и где пайплайн может отказать. Всё остальное — ссылки.

- Потребитель документа — инженер и член жюри, которому нужно проверить
  утверждения по коду, а не поверить на слово.
- Дата сверки: 27.11.2026. Если документ расходится с кодом — прав код.

---

## 1. Из чего состоит

Три слоя и два внешних сервиса. Внешние — потому что их состояние LEX не
контролирует и должен переживать их отказ.

```
┌───────────────────────────────────────────────────────────────────────┐
│  КЛИЕНТ — src/web (классические скрипты, без сборщика)                 │
│  app.js · progress-view.js · console-view.js · lex.css                │
│  Вопрос → лента шагов → ответ с цитатами → оговорка → уточнение/заявка│
└───────────────────────────────┬───────────────────────────────────────┘
                                │  SSE: event: step|answer|refusal|clarify|escalate|done
┌───────────────────────────────▼───────────────────────────────────────┐
│  HTTP — src/api (FastAPI)                                             │
│  app.py     маршруты, превращение Signal → SSE-кадр                   │
│  config.py  пути, адреса, .env — единственная точка чтения окружения  │
│  probes.py  доступность модели/эмбеддера/реранкера для /api/health     │
│  Логики RAG здесь нет: слой только вызывает ядро и сериализует.        │
└───────────────────────────────┬───────────────────────────────────────┘
                                │
┌───────────────────────────────▼───────────────────────────────────────┐
│  ЯДРО — src/lex (не знает про HTTP)                                   │
│  orchestrator.py  каскад шагов, гейт, сборка ответа, эскалация        │

│  corpus.py        разбор корпуса → чанки (600 токенов, перекрытие 80) │
│  grounding.py     проверка цитат: близость, усечение, covered_text    │
│  access.py        модель прав: роли из манифеста, фильтр по отделу    │
│  dialogue.py      уточнения (2–3 итерации) и эскалация                │
│  policy.py        компетенция и направление бизнеса                   │
│  editions.py      действующая редакция (шаги resolve/conflict)        │
│  llm.py           один вызов модели, повторы, бюджеты токенов         │
│  models.py        StepKey/STEP_ORDER, схемы событий                   │
└───┬────────────┬────────────┬────────────┬────────────────────────────┘
    │            │            │            │

│ ЖУРНАЛ  │ │ КЕЙСЫ    │ │ ЗАЯВКИ   │ │ КОРПУС                  │
│journal  │ │cases     │ │tickets   │ │corpus-real/manifest.json│
│.jsonl   │ │.jsonl    │ │.jsonl    │ │ + документы + формы     │
│var/     │ │var/      │ │var/      │ │ (в .gitignore)          │
└─────────┘ └──────────┘ └──────────┘ └─────────────────────────┘
    ▲

┌───┴───────────────────────────────────────────────────────────────────┐
│  ВНЕШНИЕ СЕРВИСЫ                                                      │
│  LLM: NexusLink на sage-pl (слот маршрутизируется на стороне шлюза)   │
│  embed :8081 bge-m3 · rerank :8082 bge-reranker-base — локальные, CPU  │
└───────────────────────────────────────────────────────────────────────┘
```

**Что внешне, а что наше.** Модель — внешняя; её отказ LEX переживает (отказ
или повторы, но не падение). Эмбеддер и реранкер — локальные, но отдельными
процессами: их отказ LEX тоже переживает — деградацией до BM25. Это осознанная
граница: сбой чужого сервиса не должен обнулять ответ, он должен быть виден.

## 2. Путь вопроса: каскад

Одиннадцать ключей шагов зафиксированы в `STEP_ORDER`
(`src/lex/models.py:34-46`). На реальном корпусе видимых шагов **девять**:
`resolve` и `conflict` пропускаются, когда в манифесте нет правил редакций
(`_has_rules()`, `orchestrator.py:450-464`). В `corpus-real` правил 0, в
`sample-corpus` — 3, поэтому там шагов одиннадцать.

```
  ВОПРОС + роль_id
        │
        ▼
 ┌─────────────────┐
 │ 1 accept        │  принимает вопрос, фиксирует роль и дату отсчёта
 └────────┬────────┘
          ▼
 ┌─────────────────┐
 │ 2 policy        │  компетенция + направление бизнеса
 └────────┬────────┘
          ├──── не наша компетенция ──► ОТКАЗ out_of_scope (без эскалации)
          ▼
 ┌─────────────────┐
 │ (clarify)       │  параметров не хватает → УТОЧНЕНИЕ, не шаг, поток закрыт
 └────────┬────────┘
          ▼
 ══════════ дальше идёт _run_stages ══════════
 ┌─────────────────┐
 │ 3 decompose     │  вопрос → подвопросы (без модели, по союзам)
 └────────┬────────┘
          ▼
 ┌─────────────────┐
 │ 4 inspect       │  текст N · картинки N · сканы N · смешанные N
 └────────┬────────┘
          ▼
 ┌─────────────────┐
 │ 5 retrieve      │  search_many → фильтр прав → rerank → ГЕЙТ
 └────────┬────────┘
          │            гейт: предмет ≥ 0.75 И близость ≥ 0.50
          ├── предмет не найден ──► кейс из практики? ──► ОТВЕТ по кейсу
          │                      └──────────────────► СТОП, эскалация
          ▼
 ┌─────────────────┐
 │ 6 cases         │  поиск по кейсам из практики
 └────────┬────────┘
          ▼
 ┌─────────────────┐
 │ 7 permissions   │  граница чтения по отделу (dropped считает фильтр)
 └────────┬────────┘
          ▼
 ┌─────────────────┐        ┌─────────────────┐
 │ 8 resolve       │───────►│ 9 conflict      │   только если есть правила
 └────────┬────────┘        └────────┬────────┘   редакций в манифесте
          └────────────┬─────────────┘
                       ▼
 ┌─────────────────┐
 │ 8′ compose      │  ОДИН вызов модели; повторы по опоре на цитаты
 └────────┬────────┘        (на sample-corpus это шаг 10)
          │            нет фрагментов ──► ОТКАЗ + заявка
          ▼
 ┌─────────────────┐
 │ 9′ verify       │  проверка цитат, усечение, оговорка
 └────────┬────────┘        (на sample-corpus это шаг 11)
          │            ничего не подтвердилось ──► ОТКАЗ + заявка
          ▼
        ОТВЕТ с цитатами, оговоркой и уверенностью
```

Номера — те, что видит пользователь в ленте (`N из 9`). На `sample-corpus`,
где правила редакций есть, `compose` и `verify` становятся шагами 10 и 11.

`clarify` — особый случай: он занимает **третью** позицию вместо `decompose`
(`_clarify_step(3, state)`) и закрывает поток, поэтому в ленте видно 3 шага из
9. Это не обрыв: каскад остановлен по своей воле, и следующий кадр — карточка
уточнения, а не шаг. `total` при этом остаётся 9 (`_total() = len(STEP_ORDER)
− 2`), то есть счётчик не доходит до конца — по ленте это читается как
«остановились на третьем», и карточка уточнения объясняет почему.

Тот же `_total()` даёт 11 на `sample-corpus`: правила редакций есть, шаги
`resolve`/`conflict` не пропускаются.

### Почему гейт стоит там, где стоит

Гейт находится **внутри** шага `retrieve`, после фильтра прав и после
реранка, но **до** `compose`. Три следствия, каждое намеренное:

1. **Ни одного лишнего вызова модели.** Если нормы нет, `compose` не
   вызывается — расход нулевой.
2. **Фильтр прав раньше гейта.** Иначе гейт нашёл бы предмет в чужом
   фрагменте, каскад пошёл бы дальше, и `compose` собрал бы ответ по
   документу, которого роль не должна видеть.
3. **Кейс проверяется до остановки.** Вопрос, который регламент не покрывает,
   может закрываться кейсом из практики; если останавливаться раньше, полный
   цикл дообучения не работает — тот же вопрос снова уходит в эскалацию.

## 3. Где пайплайн может отказать

Таблица для проверки на демо: каждая строка — реальное место в коде, где
каскад сворачивает не туда. «План Б» — что делает система, а не как чинят.

| # | Шаг | Что ломается | Как выглядит | Поведение |
|---|---|---|---|---|
| 1 | 2 policy | Вопрос вне компетенции организации | Отказ `out_of_scope` | Отказ с объяснением, **без** заявки: службе качества нечего разбирать в вопросе про НДС |
| 2 | 3 clarify | В вопросе нет предмета (заказа, договора, поставщика) | Карточка уточнения | Уточнение, поток закрывается; модель не тратится |
| 3 | 6 retrieve | Эмбеддер недоступен | в шаге «вектор 0» | `EmbeddingError` ловится, поиск идёт по BM25 — не падение |
| 4 | 6 retrieve | Гейт: предмет < 0.75 или близость < 0.50 | «предмет вопроса не найден» | Кейс из практики → иначе стоп и эскалация |
| 5 | 6 retrieve | Вопрос называет документ прямо | Гейт не режет даже при промахе | `_DOC_REF` распознаёт «в документе Регламент „X"», `КД-`/`ТЗ-` коды |
| 6 | 8 permissions | Роль чужая для всех найденных документов | «скрыто по отделу N» | Пусто после фильтра → `not_in_corpus`, **не** `no_access` |
| 7 | 11 compose | Модель вернула пустой `content` | `finish_reason: length` | Повтор с потолком до 32768; пауза на 429 |
| 8 | 11 compose | Оба вызова сорвались по сети | `LLMError` с текстом | Кадр ошибки **с причиной**, а не «не понял» |
| 9 | 12 verify | Модель написала без цитат | «0 подтверждено» | Второй разбор построчно; если и он пуст — отказ + заявка |
| 10 | 12 verify | Часть утверждений без цитат | «отброшено N» | Усечение до покрытых, ответ отдаётся короче |
| 11 | 12 verify | Всё отброшено | Пустая строка | Отказ + заявка: пустой «ответ» хуже отказа |

Строки 9–11 — не гипотетические: 26.11.2026 `compose` дал ответ с 96 % опоры,
`verify` насчитал 0 утверждений и увёл в уточнение; по этому случаю в
`_stage_verify` появился повторный разбор (`orchestrator.py:974-998`).

## 4. Модель

**Основной путь — NexusLink** на `sage-pl`: внешний шлюз, который
маршрутизирует слот на провайдера. Модель называется в описании продукта, как
требуют правила. Код LEX не знает, какой провайдер за слотом: адрес и имя слота
приходят из `.env` (`NEXUS_LINK_BASE_URL`, `NEXUS_LINK_MODEL`,
`NEXUSLINK_KEY`).

**Один вызов модели на вопрос.** Не «один вызов в среднем» — ровно один
успешный: замер `calls: 1`, 4 778 токенов (3 207 prompt + 1 571 completion).
Повторы не считаются вторым вызовом «на ответ» — это механизм устойчивости,
второй вызов происходит только когда первый сорвался.

**Бюджеты (`src/lex/llm.py`).** Три константы и правило повтора:

| Что | Значение | Зачем |
|---|---|---|
| `DEFAULT_MAX_TOKENS` | 16384 | рассуждение + ответ должны уместиться оба |
| `RETRY_BUDGETS` | 16384 → 32768 | упёрлись в `length` — второй раз с большим потолком |
| `RATE_RETRIES` / пауза | 3 / 3 с | 429 апстрима (NexusLink отдаёт его как 502) лечится паузой, не бюджетом |
| `COMPOSE_ATTEMPTS` | 2 | два вызова, берём лучший по опоре на цитаты |

**Что наше, а что нет.** Эмбеддинги — локальный `bge-m3` (1024), реранк —
локальный `bge-reranker-base`; оба под MIT. Локальная LLM не используется.
Подробности — `docs/MODEL.md`; лицензии — `docs/COMPONENTS.md`.

## 5. Права чтения: роли = отделы (v1.16)

Требование заказчика — разграниченный доступ на чтение. Роли не перечислены в
коде: они выводятся из `manifest.json` корпуса (`lex.access.roles_for_corpus`).
На реальном корпусе это `technical` (Техническая дирекция), `ib` (Дирекция ИБ),
`dbrct` (ДБРЦТ) плюс сквозные `quality` и `director`.

| Слой | Где | Что делает |
|---|---|---|
| Модель | `src/lex/access.py` | `filter_docs`, `case_allowed`, `roles_for_corpus` |
| Каскад | `orchestrator._filter_access` | отсекает чужие фрагменты **до** гейта предмета |
| HTTP | `api/core.filter_documents`, `/api/roles` | те же числа, что в каскаде |
| UI | `app.js` | «Дирекция ИБ · 2 из 4» на чипе роли |

**Режим `department_read`.** Документ виден, если его отдел входит в
подразделения роли; `director` и `quality` видят всё. Запись — `quality` и
`director` (`WRITE_ROLES`).

**Старые алиасы.** `lawyer` и `it` → `technical` (`ROLE_ALIASES`), но в списке
`/api/roles` их нет: это совместимость для старых клиентов, а не роль для UI.

**Неизвестная роль — fail-closed.** Опечатка в `role_id` даёт пустой список,
а не весь корпус.

**Пустой результат — это `not_in_corpus`, а не `no_access`.** Фильтр отдаёт
`by_reason`, чтобы шаг показывал настоящую причину. Молчаливый полный доступ по
ошибке — та дыра, из-за которой v1.15 пришлось отменять.

## 6. Данные: корпус, кейсы, журнал

| Что | Где | Формат | В git |
|---|---|---|---|
| Корпус | `corpus-real/` (по умолчанию), `sample-corpus/` | `manifest.json` + документы.md + формы | **нет** (`.gitignore`) |
| Индекс | `.lex-index.npz` рядом с корпусом | кэш BM25 + вектора | нет |
| Журнал | `var/journal.jsonl` | append-only JSONL | нет (`var/`) |
| Кейсы | `var/cases.jsonl` | append-only JSONL | нет |
| Заявки | `var/tickets.jsonl` | append-only JSONL | нет |

Корпус по умолчанию — `corpus-real` (`src/api/config.py:21`,
`orchestrator.py:66`). Синтетика не подставляется молча: стенд обязан
отвечать по документам заказчика, а не по фикстуре.

Корпус и `dataset/` не попадают в публичный репозиторий и не копируются на
чужую машину при деплое (`deploy/README.md`): это данные третьей стороны.

**Чанкинг** (`src/lex/corpus.py`): 3 символа на токен, чанк 600 токенов,
перекрытие 80, разбиение по заголовкам `##`. На корпусе заказчика — 4 документа,
154 чанка.

**Аналитика** — агрегат по журналу, отдельного хранилища нет: `GET
/api/analytics` считает по `journal.jsonl` число запросов, отказы по причинам,
среднюю и p95 задержки.

## 7. Устойчивость: что переживает отказ

Таблица для вопроса «а если?». Каждая строка — механизм в коде, а не обещание.

| Отказ | Механизм | Где |
|---|---|---|
| Модель недоступна или отвечает пусто | повторы с ростом потолка, пауза на 429, `LLMError` с текстом | `llm.py`, `_ask_model_with_retry` |
| Эмбеддер не поднят | `EmbeddingError` → поиск по BM25, каскад идёт | `index.py`, `search()` |
| Реранкер не поднят | порядок гибрида сохраняется | `orchestrator._rerank` |
| Ошибка на любой стадии | `Signal("error", message, stage)` — причина называет стадию, каскад не теряет контекст | `_run_stages`, `orchestrator.py:472-479` |
| Сканы в корпусе | `ocr.available: false` виден в health; `ContentType` (`models.py:89`) различает текст и скан | `docs/LIMITS.md` §4 |
| Конфликт редакций | при 0 правил шаги пропускаются, а не выводят пустую строку | `_has_rules` |

## 8. Что НЕ входит в архитектуру (и почему)

Называю прямо, чтобы это не искали в коде:

- **Нет агентного цикла.** Модель не выбирает следующий шаг. Один вызов —
  потому что корпус плотный и поиск уже даёт нужные фрагменты. Подробно —
  `docs/LEX-LIMITS.md` §3.
- **Нет OCR.** Сканы не читаются; распознанный скан делает цитату недословной.
- **Нет единого входа.** Роль приходит в запросе; аутентификации нет.
- **Нет интеграции с корпоративными системами.** Письма имитируются
  (`QUALITY_EMAIL` на `example.invalid`), изменения в регламенты не вносятся.
- **Нет векторной БД.** Индекс — файл `.npz` целиком в памяти; для 154 чанков
  это правильно, для тысяч документов нужен другой слой.

Ранняя версия этого документа (`docs/IIKUZNITSA-ARCHITECTURE.md`, 20.11.2026)
описывала планируемую агентную архитектуру с локальной Qwen3-8B как fallback.
Она не реализована и заменена этой. Старый документ оставлен как история.
