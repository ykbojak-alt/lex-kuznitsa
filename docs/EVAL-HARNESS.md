# EVAL-HARNESS — методика оценки RAG-контура ИИкузницы

**Статус:** методика готова до старта спринта, результатов ещё нет. Все числовые
значения метрик в разделе «Результаты» — **«не измерено»**, пока не проведён
прогон по протоколу ниже. Выдуманные числа в этот документ не попадают.

**Основа:** корпус `sample-corpus/` (генератор `demo/gen-sample-corpus.py`),
вопросы `sample-corpus/questions.jsonl`, критерии приёмки `docs/QA.md` §6 и §5.

---

## 1. Что оцениваем

| Объект | Значение |
|---|---|
| Документов в корпусе | 27 (20 обычных + 7 редакций конфликтующих правил) |
| Конфликтующих правил | 3 (`SR-01`, `SR-02`, `SR-03`) — по 2–3 редакции с разными датами вступления |
| Вопросов всего | 92 |
| Из них обычных (по конкретному документу) | 80 — по 4 на каждый из 20 обычных документов |
| Из них по правилам (`kind = rule_asof`) | 12 — по 4 на каждое правило |
| Из них требуют обоснованного отказа | 3 — дата раньше первой редакции правила |
| Опорная дата (`as_of`) | 2026-11-26 — день старта спринта |
| Seed генератора | 20261126 (корпус детерминирован) |

Три класса проверок:

1. **Поиск** — находит ли система нужный документ.
2. **Ответ** — соответствует ли ответ содержимому найденного документа.
3. **Действующая редакция** — применяет ли система ту редакцию, которая действует
   на указанную в вопросе дату, и отказывается ли, когда правило на эту дату
   ещё не введено.

Третий класс — главный: он отделяет «просто нашёл похожий текст» от «выбрал
правильный документ по дате».

## 2. Протокол прогона (фиксируем до прогона, меняем только новым прогоном)

| Параметр | Значение | Почему важно |
|---|---|---|
| Корпус | `sample-corpus/`, seed `20261126` | иначе результаты несопоставимы между прогонами |
| Хэш корпуса | `sha256` из `sample-corpus/manifest.json` (по каждому файлу) | фиксирует состояние данных |
| Индексация | один и тот же способ нарезки для всех прогонов | иначе меняется recall |
| Модель | конкретная, зафиксированная в логе | иначе невоспроизводимо |
| Путь инференса | **Nexus Link (sage-pl) — основной**; локальная Qwen3-8B — только fallback | смена пути = новый прогон, числа разных путей несопоставимы |
| Температура | 0 | убирает случайность формулировок |
| Число кандидатов (top-k) | фиксируется до прогона | влияет на recall и на скорость |
| Доступ в сеть | выключен, кроме вызова модели | иначе ответ может прийти извне |
| Порядок вопросов | как в `questions.jsonl` | не перемешивать без нужды |

Любое изменение этих параметров = новый прогон с новой строкой в таблице результатов.

## 3. Как прогонять

### 3.1 Быстрый путь — проверка обвязки (до появления продукта)

```bash
sh demo/run-local.sh
```

Скрипт последовательно: проверяет окружение (`scripts/preflight.sh`), проверяет **путь
инференса**, генерирует корпус и прогоняет **5 вопросов** через лексический поиск без
LLM. Это проверка конвейера (индексация → поиск → сверка), а не оценка качества
ответов модели.

Проверка пути инференса (шаг 2) фиксирует текущую конфигурацию:

| Путь | Роль | Что проверяется |
|---|---|---|
| Nexus Link (sage-pl) | **основной** | адрес `NEXUS_LINK_BASE_URL` задан и endpoint отвечает (любой HTTP-код, включая 401 — это значит «достижим, нужен токен») |
| Локальная модель Qwen3-8B | **fallback** | доступность локального сервера модели (`LOCAL_MODEL_BASE_URL`, по умолчанию `http://127.0.0.1:8080/v1`) и наличие GPU |

Правило выбора пути: **пока Nexus Link отвечает, вызовы идут на него**; локальная
модель включается только если основной путь недоступен. Скрипт печатает, какой путь
активен, и записывает его в артефакт прогона (`stub-summary.json`, поле
`inference_path`). Ключи и токены не выводятся никогда — только адреса и HTTP-коды.
Флаг `--require-inference` делает недоступность основного пути блокирующей (код
возврата 1) — он нужен на старте спринта, когда прогон уже идёт через стенд.

Путь инференса **не влияет на корпус**: `sample-corpus/` от пути не зависит и
перегенерировать его при смене пути не нужно.

### 3.2 Полный путь — оценка (после появления продукта)

Контракт раннера, который пишется на старте спринта:

- **вход:** `sample-corpus/questions.jsonl` (92 строки JSON) + адрес стенда;
- **для каждого вопроса:** вызов демо-API, получение ответа, извлечение `doc_id`,
  на который опирается ответ (идентификатор документа из корпуса), и текста ответа;
- **путь инференса:** раннер фиксирует в каждой записи, какой путь обслужил запрос —
  `nexus-link` (основной) или `local-fallback`. Значение берётся из метаданных
  ответа демо-API, а не предполагается: если Nexus Link был недоступен и запрос
  ушёл на локальную модель, это попадает в лог как fallback;
- **выход:** `eval/results-<path>-<model>-<YYYYMMDD>.jsonl` — по строке на вопрос,
  где `<path>` = `nexus-link` или `local-fallback`:

```json
{
  "question": "…",
  "kind": "rule_asof",
  "rule_key": "SR-01",
  "as_of": "2026-11-26",
  "inference_path": "nexus-link",
  "expected_doc_id": "ТЗ-ЭКЗ-СР01-Р2",
  "expected_answer": "пяти рабочих дней",
  "refusal_expected": false,
  "retrieved": ["ТЗ-ЭКЗ-СР01-Р2", "…"],
  "cited_doc_id": "ТЗ-ЭКЗ-СР01-Р2",
  "answer": "…",
  "refused": false,
  "latency_ms": 1234,
  "usage": {"prompt_tokens": 0, "completion_tokens": 0}
}
```

- **шаг подсчёта:** отдельный скрипт `demo/score-eval.py` (пишется на старте) читает
  файл результатов и печатает таблицу метрик из §4.

Прогон должен быть **одним непрерывным**, без ручной правки ответа «на глаз»:
любая правка ответа вручную — нарушение протокола и повод перепрогнать.

## 4. Метрики

### 4.1 Поиск (retrieval)

| Метрика | Определение | Как считается |
|---|---|---|
| `recall@1/3/5` | доля вопросов, для которых нужный документ попал в top-k выдачи | `expected_doc_id` есть в `retrieved[:k]` |
| `MRR` | средняя обратная позиция нужного документа (1/rank, 0 если не найден) | по всем вопросам |
| `hit rate по классам` | те же величины отдельно для `generic` и `rule_asof` | разрез по `kind` |
| `confusion: отказ/не-отказ` | сколько раз система отказалась там, где отказ не требовался, и наоборот | по `refusal_expected` |

Отдельно считается **`rule_asof` recall**: правильный документ — это конкретная
**редакция**, а не любой документ по теме. Если в выдаче только более ранняя
редакция — это провал, даже если тема совпала.

### 4.2 Ответ (answer quality)

| Метрика | Определение | Как считается |
|---|---|---|
| `answer accuracy` | доля вопросов, где ответ содержит ожидаемое значение | нормализованное сравнение строк: регистр, пробелы, `ё/е`, порядок слов |
| `faithfulness` | доля фактических утверждений ответа, подтверждённых найденным документом | проверка человеком на выборке ≥20 ответов либо judge-моделью с цитированием; метод фиксируется в логе |
| `completeness` | для вопросов по правилам — названа ли дата вступления применённой редакции | автоматически: ищем дату в ответе |
| `citation correctness` | совпадает ли `cited_doc_id` с документом, из которого взят факт | автоматически |

`faithfulness` **не измеряется автоматически по одному правилу**: если выбран
ручной способ, в лог пишется, сколько ответов проверено и кем.

### 4.3 Отказ (refusal)

| Метрика | Определение |
|---|---|
| `refusal accuracy` | доля вопросов с `refusal_expected: true`, на которые система отказалась вместо ответа |
| `false refusal rate` | доля остальных вопросов, на которые система отказалась зря (перестраховка) |

Отказ засчитывается, если в ответе есть явный отказ («не введено», «не действует
на эту дату», «не могу определить») **и при этом в ответе нет значения ни одной
редакции**. Отказ с подставленным значением — не отказ, а подмена: это и штрафуется
как неверный ответ.

### 4.4 Актуальность редакции (recency)

| Метрика | Определение |
|---|---|
| `as-of accuracy` | для `rule_asof` вопросов: применена ли редакция, действующая на указанную дату |
| `future-revision leakage` | сколько раз в ответе применена редакция с датой вступления **позже** указанной (должно быть 0) |

Проверяется автоматически: ожидаемое значение и `expected_doc_id` известны из
`questions.jsonl`.

### 4.5 Эксплуатация

| Метрика | Определение | Источник |
|---|---|---|
| `latency p50 / p95` | время ответа на вопрос | замер раннера |
| `tokens per question` | prompt + completion | `usage` от провайдера |
| `cost per question` | токены × цена модели | счёт провайдера + его прайс |
| `стоимость сценария` | сумма по всем вопросам | счёт провайдера |

Цены берутся из прайс-листа провайдера на дату прогона; ссылка на прайс пишется в лог.

**Путь инференса влияет на эксплуатационные показатели**, поэтому сравнивать их
между путями напрямую нельзя:

| Показатель | Nexus Link (основной) | Локальная модель (fallback) |
|---|---|---|
| `cost per question` | токены × цена провайдера, по счёту | 0 — внешнего счёта нет |
| `latency p50 / p95` | время ответа внешнего сервиса | время ответа на своей GPU, обычно выше |
| ограничение | доступность и лимиты сервиса | VRAM (8 ГБ на машине разработки) и скорость генерации |

Итог по прогону на fallback-путе — **отдельная строка** в таблице результатов, а не
замена строки основного пути.

## 6. Ловушки, на которые корпус настроен специально

1. **Будущая редакция.** У `SR-01` редакция 3 вступает 2027-01-01. Вопрос на
   2026-11-26 обязан получить значение редакции 2, а не самой «свежей» по дате
   в корпусе. Это самая частая ошибка: «найти самый новый документ».
2. **Отказ вместо ответа.** На дату раньше первой редакции правила правильный
   ответ — «на эту дату правило не введено». Система, которая процитирует
   ближайшую редакцию, получает штраф за `refusal accuracy` и `false claim`.
3. **Три редакции одного правила.** Формулировки почти совпадают — лексический
   поиск без учёта даты выдаёт их вперемешку.
4. **Разные формулировки одного и того же.** Обычные документы используют одну и ту же
   тему с разными деталями (срок, система, подразделение) — ответ должен опираться
   на документ, а не на похожую фразу из другого.
5. **Синтетические «контрагенты».** В паспортах есть ИНН и номера договоров — они
   вымышленные, и ответ про них не должен выдумываться.

## 7. Правила честности измерений

- Метрика без источника (лог, счёт, прайс) = «не измерено».
- Один прогон — одна строка в таблице; подменять числа разными прогонами нельзя.
- **Прогон через Nexus Link и прогон через локальный fallback — разные прогоны.**
  Их числа нельзя смешивать, усреднять или выдавать одно за другое; в лог пишется
  фактический путь каждого прогона.
- Если менялся корпус, модель, нарезка или параметры — это новый прогон, а не
  «улучшение» прежнего.
- Точность ответов измеряется на фиксированном корпусе; на данных заказчика те же
  метрики не переносятся автоматически — это проверка контура, а не продукта.
- Публичные числа из предыдущих прогонов нельзя выдавать за результаты текущего.

## 8. Порядок работы на старте спринта

1. Зафиксировать протокол §2 (путь инференса, модель, нарезка, top-k) в логе прогона.
2. Проверить путь инференса: `sh demo/run-local.sh --require-inference` — основной
   путь (Nexus Link) должен отвечать; при его недоступности прогон на локальном
   fallback помечается в логе как отдельный прогон.
3. Реализовать `demo/score-eval.py` по контракту §3.2.
4. Прогнать все 92 вопроса, заполнить §5.1–5.3, разобрать провалы.
5. Перенести те же числа в `docs/QA.md` §5 и §6 — измерение должно быть одно, а не
   два разных.

## 9. Воспроизведение

```bash
# корпус (детерминирован)
python demo/gen-sample-corpus.py --count 20 --seed 20261126 --clean

# проверка обвязки без модели
sh demo/run-local.sh

# проверка пути инференса: основной — Nexus Link, fallback — локальная модель
sh demo/run-local.sh --skip-preflight --require-inference

# самопроверка генератора
python demo/gen-sample-corpus.py --self-test
```

Манифест с хэшами всех файлов корпуса — `sample-corpus/manifest.json`; индекс с
перечнем документов и редакций — `sample-corpus/INDEX.md`.
