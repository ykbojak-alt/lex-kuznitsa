# Подключение LEX к вики заказчика (Atlassian Confluence)

Документ проектный: описывает сценарий внедрения, а не реализацию. Доступа к
базе заказчика у команды нет, адаптер не написан. Всё ниже — что именно
поменяется в LEX, если источником корпуса станет Confluence, и где проходят
границы этого изменения.

Зачем это важно для оценки: LEX уже отделяет **источник корпуса** от всей
остальной логики. Корпус читается из каталога по манифесту
(`lex.corpus.load_corpus`), и ничего кроме этого каталога конвейер не знает.
Поэтому переход на вики — это замена источника, а не переписывание продукта.

---

## 1. Что меняется и что нет

| Слой | Меняется? | Почему |
|---|---|---|
| Чанкинг по секциям | **нет** | режет markdown по `## N. Название`, окно 600 токенов с перекрытием 80 (`lex.corpus`) |
| BM25 + вектор + RRF | **нет** | `lex.index.SearchIndex`, слияние по рангам |
| Реранкер | **нет** | cross-encoder по паре «вопрос–чанк» |
| Гейт релевантности | **нет** | `subject_coverage` + косинус, пороги не зависят от источника |
| Clarify (уточнение параметров) | **нет** | `lex.dialogue`, читает манифест |
| Эскалация, кейсы | **нет** | `lex.cases`, `lex.access` (права записи) |
| Цитаты и проверка | **нет** | `lex.verify`, дословная сверка с фрагментом |
| Фильтр чтения по роли | **нет** (уже есть с v1.16) | `lex.access.filter_docs`, режим `department_read` |
| **Источник корпуса** | **ДА** | было: каталог `.docx` → markdown; станет: Confluence → markdown |
| **Манифест** | **ДА, расширяется** | новые поля: внешний URL, история версий, источник отдела |
| **Источник отдела документа** | **ДА** | сейчас поле `department` в манифесте; станет пространство/ограничения вики |

Одной фразой: **конвейер ответа не трогается, меняются вход и два поля
модели данных.** Это и есть основной аргумент сценария — риск внедрения
ограничен краем системы.

## 2. Экспорт: из Confluence в корпус LEX

### 2.1 Что забираем

Три вида объектов, потому что у них разная роль в LEX:

| Объект Confluence | Во что превращается | Роль в LEX |
|---|---|---|
| Пространство (space) | `business_line` / `department` документа | направление и отдел в манифесте |
| Страница (page) | markdown-файл документа | единица поиска |
| Страница верхнего уровня с дочерними | один документ с секциями | чанкинг по `##` |
| Вложение (attachment) | либо отдельный документ, либо ссылка | зависит от типа |
| История версий страницы | `conflict_rules` | редакции правила |

### 2.2 Эндпоинты

Базовый путь зависит от редакции продукта: **Cloud** — `/wiki/rest/api/…`,
**Server / Data Center** — `/rest/api/…`. Это первое, что надо зафиксировать
при внедрении, потому что пути и часть полей различаются.

**Инвентаризация**

```
GET /rest/api/space?limit=100&start=0
GET /rest/api/content?spaceKey=<KEY>&type=page&limit=50&start=0
    &expand=body.storage,version,history,ancestors
```

Постранично: в ответе `_links.next` содержит готовый URL следующей страницы.
Страницы берутся пачками (`limit`), иначе на большом пространстве запрос
упрётся в лимит ответа.

**Одна страница целиком**

```
GET /rest/api/content/{id}?expand=body.storage,version,history,space,ancestors
```

Именно этот вызов просили как основной. Поля, которые нужны:

| Поле | Зачем |
|---|---|
| `body.storage.value` | XHTML-тело страницы — источник текста |
| `version.number` | номер редакции → `revision` |
| `version.when` | дата редакции → `effective` |
| `history.createdDate` | дата создания → `issued` |
| `space.key`, `space.name` | пространство → направление |
| `ancestors` | родительские страницы → иерархия документа |
| `_links.webui` | путь к живой странице → `source_url` |

**История версий**

```
GET /rest/api/content/{id}/version?limit=50
```

Список версий с датами. Отсюда собираются редакции правила (см. §3).

**Вложения**

```
GET /rest/api/content/{id}/child/attachment?expand=version
GET /rest/api/content/{id}/download/attachments?...   # тела файлов
```

Вложения разбираются по типу: `.docx` / `.pdf` идут обычным путём конвертера
(они уже умеют `dataset/`), картинки не индексируются, но могут попасть в
цитату как ссылка.

### 2.3 Путь преобразования

```
Confluence REST API
   ↓  XHTML (storage format)
   ↓  очистка макросов и разметки
   ↓  markdown с заголовками «## N. Название»
   ↓  manifest.json  (+ source_url, revisions, rights)
   ↓  lex.corpus.load_corpus  →  чанки
```

**XHTML → markdown** — единственное место, где нужна аккуратность, и главная
техническая работа сценария. Тело страницы в storage-формате — это XHTML с
макросами Atlassian (`<ac:structured-macro>`, `<ri:page>`, `<ac:image>`).
Заголовки страницы (`<h2>`) должны стать `##`, иначе чанкинг не найдёт границы
секций: `lex.corpus` режет по регулярному выражению `^##\s+(.+?)\s*$`.
Списки и таблицы сохраняются как есть — они и сейчас попадают в чанки.

Правила преобразования, которые важно зафиксировать заранее:

1. `<h2>` → `## `, `<h3>` → `### ` (глубже не режем — секция одна).
2. Таблицы: строки → строки markdown. Норма в регламентах часто живёт в
   таблице (сроки, ответственные), терять её нельзя.
3. Макросы-вставки (`<ac:structured-macro>`, включения других страниц):
   **раскрывать** включённую страницу как текст, а не выкидывать. Если
   раскрыть нельзя — оставлять видимую пометку, чтобы пробел был заметен.
4. Служебные блоки (оглавление, метки, комментарии) — отбрасывать.

Отдельно: **документ = страница верхнего уровня, секции = дочерние страницы**
или заголовки внутри одной страницы. Это выбор внедрения, и он влияет на
гранулярность цитат. В текущем корпусе документ — файл, секция — `##`.
Рекомендация: секция = заголовок второго уровня внутри страницы, потому что
тогда ссылка на цитату ведёт на страницу и якорь, а не на отдельную страницу.

### 2.4 Что уже готово

Конвертер `demo/convert-dataset.py` пишет ровно тот формат, который читает
`lex.corpus`: один markdown на документ, заголовки `## N. Название`,
`manifest.json` с `documents` и `conflict_rules`. Для Confluence меняется
**источник** этого скрипта (вместо `.docx` — REST API), а формат выхода
остаётся прежним. Это и есть точка подключения.

## 3. Редакции: история версий страницы как `conflict_rules`

### 3.1 Почему это важно именно здесь

Сейчас в реальном корпусе **конфликтующих редакций нет**. В
`corpus-real/manifest.json` список `conflict_rules` пуст — ноль правил.
Конвертер пишет об этом прямо:

> «Чего скрипт НЕ делает: не придумывает `conflict_rules`. В реальных
> документах нет версионированных редакций одного правила — это была
> синтетическая конструкция. Пустой список честнее выдуманного.»

Из-за этого шаг `resolve` в демо на реальных документах фактически холостой:
он отрабатывает, но говорит «правило не определено — действует как есть».

**Confluence это меняет по существу.** У страницы есть история версий с датами
— это настоящие редакции, а не выдуманные. Как только каждая версия страницы
становится записью в `conflict_rules`, шаг `resolve` начинает отвечать на
реальный вопрос: *какая редакция нормы действовала на указанную дату*.

### 3.2 Как это ложится на модель

В LEX правило (`lex.models.Rule`) — это набор редакций с датами, и на дату
выбирается последняя действующая (`Rule.effective_on`). Формат ответа шага:

> «N редакций, действует Р3 от 2026-03-01»

или, если ни одна не действует на дату:

> «N редакций, ни одна не действует на 2025-01-01: первая — с 2026-03-01»

Маппинг Confluence → правило:

| Confluence | Поле `conflict_rules` |
|---|---|
| `version.number` | `revision` |
| `version.when` (дата) | `effective` |
| `content.id` | `doc_id` |
| ключ правила (задаётся при внедрении) | `key` |
| текст версии | значение правила (`value`) |

### 3.3 Честная оговорка

**Дата редактирования страницы — не то же самое, что дата вступления нормы в
силу.** Страницу правят и по опечаткам, и по оформлению. Если брать
`version.when` как `effective` без разбора, LEX будет считать, что норма
изменилась, когда поправили запятую.

Поэтому при внедрении нужно правило отбора: какие изменения считать новой
редакцией нормы. Варианты, по возрастанию стоимости:

1. **Ручная разметка** ключевых страниц (нормы, сроки, ответственные) — верно,
   но требует человека.
2. **Фильтр по метке**: страницы с меткой «регламент»/«норма» версионируются,
   остальные — нет.
3. **Автоматически**: любая версия = редакция. Дёшево, но даёт шум в шаге
   `resolve`.

Рекомендация — вариант 2: метка на странице говорит, что её версии
значащие. Это минимальное допущение, которое делает `resolve` настоящим, и
оно проверяемо: если метки нет, поведение остаётся текущим (пустой список).

## 4. Права: ограничения вики → `role_id`

### 4.1 Что в Confluence и что в LEX

В Confluence права живут на двух уровнях:

```
GET /rest/api/space/{key}/permissions        # права пространства
GET /rest/api/content/{id}/restriction       # ограничения страницы
```

Первое — кто видит пространство целиком, второе — точечные ограничения на
страницу (чтение/запись для пользователей и групп). Оба уровня нужны:
страница может быть открыта в закрытом пространстве, и наоборот.

В LEX роль задаётся `role_id`, и определения ролей собираются **по манифесту
корпуса** (`lex.access.roles_for_corpus`). В модели прав v1.16 роли — это
реальные отделы организации, а не абстракции. Для текущего корпуса заказчика
(`corpus-real`) действует такой набор (`lex.access.ROLE_DEFS_REAL`):

| `role_id` | Название | Отделы | Видит документы |
|---|---|---|---|
| `technical` | Техническая дирекция | Техническая дирекция | КД-ПД-01 |
| `ib` | Дирекция ИБ | Дирекция ИБ | КД-ПС-02, КД-ПД-04 |
| `dbrct` | ДБРЦТ | ДБРЦТ | КД-ПД-03 |
| `quality` | Служба качества | все (`*`) | весь корпус |
| `director` | Руководитель | все (`*`) | весь корпус |

Роли `lawyer` / `it` из прежнего синтетического набора в реальной структуре
заказчика отсутствуют. Они не удалены, а имеют псевдонимы: `lawyer` и `it`
переводятся в `technical` (`access.ROLE_ALIASES`), причём **не** в `director`
— дать «юристу» права руководителя на весь корпус было бы утечкой, а не
совместимостью.

Маппинг: **группа Confluence → `role_id`**. Не пользователь, а группа —
потому что в организациях права дают группами, и это устойчивее к смене
сотрудников.

| Группа Confluence (пример) | `role_id` | Что видит |
|---|---|---|
| `lex-tech` | `technical` | документы Технической дирекции |
| `lex-ib` | `ib` | документы Дирекции ИБ |
| `lex-dbrct` | `dbrct` | документы ДБРЦТ |
| `lex-quality` | `quality` | весь корпус (сквозная роль) |
| `lex-directors` | `director` | весь корпус (сквозная роль) |

Соответствие «группа → отдел» устанавливается при внедрении по факту
структуры заказчика: роли строятся из отделов в манифесте, поэтому если в
корпусе появится новый отдел, роль для него появится вместе с ним, без правки
кода.

### 4.2 Где здесь настоящая развилка

Здесь надо сказать прямо, потому что это влияет на объём работ — и потому что
**это место недавно изменилось**.

**В v1.15 чтение было единым.** Шаг `permissions` был информационным: он
показывал «чтение: полный корпус» и ничего не отсеивал (`dropped = 0` жёстко).
Это расходилось с обещанием интерфейса («от роли зависит, какие документы
агент вправе показать»), и было признано неверным для приёмки.

**В v1.16 фильтр чтения включён.** Документ виден, если его отдел входит в
подразделения роли; `quality` и `director` видят всё. Фильтр —
**только по отделу**, не по направлению: направление — это тема документа, и
темы у отделов пересекаются («проектная деятельность» есть у трёх), поэтому
фильтр по направлению отнимал бы документы своего же отдела. Шаг
`permissions` теперь показывает настоящие числа: сколько документов отсеяно
и сколько осталось (`lex.access.filter_docs`, режим `department_read`).

| | v1.15 | v1.16 |
|---|---|---|
| чтение | единое, весь корпус любой роли | по отделу роли |
| шаг `permissions` | информационный, `dropped = 0` | `dropped` настоящий |
| роли | `lawyer`/`quality`/`it`/`director` | `technical`/`ib`/`dbrct`/`quality`/`director` |
| при чужом документе | отдавался | `403` с причиной «вне подразделения» |

**Что это меняет для Confluence.** Раньше я писал, что «права из пространств
вики — не бесплатный маппинг, а смена контракта», потому что фильтра чтения не
было вовсе. **После v1.16 это уже не так.** Механизм отсева существует и
работает по отделу. Задача подключения сводится к тому, чтобы **источником
отдела** документа стала вики (пространство или ограничения страницы), а не
поле `department` в манифесте. Это расширение существующего механизма, а не
введение нового поведения поверх «единого чтения».

Что при этом остаётся решением, а не механикой:

1. **Гранулярность.** LEX фильтрует по отделу (крупно). Confluence умеет
   ограничивать отдельные страницы для отдельных групп (мелко). Сопоставлять
   мелкое с крупным — выбор: либо пространство целиком = отдел (просто,
   грубее), либо ограничения страницы уточняют видимость внутри отдела.
2. **Пустой результат.** Если роль видит 0 документов, LEX отвечает
   `not_in_corpus` («в базе нет документов»), а не `no_access`. Для вики это
   важно: «нет прав» и «нет документа» — разные сообщения, и LEX намеренно
   говорит второе, потому что роль читать вправе.

Варианты, по-прежнему требующие слова заказчика:

| Вариант | Поведение | Следствие |
|---|---|---|
| **A. Пространство = отдел** | видимость по пространству Confluence | просто, совпадает с текущей моделью; ограничения отдельных страниц игнорируются |
| **B. Пространство + ограничения страниц** | отдел от пространства, уточнение от `restriction` | точнее, но маппинг групп обширнее |
| **C. Только открытые** | индексируются лишь страницы без ограничений | безопасно, но часть знаний выпадает из поиска |

Рекомендация — **A как минимум, B если заказчику нужна точность до страницы**.
Смена контракта для этого больше не требуется: фильтр включён, и подключение
касается источника атрибута «отдел».

### 4.3 Права — из источника, а не из манифеста

Сегодня отдел документа приходит из манифеста (`department` в `DocumentMeta`),
а определения ролей собираются из отделов манифеста автоматически
(`roles_for_corpus`). При подключении Confluence **отдел приходит из вики** —
из пространства, в котором лежит страница. Манифест при этом лишь фиксирует
снимок на момент сборки корпуса.

Практическое следствие остаётся: изменение прав в вики требует пересборки
корпуса, и об этом надо сказать заказчику прямо, чтобы не было ожидания
«поменял права — заработало сразу». Но сама модель ролей уже готова принять
такой источник: роли строятся из данных, а не из списка в коде.

## 5. Ссылки в цитатах: `source_url`

### 5.1 Чего не хватает сейчас

`lex.models.DocumentMeta` (`src/lex/models.py:261`) описывает документ
корпуса — `doc_id`, `title`, `file`, `sha256`, секции, тип содержимого — но
**поля для внешнего адреса в нём нет**. Цитата сейчас ссылается на документ
по `doc_id` и на файл в корпусе, а не на живой источник.

Для Confluence это недостаточно: пользователь хочет из цитаты перейти на
страницу в вики и увидеть норму в её актуальном виде.

### 5.2 Что предлагается

Добавить в `DocumentMeta` необязательное поле:

```
source_url: str = ""
```

Пустое значение — для корпуса из файлов (текущий случай), заполненное — для
внешнего источника. Это **аддитивное изменение**: оно не ломает существующие
манифесты, потому что поле необязательное и по умолчанию пустое.

Откуда берётся значение:

| Источник | Как получить URL |
|---|---|
| Confluence Cloud | `_links.base` + `_links.webui` из ответа API |
| Confluence Server | то же, но базовый путь без `/wiki` |

Для секции, а не только для страницы, полезно добавлять якорь (`#<заголовок>`),
если цитата относится к конкретному заголовку: тогда ссылка открывает страницу
на нужной секции, а не в начале.

### 5.3 Что это даёт проверке

Сейчас `lex.verify` сверяет цитату дословно с фрагментом корпуса — это
защищает от выдуманного текста. `source_url` добавляет второе измерение:
пользователь может сам открыть источник и убедиться, что фрагмент там есть и
не устарел. Для юридического продукта это сильный аргумент: цитата перестаёт
быть «текст, который LEX где-то нашёл», и становится «ссылка на норму».

---

## 6. Чего не делаем сейчас

Явно, чтобы не создавать ложных ожиданий:

* **Доступа к Confluence заказчика у команды нет.** Ни одного запроса к его
  вики не сделано.
* **Адаптер не написан.** Сценарий описывает, что нужно, а не то, что есть.
* **Синхронизация не настраивается.** Вопрос «раз в час или по вебхуку» —
  отдельный и не решён.
* **Сроков нет.** Документ описывает состав работ, а не план.

Границы сделаны так, чтобы внедрение можно было вести частями: экспорт
корпуса (§2) не зависит от редакций (§3) и от прав (§4); `source_url` (§5) —
самая независимая часть, её можно сделать первой.

## 7. Риски и открытые вопросы

| Риск | Почему важен | Что решает |
|---|---|---|
| Macros и вложения теряют норму при конвертации | норма часто в таблице или включённой странице; потеря — молчаливый пробел | проверка: сумма текста чанков не меньше текста секции (уже есть методика) |
| `version.when` ≠ дата вступления нормы | шаг `resolve` начнёт врать | фильтр по метке (§3.3) |
| Гранулярность прав: отдел vs ограничения страницы | LEX фильтрует по отделу, вики умеет мельче | выбор варианта (§4.2) |
| Объём пространства | полный экспорт может быть очень большим | инкрементальный экспорт по `version.when` |
| Различие Cloud / Server | другие пути API, часть полей отсутствует | зафиксировать редакцию продукта до работ |

Открытые вопросы к заказчику:

1. Confluence Cloud или Server/Data Center?
2. Какие пространства входят в корпус — все или перечень ключей?
3. Есть ли метка, по которой отличить регламент от рабочей страницы?
4. Ограничения страниц: LEX должен их соблюдать (и насколько строго)?
5. Кто владелец прав на публикацию экспортированного корпуса в LEX?

Ответы на эти пять вопросов определяют объём работ; без них сценарий остаётся
проектным, что для текущего этапа и требуется.
