## 2. Шаги в кадре: «N из 11» или «N из 9» — зависит от стенда

**Важная поправка MIMIC (t5), подтверждена кодом.** В интерфейсе счётчик рисуется
не как `[N/9]`, а как **«N из TOTAL»** — `src/web/progress-view.js:86`:
```js
this.count.textContent = this.done + ' из ' + this.total;
```

`total` приходит из SSE (`StepEvent.total`, `orchestrator.py:390`). По коду `HEAD`
`_total()` = `len(STEP_ORDER) - 2` при пустом `corpus.rules` (`orchestrator.py:416-419`),
и в обоих манифестах `conflict_rules: []` (проверено) → **на HEAD ожидается «N из 9»**.

Но **живой стенд `:4437` отдаёт `total: 11`** (два прогона 27.11, MIMIC wave13 D2) —
значит стенд собран не под HEAD либо на нём в правилах есть записи. В кадре будет
**«9 из 11»**.

**Гейт V4/V8:** титр обязан повторять то, что в кадре. До передеплоя стенда под
HEAD титр — «шаг 9 из 11»; после — «из 9». Одно из двух, не смешивать.

Состав стадий при этом одинаковый — 9 видимых:

| # | `key` | Титр в UI | Что должно быть видно |
|---|---|---|---|
| 1 | `accept` | Запрос принят | «роль Руководитель, дата отсчёта …» |
| 2 | `policy` | Проверка компетенции | «в компетенции: да · направление: …» |
| 3 | `decompose` | Разбор вопроса | разложенный вопрос |
| 4 | `inspect` | Разбор источников | типы источников |
| 5 | `retrieve` | Поиск | `BM25 N · вектор N → кандидатов N → после rerank N` |
| 6 | `cases` | Поиск по кейсам | сколько кейсов подошло |
| 7 | `permissions` | Проверка прав | «полный корпус (12 документов) · запись: разрешена» |
| 8 | `compose` | Сборка ответа | «из N фрагментов» или «модель вернула отказ» |
| 9 | `verify` | Самопроверка | сколько утверждений подтверждено цитатой |

`resolve` и `conflict` **не выводятся** — не путать с «сломалось». На отказе
`out_of_scope` прогон обрывается на шаге 2 — в кадре будет «2 из 11» (или «из 9»),
и это правильно.

## 2a. Почему «вектор 0» — это путь кэша, а не вопрос

**Находка MIMIC, проверена мной по коду.** «Вектор 0» и «близость 0.00» в шаге
«Поиск» означают «векторный канал выключен», а не «поиск не работает». Цепочка:

| Шаг | Код | Что происходит |
|---|---|---|
| путь кэша | `index.py:158` | `self._cache_path = corpus.root / ".lex-index.npz"` |
| `corpus.root` | `corpus.py:187` + `266` | `load_corpus_multi` берёт `bases[0]` → `corpus-real` |
| список чанков | `corpus.py:267-283` | **объединённый** (154 + 721) |
| сверка кэша | `index.py:193-201` | `ids != [c.chunk_id …]` → `return None` |
| следствие | `index.py:232-243` | `vector()` бросает `EmbeddingError` |
| деградация | `index.py:260-266` | `search()` ловит → `ve = []`, только BM25 |

Кэш от 154 чанков никогда не совпадёт с объединённым списком из 875 → на 12
документах «вектор 0» **при любом вопросе**. На диске это подтверждается:
`corpus-real/.lex-index.npz` есть (586 785 б, 26.11 15:56), `corpus-norm/` своего
кэша не имеет.

### Три добавки к находке (мои, проверены по коду)

1. **`/api/health` показывает «Embed: доступен» рядом с «вектор 0».** `probe_embed`
   (`probes.py:27-34`) пингует только `:8081/health` и про кэш не знает. В кадре
   будет видимое противоречие — провал 4.10 («нет заранее заготовленных бейджей»)
   и 4.11 (числа не бьются). **Это аргумент против A без A+.**
2. **A+ затирает рабочий кэш.** Пересборка под 875 пишет в тот же
   `corpus-real/.lex-index.npz`, а файл в `.gitignore:64` — git его не вернёт.
   Возврат к B = ещё одна пересборка (~12 мин по замеру roy1). **Скопировать `.npz` вне репозитория
   перед `--force`.**
3. **Цена A+ — десятки минут, но источники расходятся втрое.** Докстринг
   `embed_texts` (`index.py:87-97`): ~14 с/чанк при 2 потоках → 875 чанков ≈ 3,4 ч.
   **Замер ALICE на roy1 — 4.8 с/чанк → ≈ 70 мин.** Откат к B (154) — ≈ 12 мин.
   Скрипт печатает обе оценки. **На сервере скорость своя — замерить до запуска.**

### Что я сделала в `demo/` (моя зона)

`demo/build-index-cache.py` получил `--corpus-norm` (аддитивно; без флага — прежнее
поведение, один корень). Кэш теперь можно построить от объединённого корпуса:


Это закрывает A+ по коду. **Запуск — CODEX по команде ALICE** (пересборка грузит

### `chunk_id` позиционный — кэш привязан к составу корпуса

`chunk_id = f"{meta.doc_id}#{pos:04d}"`, где `pos = len(corpus.chunks)` — сквозной
по объединённому корпусу (`corpus.py:200-205`). Значит id зависит от **состава
документов, их порядка и разбивки на чанки**. Следствия:

1. **Кэш валиден только при том же составе.** ALICE сверила сервер по sha256:
   документы, порядок и `conflict_rules` совпадают с локальными → `chunk_ids`
   совпадут, кэш переносим. Но это верно **на момент проверки**: любая правка
   корпуса (добавили документ, поменяли разбивку) сдвигает `pos` и обнуляет кэш.
2. **Контрольный вопрос после рестарта: «вектор N», не 0.** Если 0 — id не совпали
   (корпус изменился после проверки), кэш пересобирать.
3. **После пересборки под 875 локальная репетиция на 4 регламентах даст «вектор 0».**
   Это ожидаемое следствие (id от объединённого списка), а не дефект. Не путать
   с поломкой.

**Предупредить CODEX и MIMIC:** один кэш — один состав. Кэш, снятый при одном
корпусе, на другом молча не применится (даст «вектор 0»), а после смены разбивки —
даст неверные `chunk_ids` и, если размерность совпадёт, тихий мусор вместо ошибки.

### Кэш не хранит модель и размерность — совпадение `chunk_ids` не доказывает сравнимость

`_save_cache` пишет только `vecs` и `chunk_ids` (`index.py:183-187`) — **ни имени
модели, ни размерности**. Сходство считается как `sims = self._vecs @ qv`
(`index.py:246`), где `qv` приходит с эмбеддера **того** стенда, который отвечает.
Значит сверка `chunk_ids` доказывает «те же документы», но **не** «те же векторы».

Два разных отказа, и они не равны по опасности:

| Что не совпало | Что будет | Видно ли |
|---|---|---|
| размерность вектора | `np.matmul` бросает `ValueError`, а `search()` ловит **только** `EmbeddingError` (`index.py:262-266`) → прогон падает | да, сразу |
| модель при той же размерности | **тихий мусор**: «вектор N» в кадре есть, косинусы случайные, ответы неверные | **нет** |

**Проверка перед записью — не только «вектор N», но и близость.** При живом
векторном канале косинус лучшего совпадения на релевантном вопросе — не около нуля.
Если «вектор N», но `близость 0.00`–`0.05` на вопросе по регламенту — векторы не
сравнимы, кэш собран другой моделью.

**Что сверить на сервере:** `LEX_EMBED_MODEL` (`index.py:35`, по умолчанию `bge-m3`,
dim 1024) — значение то же, что локально, и `dim` в `GET :8081/health` = 1024.
Совпадения sha256 документов (проверка ALICE) для этого **недостаточно**: она
про корпус, а не про эмбеддер.
